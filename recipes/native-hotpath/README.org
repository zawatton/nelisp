#+TITLE: Recipe — native hot path

* Shape

Put the functions that need to be fast in their own file, compile that
file to a =.neln= artifact, and let the manifest tell you — per
function — whether they actually went native.

#+begin_src sh
nelisp compile-elisp-artifact --kind neln --input hot.el --output hot.neln
nelisp inspect-elisp-artifact hot.neln
#+end_src

* Two claims, two gates

These are true on different sets of machines, so =verify.sh= reports
them separately.

| gate                         | claim                          | where                                    |
|------------------------------+--------------------------------+------------------------------------------|
| =recipe-native-hotpath=      | it compiles, and the manifest says which functions are native | Windows and linux-x86_64 (fixed 2026-08-22; was Windows-only, see below) |
| =recipe-native-hotpath-exec= | the compiled code runs, natively — proven by executing the compiled function and checking its answer | linux-x86_64 only today |

The execution limit is not a guess: the repository's own tests gate on
it (=skip-unless= a linux-x86_64 predicate throughout
=test/nelisp-artifact-native-exec-test.el=), and on Windows
=native-exec-elisp-artifact= exits 1.  The artifact's object format is
=nelisp-aot-elf-v1= even when =:target= is =x86_64-w64-mingw32=.

** And the compile half does not hold on Linux either (2026-08-18)

Running this recipe in WSL Debian for the first time, both functions
fell back:

#+begin_example
:native-report ((:name "hot-sum-to"  :native nil
                 :reason "write-region stub: wrf returned 628 (expected 623)
                          path=.neln-probe.o.0.972598")
                (:name "hot-checksum" :native nil ...))
#+end_example

The source is pure ASCII.  What fails is the compiler writing its own
*object file*: =write-region= checks its work by comparing a character
count against the byte count written, and an object file is full of
bytes above 127, so the write succeeds and then signals.  The compiler
reads that as "cannot go native" and falls back.

So the defect the =batch-data= recipe records as an annoyance for
Japanese text silently disables native compilation here — on the one
platform that can execute the result.  The recipe's checks caught it,
which is what they are for; the claim in the table above was corrected
rather than the check relaxed.

Keeping them apart matters: folded into one gate, the compile half —
which works, and which is the half you can act on today — would be
hidden behind a permanent red on every non-Linux machine, and a gate
that always fails is a gate everyone learns to ignore.

** Fixed 2026-08-22: the write-region check was already fixed; two other bugs were not

Re-running this recipe on 2026-08-22 (same shape, WSL Debian, updated
tree) reproduced a *different* failure than the one above:
=write-region= itself no longer signalled — its own byte-count check had
already been corrected to compare against =string-bytes= rather than
=length= — but the compiled function still fell back, and once it did
not, the emitted =.neln='s embedded object decoded to an ELF file
=objcopy= rejected: first as unrecognized, then, after the first fix
below, as "a section extending past end of file".  The 2026-08-18 entry
above was accurate for what it measured; the actual blocker had moved.

Both remaining bugs were the same defect family as the =write-region=
check — Doc 161's char-aware =aref=/=length= misreading a raw byte
buffer — just at call sites that check had not covered:

1. *=base64-encode-string=* (=scripts/nelisp-stdlib-prelude.el=), which
   the compiler uses to embed the compiled object in the =.neln=, read
   its input with =aref=/=length=.  Those decode UTF-8 characters, not
   bytes, so any byte >= 128 in the object — ordinary in machine code —
   was misread, corrupting the embedded payload while the base64
   alphabet math still produced *some* answer, so nothing signalled.
2. *The ELF writer's own section-size arithmetic*
   (=lisp/nelisp-elf-write.el=, both =nelisp-elf--build-rich= and the
   ET_REL sibling =nelisp-elf--build-rel=) sized =.text=/=.rodata=/=.data=
   with plain =length= on buffers that can hold bytes >= 128, instead of
   the module's own established =nelisp-elf--byte-length= (= =string-
   bytes=) helper — the same fix already used elsewhere in the same file
   for exactly this reason.  Every section offset built from an
   undercounted =text-size= was then wrong.

Both were fixed with the existing byte-clean pair, =string-byte= /
=string-bytes= (Doc 161), not a new mechanism — reusing =nelisp-elf--
byte-length= for #2, and the same idea (read the byte at a byte index,
not the character at a char index) for #1.  One trap surfaced fixing #2:
=nelisp-elf--build-rich='s =text=/=rodata=/=data= are *not* unibyte-
coerced at binding time the way the ET_REL sibling's are, so on host
Emacs (where the ERT suite runs) they can be genuinely multibyte, and
=string-bytes= on an uncoerced multibyte buffer over-counts the same way
=length= on a standalone-runtime raw-byte buffer under-counts.
Coercing at binding time, matching =nelisp-elf--build-rel=, made the
byte count agree with the actual write on both runtimes at once;
=nelisp-elf-write-cbuf-large-rich-correct-bytes= catches a regression
either way.

Measured, both gates green on linux-x86_64:

#+begin_example
  ok   compiled to a .neln artifact
  ok   both functions listed in the native section
  ok   hot-sum-to reported as natively compiled
  ok   sensitivity control: an absent symbol is not reported
gate report: target/gates/recipe-native-hotpath.json (pass, ran 4, failed 0)
  ok   native-exec hot-sum-to 10 -> 55
gate report: target/gates/recipe-native-hotpath-exec.json (pass, ran 1, failed 0)
#+end_example

=hot-sum-to 10 -> 55= is native code actually running, not merely "no
error": =native-exec-elisp-artifact= links the compiled object into a
tiny C driver via =cc=/=objcopy= and executes it.  Two independent
compiles of =hot.el= produce byte-identical =.neln= output (=sha256sum=
equal).  The wider battery — =make compile=, =parens-check=,
=generated-source-parse=, the full ERT suite, =standalone=, all 28
reader smokes, =nelisp-native-artifact-gate= (9/9), =nelisp-performance-
gate= (9/9), =emacs-parity=, and =binary-size-ratchet= — is green on the
same tree with these fixes in place.

* What the compile half is actually good for

A regression guard.  The manifest carries a per-function report:

#+begin_example
:compile-report ((:name "hot-sum-to" :native t) (:name "hot-checksum" :native t))
#+end_example

A change that quietly makes a function ineligible for native
compilation does not fail any test — it just gets slower, somewhere,
later.  Checking the manifest turns that into a build failure at the
moment it happens.  That is worth wiring up even on a machine that
cannot run the artifact.

* Verify first

#+begin_src sh
recipes/native-hotpath/verify.sh
#+end_src

Four checks, the fourth of which asks the manifest about a symbol that
does not exist and requires a negative answer.  Without that control,
the other checks would keep passing if the pattern they grep for
silently stopped matching.

* What it cannot do

- *Run anywhere but linux-x86_64* (see above).
- *Be self-contained.*  An artifact that calls libc emits relocations a
  linker must resolve; the =.el= alone does not run such code.
- *Float freely.*  f64 arithmetic is x86_64 only, =extern-call= caps at
  eight f64 arguments, and =va_arg= of a double is a loud error.
- *Escape the boundary ABI.*  Multi-defun artifacts have known limits
  around boundary slots; =docs/design/142-native-exec-findings.md= is
  the reference, and that area is under active work.

=docs/runtime-limitations.md= is the full list, grouped by how badly
each item breaks C-equivalence.  Read it before assuming a compiled
function behaves like its C original.

* Where to cut

Replace the two functions in =skeleton/hot.el=.  Keep the file small
and keep the arithmetic integer; the point of the shape is that the
hot path is separable, not that everything moves into it.
