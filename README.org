*A Lisp for hackers — and a Lisp you can hack.*

Every layer of NeLisp, from the reader to the GC and the native code
emitters, is Elisp you can read, redefine, and reload from the REPL
that is running it.  There is no C core underneath to treat as a black
box: when the runtime does something you don't like, the fix is Lisp,
and you can try it without restarting.

* Start developing: REPL → error → edit → reload

For a source checkout, start with the
[[file:docs/repl-development.md][REPL development guide]]. It includes first-time setup and a runnable
example that finds an error, rebuilds one file, and calls its replacement
in the same process while keeping session state.

#+begin_src sh
make standalone-reader
tools/ai/nelisp-ai.sh repl
#+end_src

This development command preloads the full artifact runtime required by
=nelisp-artifact-reload-source-file=. The guide describes the supported
=defun=-only source files and the limits of native-code replacement.
Load =(require 'nelisp-repl-development)= in that REPL for explicit failure
recording/retry, function provenance, GC diagnostics, and session replay
exports. =(nelisp-repl-help)= lists the commands; the guide gives examples.
It works as the starting point for a new human or AI session; prior chat
history and private workspace configuration are not required. AI agents
should also read [[file:AI.md][AI.md]] for the repository workflow and verification rules.

For structured tool responses, start with the
[[file:docs/development-protocol.md][development protocol guide]]. Its JSON CLI and host Emacs dispatcher share
one backend, identify unavailable operations, and keep incomplete verification
visible. This source-query interface complements the persistent REPL workflow.

Allocator and GC development has a separate opt-in Linux x86_64 build:

#+begin_src sh
make runtime-reload-reader
NELISP_BIN=target/nelisp-runtime-reload tools/ai/nelisp-ai.sh repl
#+end_src

The [[file:docs/repl-development.md][native runtime workflow]] explains how to edit the collector, compile a
replacement, and publish it in the running REPL. Keep the public runtime
ABI and heap layout compatible; layout changes require a new process.

User-defined raw native functions can also expose stable entry addresses via
=nelisp-native-unit-rebuild-and-reload=. The [[file:docs/repl-development.md#replace-user-defined-native-functions][native unit walkthrough]] shows
how to replace a closed unit while its native callers keep the same address.
This currently supports fixed integer/pointer SysV signatures on Linux x86_64;
existing executable direct calls are not automatically redirected.

* TL;DR

NeLisp is a from-scratch Emacs Lisp runtime where essentially the
entire language layer (JIT, allocator, GC, coding-system, evaluator,
bytecode interp, reader, special forms, builtin dispatcher, object
file writers, native code emitters, and standalone OS surface) is
written in Elisp itself.

In the wider "replace Emacs" effort, this repo is *Layer 1* (the
runtime / reader / AOT compiler that produces =target/nelisp=).  *Layer 2*
(Emacs semantics) began as the sibling repository =nelisp-emacs= and now
lives in this tree as =packages/emacs-lib-*= (Doc 211, see
[[file:docs/design/211-emacs-api-packages.org][the design]]).  *Layer 3* (X11 drawing and input, =nelisp-gui=) was
imported as =gui/=.  The 3-layer responsibility boundary, inter-layer
contracts, and completion conditions are fixed in
[[file:gui/docs/design/00-three-layer-architecture.org][=gui/docs/design/00-three-layer-architecture.org=]].

The important claim is not merely "Elisp can call into a runtime".
NeLisp's runtime implementation is Elisp: the evaluator, reader,
compiler, allocator, GC, object writers, and native code emitters live
as Lisp source that the project can load, evaluate, redefine, compile,
and eventually self-host.  The OS-facing pieces are moving the same
way: standalone file I/O, stdout/stderr, process exit, raw memory,
=mmap=-backed allocation, atomics, =clone(2)=, =fork(2)=, and the
syscall surface used by the standalone reader are expressed from Elisp
via AOT codegen and =syscall-direct=.

What the runtime consists of:
- *Pure-Elisp runtime implementation* — evaluator, reader, special
  forms, builtins, compiler, allocator, GC, object writers, codegen,
  and standalone OS interaction all live in Elisp source.
- *Cross-platform support* on 4 targets — linux/x86_64,
  linux/aarch64, macos/aarch64, windows/x86_64 — with pure-elisp
  object-file writers (ELF, Mach-O, PE/COFF) and pure-elisp asm encoders
  (x86_64 with both SysV and Microsoft x64 ABIs, plus AArch64 AAPCS).
  See =Cross-platform support=.
- *Self-host + parallel build* — a pure-elisp AOT-AOT binary
  (=target/nelisp=, pure Elisp) loads its own
  compiler and compiles Elisp source → native ELF *with no Emacs in
  the loop*, including recursion (=(fact 5)= → exit 120),
  multi-threaded native programs (=clone(2)= + atomics), and *N units
  compiled concurrently* (=fork(2)= workers).  All CI-gated.  See
  =Standalone self-host & parallel build=.
- *REPL-driven runtime development* — the same pure-Elisp standalone
  reader starts a REPL with no arguments; scripts can use
  =--repl [--no-prompt]=.  It keeps one live evaluator
  environment, so redefining a function and calling it again takes
  effect immediately, including through persistent
  =nelisp--eval-source-string=.
- *Low-footprint standalone load* (measured 2026-06) — a hybrid
  refcount+tracing *compacting* GC (=mmap=-chunked arena, segregated
  free-list, a moving collector that forwards live objects and
  =munmap=s reclaimed chunks) together with an *8-byte tagged-word
  container representation* (=NlConsBox= 72→24B; vector / record / cell
  slots 32→8B) cut the full 319-file vendor-load peak RSS from *1.80GB
  to 118MB (−93%)* and the load time *≈13×* (13.4s → 0.9s).  A container
  slot (cons car/cdr, vector element, cell value) is either an immediate
  (=Nil=/=t=/fixnum) or an 8-byte pointer to a 32-byte child box; the GC
  marks, forwards, and moves them word-aware.  Validated at the time by a
  50× load soak under compaction.
- *Reader/core breadth since v0.5.1* — correctly-rounded float parse /
  print paths, broader Common Lisp / Emacs Lisp prelude coverage,
  additional raw syscall surface, AOT data/blob relocations, defined
  varargs, =f64= extern returns, bucketed hash tables, incremental
  =load=, and native list-search hot paths for SMIE / Org-style loads.

Use cases: running Elisp on machines without Emacs, and as a
substrate for Lisp Machine / new-dialect experiments.

* What NeLisp is

A research project to implement Emacs Lisp on a substrate other than
the existing Emacs C core — modeled after SBCL (Common Lisp
implemented in itself, on a small non-Lisp runtime) and deliberately
*not* a Scheme rewrite or a rewrite of the entire Emacs C core in a
different systems language.

The runtime is implemented in Elisp itself.  NeLisp keeps the language
surface, compiler, memory manager, object writers, OS-facing standalone
driver, and development REPL in Lisp source so the system can inspect
and modify itself while it is running.

Current source is centered in =lisp/=, =src/=, =packages/=, and
=scripts/=, with the AOT compiler emitting native object code from
Elisp forms.

Object file writers, asm encoders, and ABI-aware codegen for 4 OS×arch
targets are also pure Elisp.

** Two things Emacs proper doesn't ship in the same form

- *A JIT and AOT compiler written in Elisp itself.*  Emacs 28+ has
  native-comp, but it depends on libgccjit (an external C library)
  and is used as AOT in practice.  NeLisp's compilers (=lisp/nelisp-jit-*.el=,
  =lisp/nelisp-aot-compiler.el= and the assemblers) are Elisp source you can
  read end-to-end and modify, with runtime codegen via =mmap= + =PROT_EXEC=.
- *Real parallel execution.*  Emacs's =make-thread= is cooperative —
  one Lisp thread runs at a time.  NeLisp runs allocating Elisp on real
  =clone(2)= threads with a park barrier for the collector (see
  =The park barrier=), and =fork(2)= workers for parallel builds.

* Standalone self-host & parallel build

The pure-Elisp AOT toolchain now produces a *standalone
interpreter binary* — =target/nelisp=, built by =make
standalone-reader= — that runs with *no Emacs in the loop
at all*: it starts a REPL when launched with no arguments, loads an
=.el= file via =argv[1]=, evaluates it, and exits with the low byte of
the last form's integer value.  It also exposes =--repl [--no-prompt]=
for line-oriented interactive development against one live evaluator
environment, plus short CLI options:

#+begin_src shell
target/nelisp --help
target/nelisp                         # starts the REPL
target/nelisp --eval '(+ 40 2)'       # prints 42, exits 0
target/nelisp --load /tmp/prog.el     # prints the last value, exits 0
target/nelisp /tmp/prog.el           # exits with the last integer value
#+end_src

Its OS connection is also written on
the Elisp side: opening and reading files, reading stdin, writing
stdout/stderr, exiting, allocating memory, spawning OS threads, and
forking compile workers all flow through Elisp-generated native code
and raw syscall forms.

Fed its own compiler toolchain as source (=nelisp-aot-compiler= +
=nelisp-asm-x86_64= + =nelisp-elf-write= + =nelisp-static-linker=,
~20k lines of Elisp), this binary *self-hosts*: it compiles Elisp
source to a native x86_64 ELF executable, with no Emacs anywhere.  The
following are all CI-gated (=.github/workflows/ci.yml=):

| Make target                              | What it proves                                                                                    |
|------------------------------------------+---------------------------------------------------------------------------------------------------|
| =make standalone-selfhost-test=          | compiles =(seq (defun fact (n) ...) (exit (fact 5)))= → native ELF → run → exit *120* (recursion)  |
| =make standalone-selfhost-mt-test=       | compiles a *multi-threaded* program (=clone(2)= + SeqCst atomics, 3 OS threads) → native ELF → *42* |
| =make standalone-parallel-compile-test=  | compiles *4 units concurrently* — 4 =fork(2)= workers each running the full compiler → 11,22,33,44  |

The incremental standalone eval build also has a multi-process worker entry.
On POSIX use =tools/build-standalone-parallel.sh [NJOBS]=; on native Windows
PowerShell use =.\tools\build-standalone-parallel.ps1 -Jobs 4=.  Both routes
drive =nelisp-standalone-compile-chunk= and then link once serially, using
Emacs and pure elisp only.

** REPL-driven runtime development

For the file rebuild/reload workflow, use
=tools/ai/nelisp-ai.sh repl= and the
[[file:docs/repl-development.md][REPL development guide]]. The lower-level examples below describe the
standalone reader itself; starting that reader alone does not load the
full artifact compilation runtime.

The standalone reader is also the development REPL for NeLisp itself.
The REPL runs in the AOT standalone interpreter and evaluates forms
through the same reader, evaluator, builtin dispatcher, environment, and
GC path used by normal file execution.

That makes the core workflow Lisp-native:

1. Start one standalone NeLisp process.
2. Define or redefine functions in that process.
3. Call them immediately without restarting the runtime.
4. Use =nelisp--eval-source-string= to evaluate generated source into
   the same live environment.

#+begin_src shell
make standalone-reader

target/nelisp
nelisp> (defun hot () 1)
hot
nelisp> (hot)
1
nelisp> (defun hot () 42)
hot
nelisp> (hot)
42
#+end_src

Runtime sources can also be pre-bundled into a replay image.  This is
the portable bootstrap cache used before the native artifact layer:

#+begin_src shell
printf '(defun cached-hot () 42)\n' >/tmp/runtime-src.el
target/nelisp dump-runtime-image /tmp/runtime.nlri --load /tmp/runtime-src.el
target/nelisp eval-runtime-image /tmp/runtime.nlri '(cached-hot)'
#+end_src

For repeated command execution, compile the replay image into a NeLisp
artifact cache.  =.nelc= removes repeated source parsing/replay from
the command path.  The =.neln= native hot path uses the same flattened
runtime-image input in the host/dev native compiler gate; wiring that
compiler into the standalone command path is tracked separately.

When a =.neln= artifact is loaded, native-eligible functions are
registered as ordinary NeLisp functions with a native-first wrapper and
bytecode fallback.  The integer native proof path also caches the linked
driver executable under the user cache directory, so repeated calls do
not pay object extraction and link cost every time.

Generic source loading can use the same artifact layer.  Compile a tree
with =compile-elisp-artifacts --kind neln FILE.el DIR...= to create
adjacent =FILE.el.neln= artifacts; =nelisp-load-file= probes fresh
adjacent =.neln= then =.nelc= before source replay.  If
=nelisp-load-auto-compile-artifacts= is enabled, a missing or stale
adjacent artifact is rebuilt on demand.  =inspect-elisp-artifact= shows
=:native-report= so unsupported native bodies are visible while the
portable fallback remains usable.

#+begin_src shell
target/nelisp compile-runtime-image \
  --kind nelc \
  --input /tmp/runtime.nlri \
  --output /tmp/runtime.nelc

target/nelisp eval-elisp-artifact /tmp/runtime.nelc '(cached-hot)'
#+end_src

For editor integration or scripted probes, use =--no-prompt=:

#+begin_src shell
printf '(defun hot () 7)\n(hot)\n(nelisp--eval-source-string "(defun hot () 9)")\n(hot)\n(exit)\n' \
  | target/nelisp --repl --no-prompt
# => hot
# => 7
# => hot
# => 9
#+end_src

The last example proves both parts of the development surface:
top-level REPL input mutates the live environment, and persistent
source-string evaluation mutates that same environment.

** Two concurrency paths, exposed to interpreted code

Both are built only from existing AOT grammar ops
(=syscall-direct= / =atomic-fetch-add= / raw memory access).

- =(thread-spawn 'FORM)= / =(thread-join ADDR N)= — true multi-threaded
  *eval* via =clone(2)= (CLONE_VM): OS threads sharing one address
  space, each evaluating FORM with its own per-thread context (own
  recursion counter), joined through a shared atomic counter.  The
  shared-memory model (12/12 stable for parallel =eval=).
- =(fork-spawn 'FORM)= — =fork(2)= workers with *COW-isolated* address
  spaces (each its own arena / globals / env), so N workers compiling
  concurrently share no mutable eval state and cannot race.  This is
  the production *parallel build* path (4-way and 5-way verified
  100%).

The standalone arena allocator advances its bump pointer with a SeqCst
=atomic-fetch-add=, so concurrent allocation is thread-safe by
construction.

The same pattern is used for ordinary OS interaction in the standalone
reader: file loading, REPL stdin, stdout/stderr writes, process exit,
thread creation, and worker forking are runtime behaviors driven from
Elisp-generated native code.  The point is not merely that Elisp logic
sits above an OS bridge; the OS bridge itself is now part of the Elisp
runtime surface for the standalone path.

This is the third rung of the self-host ladder, end to end and with no
Emacs: =text → (the standalone interpreter running the AOT
compiler) → native ELF=, scaled to *concurrent multi-unit compilation*.

* Opt-in language extensions

These are the parts of NeLisp that are not "Emacs, again".  Every one of them
follows the same rule (Doc 168 section 2), and it is the rule that makes them
usable at all: *loading one changes nothing about plain Elisp semantics.*
Unannotated code expands and runs exactly as it does in stock Emacs.  You pay
only where you annotate.

** Memory safety, borrowed from Rust — =nl-safe=, =nl-static=, =nl-check=

The ordinary Lisp layer is already memory-safe: it is a garbage-collected
dynamic language.  The danger in this project lives one level down, in the
*runtime implementation layer* -- raw pointers, =syscall-direct=, arenas, mmap
regions -- which is written in Elisp too and has none of Lisp's protections.
=nl-safe= (Doc 170 Stage 1) gives that layer Rust's discipline in three pieces:

1. *Aliasing safety.*  =nl-cell= borrow cells enforce sharing XOR mutation
   with runtime counters -- the =RefCell= strategy: dynamic checks first,
   static ones later.
2. *Memory safety.*  Fat pointers =[nl--ptr BASE LEN GENERATION]= bounds-check
   every access and catch use-after-free through allocation generations.
3. *An unsafe boundary.*  Only =nl-unsafe= blocks may mint a raw pointer, and
   the unsafe surface is a named inventory with a CI ratchet
   (=make unsafe-inventory=) so it cannot grow quietly.

=nl-static= (Doc 197) moves what it can to macroexpansion time -- =nl-total=
for totality, =nl-borrow-scope=/=nl-with-borrow-mut= for statically scoped
borrows, =nl-typed= for argument types -- installing no advice, no compiler
hook, and no reading pass.  Set =nl-static--enabled= to nil and every
annotation emits its plain counterpart with no checking residue at all.
=nl-check= (Doc 170 section 10) adds expansion-time checks across the family:
where =nl-safe= catches a violation when it happens, =nl-check= tries to catch
it before it ships.  =nl-contract= (Doc 170 Stage 4) puts Racket-style
contracts with blame on module boundaries, which is what you want when =eval=
and runtime redefinition mean the perimeter is the only thing you can trust.

** Namespaces — =nl-ns=

Emacs Lisp has one obarray, so =(defun foo ...)= is assignment to a global
name and the second definition silently wins.  =nl-ns= (Doc 169 defect #6)
takes the cheap road deliberately: it does *not* rewrite code and adds
*nothing* at run time.  It reads files and reports where a boundary Elisp
cannot enforce has actually been crossed, with a CI ratchet
(=make ns-inventory=, =make ns-gate=) so the count only moves on purpose.

The bug that motivated it is worth stating, because it is the failure mode a
namespace system is really for: a file in this tree replaced a host definition
with a partial stub whose own docstring admitted it was partial, the stub's
=cl-loop= returned nil in-tree but not in a real Emacs, and three layers of
callers quietly returned nil.  Nothing about that is a name collision between
two files; it is a boundary between this tree and the host being crossed
without anyone noticing.

** Immutability and true parallelism, borrowed from Clojure — =nl-clj=

=nl-clj= (Doc 195) is a persistent-data library: a persistent vector, a
persistent hash-map and hash-set, an =atom=, and a seq API that is both eager
and lazy.  Collections are plain Elisp vectors with a tag symbol in slot 0 --
=nl-cell='s own idiom, deliberately not =cl-defstruct=/=record= -- so they
stay ordinary Lisp values.  The lazy seq leans on =nl-safe='s borrow cell to
get realize-once semantics and to make reentrancy signal loudly instead of
looping; the two libraries compose rather than merely coexisting.

Doc 199 then took the idea past cooperative scheduling.  =nl-clj-future=,
=nl-clj-pcalls= and =nl-clj-pmap= are Tier 1 and run on one thread.  Tiers 2
through 3b run *real* =clone(2)= threads: GC-free workers first, then bounded
allocating tasks, and finally unrestricted allocating Elisp with per-thread
precise roots.  Immutable structures are what make the last tier tractable --
there is nothing to race on when readers cannot mutate.

** The park barrier — how the collector and the threads coexist

The hard part of Tier 3b is not spawning threads, it is collecting garbage
while they run.  NeLisp does not mark concurrently with running mutators and
does not instrument every store.  Instead the collector asks every registered
worker to *park*, marks and sweeps with all mutators stopped, and releases
them.  The tri-colour invariant then holds by construction: a mutator cannot
create a black-to-white edge while nothing is running.

That is a real design consequence, not a simplification -- it is why Doc 152's
planned Stage 6 (a write barrier) was retired rather than implemented.  The
gate proves the barrier actually engages rather than skipping an empty
registry, by asserting =PARK-DIAG parked=3 current=0 missed=0 collections=1=:
a genuine collection with three live workers parked.

** Known limits

Said plainly so expectations are calibrated.  The first item reflects the
current layer split; the rest were measured on the v1.0 tree and have *not
been re-measured* on =main=.  The wider C-equivalence limits are in
[[file:docs/runtime-limitations.md][docs/runtime-limitations.md]] (snapshot 2026-06-24).

- *No windows or frames in the core.*  NeLisp is Layer 1, the language
  runtime.  Display belongs to Layer 3 (=gui/=); markers, overlays and
  text properties belong to the Emacs-semantics packages (=packages/emacs-lib-*=,
  =packages/nelisp-overlay=) per Doc 211, not to the core binary.
- *Worker heaps are not reclaimed per task* (v1.0).  A Tier 3b worker's share
  of the arena comes back at process exit, not at task end.
- *Workers cannot write the shared globals mirror* (v1.0).  Such a write
  signals a catchable =nelisp-worker-mirror-mutation= rather than being
  serialised.  The read path is unrestricted.
- *Sockets were Linux-only at v1.0.*  Doc 194 P6 (Windows) was blocked on
  PE import-table emission; other targets got a catchable
  =nelisp-unsupported-primitive=.
- *Mid-form collection safepoints are =while= backedges only* (v1.0).  A
  long-running workload shaped some other way still has few collection
  opportunities.

* Philosophy (short form)

Emacs Lisp is not philosophically cleaner than Scheme or Common Lisp —
but decades of accumulated, lived-in Elisp is a cultural asset worth
self-hosting /on its own terms/, rather than porting it to someone
else's substrate.

/Esperanto is a constructed language of philosophical elegance, but
English is the international language./ Elisp is English here.

The long form lives in =docs/00-motivation.org=.

* Non-goals

- Scheme rewrite (Guile-Emacs direction) — rejected
- A replacement editor for Emacs — out of scope for NeLisp itself
  (Stage B/C handled by =anvil.el= or successors)
- Replacing /all/ 3000 C functions — non-goal.
  NeLisp core team rewrites AI-critical paths, community fills the long
  tail
