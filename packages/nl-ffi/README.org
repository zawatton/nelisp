#+TITLE: nl-ffi — declarative FFI surface for NeLisp

* Purpose

=nl-ffi= is the declarative layer strategy section 8.1 asks for:
=ffi:library= names a shared library and =ffi:defun= declares a typed Lisp
wrapper around one of its C symbols. It sits entirely on top of the reader
builtin =nl-ffi-call=, which already does the actual call
(=standalone-reader-ffi-smoke= exercises it directly against libc, libm,
SQLite, GnuTLS and FreeType); this package adds named libraries, typed
signatures, argument/result conversion, and named error conditions instead
of a silent nil.

#+begin_src elisp
(require 'nl-ffi)

(ffi:library "libm.so.6")
(ffi:defun nl-ffi-example-sqrt "sqrt" [:double :double]
  "sqrt(3) via nl-ffi-call.")
(nl-ffi-example-sqrt 4.0)
;; => 2.0

(ffi:library "libsqlite3.so.0")
(ffi:defun nl-ffi-example-sqlite-version "sqlite3_libversion" [:pointer]
  "sqlite3_libversion(3) -- SQLite version string (const char*).")
(nl-ffi-get-string (nl-ffi-example-sqlite-version))
;; => "3.45.1" (exact string is whatever libsqlite3 the binary linked)

;; A symbol the build-time table does NOT carry: as of step 2, this
;; really `dlopen's the SONAME and resolves the symbol with `dlsym',
;; rather than requiring a new table row and a reader rebuild.
(ffi:library "libz.so.1")
(ffi:defun nl-ffi-example-zlib-version "zlibVersion" [:pointer]
  "zlibVersion(3) -- not in the build-time table; resolved via dlsym.")
(nl-ffi-get-string (nl-ffi-example-zlib-version))
;; => "1.3.1" (exact string is whatever libz the binary finds at runtime)
#+end_src

This package is step 2 of a 3-step rollout; see "Roadmap" below before
assuming more is possible than this.

* Scope: external-library layer only

FFI here is for the libraries Emacs itself treats as external and
dynamically loads: image decoding, font shaping, TLS, compression, XML,
SQLite, crypto. It is not a path into NeLisp's own core (allocator,
evaluator, display, buffer/text substrate) -- that boundary has no stable
C ABI to call across; see =dev/CLAUDE.md= and this repository's own FFI
policy notes. FFI is not a speed argument either: the call floor is the
interpreter, not the glue (=make standalone-call-floor-bench=).

* Symbol resolution: read this before writing =ffi:library=

There are now two resolution paths, tried in this order for every
=ffi:defun=-generated call. Both end up signalling the same named
conditions instead of a silent nil; which path a given C-SYMBOL uses is
never visible in =ffi:defun='s call shape, only in which SONAME was
declared for it via a preceding =ffi:library=.

** Path 1 (step 1, unchanged): the build-time table

=nl-ffi-call= dispatches through one fixed, build-time table
(=nelisp-standalone--reader-extern-table= in
=scripts/nelisp-standalone-build.el=): rows of ~(SYMBOL SONAME ARITY SIG)~
that drive both the binary's own ELF/PE import list -- resolved *eagerly by
the OS loader when the process starts*, not by anything Lisp calls at
runtime -- and a nested ~if~ chain matching the ~NAME~ argument at the
reader-builtin level. This is *global and flat*: a C symbol is either
already linked into the currently running binary, or this path does not
reach it at all, regardless of which "library" a caller thinks it belongs
to. A name that is not in the table falls through to a default dispatch
arm that writes Lisp ~nil~ -- silently, at the =nl-ffi-call= level. Every
*matched* row, by contrast, always boxes its result as a real Lisp integer
or float, never ~nil~.

** Path 2 (step 2, new): =dlopen=/=dlsym= against a declared library's handle

A raw ~nil~ from path 1 no longer means "unresolved" outright. =ffi:defun=
does not take a library argument and its signature vector never encodes
where C-SYMBOL resolves from -- =nl-ffi--invoke= is the one place that
tries every =dlopen='ed library's handle, in declaration order, via
=dlsym= (=nl-ffi--resolve-via-dlsym=), caching a resolved address keyed by
=(SONAME . C-SYMBOL)=. A resolved address is called through =ptr-call= or =ptr-call-typed=
(=nl-ffi--ptr-call-invoke=), NOT through =nl-ffi-call= -- both are
generic "call this address with up to six arguments" reader primitives,
unrelated to the fixed table; =ptr-call-typed= additionally takes a
run-time signature mask so a =double= argument in position 1-4, or the
return, lands in an XMM register instead of a GP one (see "Type
vocabulary" below for what remains refused: =:float= anywhere, and
=:double= in argument position 5 or 6). Six arguments is a hard cap
either way -- that is =ptr-call='s/=ptr-call-typed='s own limit, not
this package's choice.

=dlopen=/=dlsym=/=dlerror=/=dlclose= are themselves ordinary rows in the
same build-time table (SONAME =libc.so.6=; glibc >= 2.34 keeps them
there, already a =DT_NEEDED= entry via the =toupper=/=tolower= rows -- an
older glibc would need SONAME =libdl.so.2= instead), so path 2 needed no
new build-time mechanism, only four more rows and a Lisp-level resolver
on top of =ptr-call=, which already existed.

** What this means for =ffi:library= and =ffi:defun=

- =ffi:library= takes a SONAME spelled exactly as the table spells it
  (=libm.so.6=, not =libm= or =math=) for a *known* library --
  =nl-ffi-known-sonames= is a hand-maintained mirror of the table's own
  SONAME set. For a known SONAME, nothing changes: no =dlopen= call, a
  =nil= =:handle=, path 1 only. For any OTHER SONAME, =ffi:library= now
  really =dlopen=s it (=RTLD_NOW|RTLD_LOCAL=) and stores a real, non-zero
  handle (read through =nl-ffi-library-handle=) -- path 2's whole reason
  to exist. =nl-ffi-library-open-failed=, carrying =dlerror='s text, is
  signalled when that real =dlopen= attempt fails (for example a SONAME
  naming no real, reachable shared object); the OLD table-membership
  rejection (=nl-ffi-unknown-library=, signalled immediately for anything
  outside the mirror) is no longer signalled by =ffi:library= at all --
  see that condition's docstring in =nl-ffi.el=.
- =ffi:defun= does not take a library argument, and its signature vector
  never encodes where C-SYMBOL resolves from -- unchanged from step 1.
  What changed is what =nl-ffi--invoke= does with a raw table-miss ~nil~:
  it used to mean "unresolved" outright; it now means "try path 2".
- Calling =nl-ffi-call= with the *wrong arity* is unsafe, not merely wrong:
  a matched row reads its Nth argument by walking N ~cdr~s of the actual
  argument list, with no bounds check against what the Lisp call site
  supplied. This is why arity is validated in Lisp, first, before
  =nl-ffi-call= is ever reached -- and why =ffi:library= does not probe an
  arbitrary declared symbol by calling it with synthesized arguments:
  without a real, correctly typed call (only available once an =ffi:defun=
  wrapper is actually invoked), a probe call is either unsafe or
  meaningless. "Do not invent a loader" (the brief for this package) also
  means: do not invent an unsafe one. =ptr-call= itself is exactly as
  unsafe in the same way (it reads six argument slots unconditionally,
  padding is the caller's job) -- =nl-ffi--ptr-call-invoke= checks
  =(length ARG-TYPES)= against that six-argument ceiling before ever
  calling it, signalling =nl-ffi-too-many-arguments= rather than reading
  past the end of the real argument list.

* Dynamic-reader requirement

=nl-ffi-call= exists only in the dynamic reader, built with
=NELISP_READER_DYNAMIC=1= (see =standalone-reader-ffi-smoke= in the
Makefile). The default static reader has =nl-ffi-call= =fboundp= -- it is
never a void function anywhere -- but calling it there signals the
reader's own catchable =nelisp-unsupported-primitive= condition.
=ffi:defun=-generated functions catch that and re-signal
=nl-ffi-unavailable=, the same condition used when =nl-ffi-call= is
entirely absent (host Emacs, or any other build without it). Build the
gate's own reader with:

#+begin_src sh
make ffi-dsl
#+end_src

which builds the dynamic reader exactly as =standalone-reader-ffi-smoke=
does, then loads =packages/nl-ffi/test/nl-ffi-dsl-standalone-smoke.el=.

* Type vocabulary

: :uint8 :uint16 :uint32 :uint64 :sint8 :sint16 :sint32 :sint64
: :float :double :pointer :void

Matches =dev/nelisp-ffi= (itself a fork of Christopher Wellons's
public-domain [[https://github.com/skeeto/elisp-ffi][elisp-ffi]]), including the vector call shape (=[RET
ARG...]=, return type first) and the =ffi-call=/=ffi-get-string=
compatibility aliases below, so existing elisp-ffi/nelisp-ffi call sites
keep working without the C++/libffi subprocess.

Conversions ( =ffi:defun='s job, done once per call, in
=nl-ffi--convert-arg=):

- a fixed-width integer type requires an integer argument and passes it
  through unchanged;
- =:float=/=:double= pass a float through unchanged, and promote an
  integer argument to a float (an implicit C =int -> double= widening,
  not a mask on a real bug);
- =:pointer= accepts an address (an integer), ~nil~ (-> address 0), or a
  Lisp string, copied into a fresh NUL-terminated buffer for the
  duration of the call (never freed -- see =nl-ffi--string-to-cstring=);
- =:void= is only valid as the return type; a =:void= return discards the
  raw result and always yields ~nil~. (=:void= as an argument type is a
  declaration error: =nl-ffi-unknown-type=.)

=:float=/=:double= are valid signature keywords for *any* C-SYMBOL.
Path 1 (a build-time table row with an =f64= SIG class, see
=scripts/nelisp-standalone-build.el=) carries either freely, in any
position. A symbol that resolves via path 2 (=dlsym= + =ptr-call=/
=ptr-call-typed=) can carry a =:double= return, or a =:double= argument
in position 1-4, through =ptr-call-typed= -- a generated sibling of
=ptr-call= that dispatches at run time over an argument/return f64 mask
(=nl-ffi--ptr-call-typed-sig=; see =nelisp-standalone--build-ptr-call-
typed-dispatch= in =scripts/nelisp-standalone-build.el= for how the 32
generated arms work). =:float= anywhere (single precision -- this path
only marshals a C =double=), or =:double= in argument position 5 or 6,
still signals =nl-ffi-dlsym-float-unsupported= instead of a silently
wrong answer -- a size budget on the generated arm count, not an ABI
limit. See "Symbol resolution" above and =nl-ffi--ptr-call-invoke='s
Commentary for what a later increment widening either limit would need.

=nl-ffi-get-string= reads a NUL-terminated C string at an address into a
unibyte Lisp string (nil for a NULL address); =ptr-read-u8=/=alloc-bytes=/
=ptr-write-u8= are the reader's own minimal raw memory primitives this
package builds string marshalling from -- no new ones were needed.

* Errors

=ffi:defun= signals one of six named conditions instead of ever returning
a silent nil (all children of =nl-ffi-error=):

| condition | when |
|---|---|
| =nl-ffi-wrong-arity= | called with the wrong number of arguments |
| =nl-ffi-unknown-type= | the signature vector used a keyword outside the type vocabulary (fires at =ffi:defun= expansion time -- NAME is never defined) |
| =nl-ffi-unresolved-symbol= | the C symbol is not linked into this binary, and no declared library's =dlsym= finds it either |
| =nl-ffi-unavailable= | this build/host has no working =nl-ffi-call= at all |
| =nl-ffi-dlsym-float-unsupported= | (step 2) the signature names =:float= anywhere, or =:double= in argument position 5/6, for a symbol resolved via =dlsym= |
| =nl-ffi-too-many-arguments= | (step 2) more than six arguments for a symbol resolved via =dlsym= + =ptr-call=, which cannot carry more |

=ffi:library= signals =wrong-type-argument= (the standard Emacs
condition, not a new one) when SONAME is not a string, =nl-ffi-unavailable=
for the same reason =ffi:defun= does, and (step 2) =nl-ffi-library-open-failed=
-- carrying SONAME and =dlerror='s text -- when SONAME is outside
=nl-ffi-known-sonames= and the real =dlopen= attempt for it fails. The old
=nl-ffi-unknown-library= (immediate rejection of any SONAME outside the
table mirror, before ever trying to open it) is *no longer signalled* by
=ffi:library= as of step 2 -- such a SONAME is now a real =dlopen=
candidate instead of an outright rejection; the condition is left defined
for any existing caller that still catches it by name. =wrong-type-
argument= also covers an =ffi:defun=-generated call's argument not
fitting its declared type.

* Public API

| name | kind | signature |
|---|---|---|
| =ffi:library= | function | ~(ffi:library SONAME)~ |
| =ffi:defun= | macro | ~(ffi:defun NAME "c_symbol" [RET ARG...] &optional DOC)~ |
| =nl-ffi-get-string= | function | ~(nl-ffi-get-string PTR)~ |
| =nl-ffi-types= | constant | the type keyword vocabulary |
| =nl-ffi-known-sonames= | constant | SONAMEs already in the build-time table -- =ffi:library= skips =dlopen= for these |
| =nl-ffi-known-soname-p= | function | ~(nl-ffi-known-soname-p SONAME)~ |
| =nl-ffi-library-handle= | function | ~(nl-ffi-library-handle SONAME)~ -- nil for a known-table SONAME or one not yet declared; a real, non-zero =dlopen= handle otherwise |
| =ffi-call= | function (alias) | ~(ffi-call LIBRARY SYMBOL SIGNATURE &rest ARGS)~, elisp-ffi/nelisp-ffi compatible |
| =ffi-get-string= | function (alias) | elisp-ffi/nelisp-ffi compatible alias of =nl-ffi-get-string= |

The =ffi-call=/=ffi-get-string= aliases are only installed when nothing
else has already defined them (=unless (fboundp ...)=), so loading this
package after =dev/nelisp-ffi='s own =ffi.el=/=nelisp-ffi.el= does not
clobber a real subprocess-backed implementation; loading it first gives
every existing =(ffi-call nil "cos" [:double :double] 1.2)=-style call
site the in-process path instead.

* Not covered

- Closures/callbacks (a C function calling back into Lisp).
- Struct layout (arguments/results are scalars and pointers; read/write a
  struct's fields yourself with =ptr-read-*=/=ptr-write-*= at known
  offsets, as the existing SQLite/FreeType smokes already do).
- Variadic C functions.
- =:float= (single precision) for a symbol resolved via =dlsym= (path 2
  above), anywhere in its signature -- this path only marshals a C
  =double=. A build-time table row (path 1) is the only way to call a
  =float=-taking function today.
- A =:double= argument in position 5 or 6 for a symbol resolved via
  =dlsym= -- =ptr-call-typed='s generated arm count only covers positions
  1-4 (a size budget, not an ABI limit); see "Roadmap" below for what
  widening either of these two limits would need.
- Path 1's fixed table and path 2's =dlopen=/=dlsym= (steps 1-2) on the
  default static reader -- neither exists there at all (see
  "Dynamic-reader requirement" above). As of step 3 increment 1, this is
  no longer "nothing is callable there": =ffi:library= falls back to a
  pure-elisp ELF loader instead -- see "Roadmap" below for exactly what
  it does and does not cover (a real, integer/pointer-only,
  no-dependencies shared object works; one needing a dependency, TLS, an
  IFUNC, or an initializer is refused with a named condition, not
  crashed or silently wrong).

Making a new integer/pointer, or =double=-in-position-1-4/return, C
symbol callable no longer needs a table row and a reader rebuild --
=ffi:library= + =ffi:defun= reach it directly via =dlopen=/=dlsym= (see
"Symbol resolution" above). A reader rebuild is still needed for: a
=float=, a =double= in argument position 5 or 6, a callback, a struct, or
a variadic call -- none of which either resolution path covers yet.

* Roadmap

This package is step 2 of 3.

** Step 1 (done): the declarative surface over the build-time table

=ffi:library=/=ffi:defun= over the symbols the reader's build-time extern
table already carries. No loader, no new table rows for a new library --
calling a symbol not already in the table signalled
=nl-ffi-unresolved-symbol= outright; the only way to add one was a new
table row and a reader rebuild.

** Step 2 (done): dlopen/dlsym rows on the dynamic reader

=dlopen=, =dlsym=, =dlerror= and =dlclose= are now ordinary rows in
=nelisp-standalone--reader-extern-table= (SONAME =libc.so.6=; confirmed
on this repository's Debian dev host, glibc 2.41, via =nm -D libc.so.6=
listing all four as =T ...@@GLIBC_2.34=, and already a =DT_NEEDED= entry
via the =toupper=/=tolower= rows, so no new shared-library dependency was
added -- an older glibc keeps them in a separate =libdl.so.2= instead,
which this repository's CI/dev hosts do not need). =ffi:library= really
=dlopen=s a SONAME outside =nl-ffi-known-sonames= (=RTLD_NOW|RTLD_LOCAL=)
and stores the handle; =nl-ffi--invoke= falls back to =dlsym= against a
declared library's handle, in declaration order, caching a resolved
address keyed by =(SONAME . C-SYMBOL)=, and calls it through =ptr-call=
instead of going back through =nl-ffi-call='s name-matching dispatch --
see "Symbol resolution" above for the full design, and =nl-ffi.el='s
Commentary/=nl-ffi--ptr-call-invoke='s docstring for the exact checks.

=ptr-call= itself only ever passed/returns integers (its one dispatch
arm, =(:lit "ptr-call")= in =scripts/nelisp-standalone-build.el=, reads
all six arguments with =wf_argval= and boxes the result with
=wf_write_int=, unconditionally -- there is no f64-classed sibling the
way a direct table row's =SIG= plist gives =nl-ffi-call= itself,
=:args=/=:ret= =f64=), and stays that way: its argument classes are
fixed at BUILD time, while a =dlsym='d address's signature is only known
at RUN time. =ptr-call-typed= is the sibling that closes most of this
gap -- a generated dispatch (=nelisp-standalone--build-ptr-call-typed-
dispatch=) branching at run time over an argument/return f64 mask, one
statically-classed =extern-call-ptr=/=extern-call-ptr-f64= call per mask
value (see "Symbol resolution" and "Type vocabulary" above). A signature
naming =:float= anywhere, or =:double= in argument position 5 or 6,
still signals =nl-ffi-dlsym-float-unsupported= instead of a silently
wrong answer -- a size budget on the generated arm count (32 arms: 4
f64-capable positions x 2 return classes), not an ABI limit -- and
integer/pointer-only foreign functions (most of libc) are unaffected.

Errors surface differently from the fixed-table path, since =dlopen=/
=dlsym= are matched rows themselves: a real call to either always returns
a real integer, including *0* for "failed" (a C NULL pointer) -- nil
cannot mean failure here the way it does for an unmatched table NAME.
=nl-ffi--resolve-via-dlsym= reads a genuine dlopen/dlsym failure as
"result is 0" (its own returned sentinel when nothing resolves), and
=nl-ffi--dlopen=/=nl-ffi--dlerror-text= fetch the message with a
follow-up call to =dlerror()= -- a different check from, and not a
replacement for, the =null result= sentinel =nl-ffi--invoke= still uses
for the fixed-table path.

** Step 2 addendum (done): an f64-capable =ptr-call-typed=

Lifts step 2's integer/pointer-only limit for the common shapes.
=ptr-call= itself is unchanged (its argument classes are fixed at BUILD
time; a =dlsym='d signature is only known at RUN time, so there is no way
to tell a single static call site "this argument goes in XMM"). The new
builtin, =ptr-call-typed=, resolves this the way =nelisp-standalone--
build-ffi-dispatch= resolves a run-time NAME: branch at run time over an
enumerated code, with each branch a statically-classed =extern-call-ptr=/
=extern-call-ptr-f64= call (Doc 122 §122.D) --

: (ptr-call-typed ADDR SIG a1 a2 a3 a4 a5 a6)

SIG is a small integer: bit N (0<=N<=3) marks argument a(N+1) as f64, bit
4 marks an f64 return -- 16 argument masks x 2 return classes, generated
as 32 dispatch arms by =nelisp-standalone--build-ptr-call-typed-dispatch=
(scripts/nelisp-standalone-build.el), the same =dotimes=-generated
pattern as =--build-ffi-dispatch= rather than 32 hand-written arms.
=nl-ffi--ptr-call-typed-sig= computes SIG from an =ffi:defun= signature's
=ARG-TYPES=/=RET-TYPE=; an out-of-range SIG (not 0..31) is never
constructed and, in the generated dispatch itself, writes nil and
returns 0 -- the same shape an unmatched =nl-ffi-call= name takes.

Two shapes stay refused, both signalling =nl-ffi-dlsym-float-unsupported=
with the offending type and position in the condition data: =:float=
(single precision) anywhere -- this path only marshals a C =double= --
and =:double= in argument position 5 or 6, past the four positions
=ptr-call-typed= classes. Both are a size budget on the generated arm
count (widening past 4 positions doubles the arm count per extra
position), not an ABI limit; a real ABI places a =double= in position 5/6
exactly as it would in position 1-4.

An alternative considered and rejected for this increment: a single
run-time trampoline (mmap an RWX page, write a stub that loads XMM0-7 and
the integer argument registers from a buffer, =call=, store both the
integer and XMM0 results back -- =nl_neln_demo_exec= in
scripts/nelisp-standalone-build.el already writes and calls code pages
this way) would handle every signature at O(1) binary cost. Rejected here
because it is hand-written x86_64 machine code needing a separate path
for Windows and aarch64, where the generated arms simply work; it remains
the option that buys the remaining signature shapes (position 5/6,
=:float=) if the enumeration ever needs to grow.

** Step 3 increment 1 (done): a pure-elisp ELF loader, static reader only

=packages/nl-ffi/src/nl-ffi-loader.el= closes the gap step 1/2 left open:
the default, STATICALLY linked reader has neither =nl-ffi-call= nor
=dlopen=/=dlsym= (both dynamic-reader-only, see "Dynamic-reader
requirement" above), so =ffi:library= there used to signal
=nl-ffi-unavailable= for any SONAME outside the build-time table's own
mirror, no matter what. It now instead maps and relocates the shared
object itself, entirely with primitives the STATIC reader already has
unconditionally -- =syscall-direct= (openat/fstat/mmap/mprotect/munmap/
close), =ptr-read-u8=/=ptr-write-u8=/=ptr-read-u32=/=ptr-write-u32=/
=ptr-read-u64=/=ptr-write-u64=, =alloc-bytes=, and =ptr-call= -- so no
reader rebuild and no opt-in build flag; =ffi:defun='s call shape and
error contract are unchanged. =dev/nelisp-ffi/nelisp-ffi-pure.el= and
=dev/nelisp-ffi/spike-loader-full.el= (a separate repository) were this
increment's starting design, not its code: the pure spike flat-mapped a
whole =.so= at one protection with no relocations at all (leaf functions
only), and the segment-loader spike mapped each =PT_LOAD= at its own
vaddr but into one shared RWX region, also with no relocations.

What increment 1 actually does:
- Maps each =PT_LOAD= with its own =mmap=, at its own address, with its
  own FINAL protection (via =mprotect=, applied only after every
  relocation runs -- never leaving a read-execute segment writable at
  relocation time) -- not one flat region. Reserves the object's whole
  span with one =PROT_NONE= anonymous =mmap= first so every segment lands
  at a consistent bias; an anonymous =mmap='s own zero-fill is =.bss=
  zeroing, so no separate zeroing pass is needed. Refuses (rather than
  mis-protects) an object whose =PT_LOAD= ranges share a page --
  measured empirically absent from this repository's own toolchain
  output (binutils 2.45, =-z separate-code= default).
- Applies =R_X86_64_RELATIVE= relocations unconditionally, and
  =R_X86_64_GLOB_DAT=/=R_X86_64_JUMP_SLOT= when the referenced =.dynsym=
  entry is DEFINED in the same object (=st_shndx <> SHN_UNDEF=) --
  eagerly, at load time (there is no lazy-PLT trampoline here). Refuses,
  naming the relocation type and (when the relocation carries one) the
  symbol: an undefined symbol (needs a dependency this loader does not
  load), =R_X86_64_IRELATIVE= (IFUNC), any TLS-classed relocation type,
  and every other numeric type (=R_X86_64_64=, =R_X86_64_PC32=,
  =R_X86_64_COPY=, ...). A =PT_TLS= program header, =DT_NEEDED=, and
  =DT_INIT=/=DT_INIT_ARRAY= are each checked directly and refused before
  a single relocation is even inspected.
- Resolves a symbol by name through =.dynsym=, preferring =.gnu.hash=
  (the only style this repository's own toolchain emits), falling back
  to the classic SysV =.hash=, then to a linear =.dynsym= scan (a
  fragile last resort, since nothing guarantees =.dynstr= immediately
  follows =.dynsym= -- documented as such, never the primary path).
  Returns 0 -- the same "not found" sentinel a real =dlsym= would give,
  not =nil= -- when nothing matches.
- Wires behind the existing surface with no change to =ffi:defun='s
  shape: =ffi:library= tries the real =dlopen= path first and falls back
  to this loader only when that signals =nl-ffi-unavailable= (the static
  reader); =nl-ffi--resolve-via-dlsym= dispatches a loader handle to
  =nl-ffi-loader-symbol= instead of =dlsym=.

Out of scope for increment 1 (dependency loading, IFUNC, and
initializers were lifted in increment 2, below; TLS and the rest stayed
out -- see increment 2's own "Out of scope" list), each refusing with a
named =nl-ffi-loader-unsupported= condition rather than half-working:
dependency loading (=DT_NEEDED=), symbol interposition across multiple
loaded objects, TLS, IFUNC, initializers, unloading (a loaded object's
mappings live for the rest of the process), the compact =DT_RELR=
relative-relocation encoding some newer linker defaults can emit, and
=PT_GNU_RELRO= re-protection. Everything =ptr-call= itself cannot
express (a float argument/return, more than six arguments) is unchanged
from step 2 -- still =nl-ffi-dlsym-float-unsupported=/=nl-ffi-too-many-
arguments=, not duplicated in the loader.

** Step 3 increment 2 (done): dependencies (DT_NEEDED), initializers, IFUNC

=nl-ffi-loader-open= now discovers and maps a shared object's WHOLE
dependency graph (breadth-first over =DT_NEEDED=, deduplicated by
resolved path), runs every object's relocations (see "Symbol search
order" below) then final segment protection then =R_X86_64_IRELATIVE=
(IFUNC) resolution, then runs =DT_INIT=/=DT_INIT_ARRAY= initializers in
dependency-first order across the whole graph -- a dependency's own
initializers always run before its dependent's. None of this changes
=ffi:library='s or =ffi:defun='s call shape.

*The libc / second-copy question.* Before writing any of this, the real
question was whether mapping a dependency graph this way is safe at
all, given a normal process already has its own libc loaded by the real
dynamic linker.  It does not for THIS loader: `make standalone-reader`'s
own output (confirmed with `file`/`readelf -d`/`readelf -l`/`ldd` on
this repository's dev host) is a genuinely freestanding static ELF --
no `PT_DYNAMIC`, no `PT_INTERP`, no libc of any kind, produced entirely
by this repository's own pure-elisp AOT compiler and static linker, and
this loader only ever runs as `ffi:library`'s fallback on exactly that
reader.  There is no first copy of libc in this process, so there is no
second copy either.  That does not make initializing an arbitrary
runtime from cold safe in general, and the increment 1 PT_TLS refusal
(kept, unchanged, and checked on every node in the graph, not just the
one a caller names) is what bounds it in practice: verified against this
host's real system libraries, a dependency chain that reaches libc.so.6
is refused several hops down at its own PT_TLS, having never mapped a
byte of it read-write or run any of its code.  See
=nl-ffi-loader.el='s Commentary ("THE LIBC / SECOND-COPY QUESTION") for
the full reasoning and =target/ai/ffi-loader-inc2-report.md= (generated
per run, not committed) for the measurements it rests on.

*SONAME resolution.* A =DT_NEEDED= name containing "/" is used
literally; otherwise the requesting object's own =DT_RUNPATH= (preferred)
or =DT_RPATH=, then =LD_LIBRARY_PATH=, then a fixed standard-directory
list (=/usr/lib/x86_64-linux-gnu/=, =/lib/x86_64-linux-gnu/=,
=/usr/lib/=, =/lib/=) are searched, in that order, for the first
openable file named SONAME. No =$ORIGIN=/=$LIB=/=$PLATFORM= token
expansion, and no =/etc/ld.so.cache= parsing (deliberately -- see the
Commentary for why). An unresolvable =DT_NEEDED= name refuses
(=:dependency-not-found=), never silently skipped.

*Symbol search order.* A relocation's own local =.dynsym= entry, when
DEFINED, is always used directly (unchanged from increment 1 -- no name
search at all). When UNDEFINED, the name is searched across the WHOLE
graph in breadth-first discovery order (the object =nl-ffi-loader-open=
was called with, then each dependency the first time it is discovered);
the first object that defines it wins. =nl-ffi-loader-symbol-object=
reports which object in a handle's graph actually answers a given name,
so a caller (or a test) can confirm this directly rather than only
inferring it from a call's result. An undefined, unresolved-anywhere
symbol still refuses (=:undefined-symbol=) -- UNLESS it is =STB_WEAK=,
in which case it resolves to address 0 exactly as a real =ld.so= would
(a real defect found while implementing this: an ordinary =cc -shared
-fPIC= object's CRT-supplied =__cxa_finalize=/=_ITM_*=/=__gmon_start__=
references are exactly this shape, and increment 1's unconditional
refusal would have wrongly rejected them the moment =:has-initializers=
stopped pre-empting it).

*IFUNC.* =R_X86_64_IRELATIVE='s addend is the resolver FUNCTION's
address; this loader calls it (via =ptr-call=, six zero argument slots)
and writes the result. Confirmed empirically that only a HIDDEN-
visibility ifunc compiles to a real =R_X86_64_IRELATIVE= in a =-shared
-fPIC= build -- a DEFAULT-visibility one instead compiles to an ordinary
=R_X86_64_JUMP_SLOT=/=R_X86_64_GLOB_DAT= whose =.dynsym= entry merely has
=st_info= TYPE =STT_GNU_IFUNC=, a related but DIFFERENT mechanism this
increment does not implement; such a relocation refuses
(=:ifunc-symbol-via-relocation=) rather than silently using the
resolver's own address as if it were the target. Ordering: every
object's ordinary relocations run first, THEN every object's segments
are protected to their final permissions (a resolver's own code must be
executable before it can be called), THEN every object's
=R_X86_64_IRELATIVE= entries run, in dependency-first order.

*Initializers.* =DT_INIT= (if present) then =DT_INIT_ARRAY= (in array
order), run strictly after every relocation in the WHOLE graph, in
dependency-first order across the graph -- a dependency's initializers
always run before its dependent's.

Out of scope for increment 2, unchanged from increment 1, each still
refusing with a named condition: TLS (=:tls-segment=/=:tls-relocation=;
increment 3, below, lifts the =PT_TLS=-segment part of this for ONE TLS
model -- =:tls-segment= no longer exists as a condition after increment
3), symbol interposition/versioning beyond the one search order above
(two separate =nl-ffi-loader-open= calls never search each other's
graphs), unloading, the compact =DT_RELR= encoding, and =PT_GNU_RELRO=
re-protection. This loader itself never needed an f64-capable =ptr-call=
variant: every call it makes through =ptr-call= (an IFUNC resolver, or a
=DT_INIT=/=DT_INIT_ARRAY= entry) passes all six argument slots as zero,
and every =float=/=double= match in this file's own source is a
substring of =Elf64_= (the ELF64 struct family), not a C =float=/=double=
argument or return anywhere in its own code. =ptr-call-typed= (see
"Symbol resolution" and "Type vocabulary" above) closes the gap that
existed on step 2's =dlsym= path alone, for a =double= return or a
=double= argument in position 1-4; =:float= and argument position 5/6
remain open -- see =nl-ffi--ptr-call-invoke='s Commentary for what
either needs.

** Step 3 increment 3 (done): TLS (Initial-Exec only)

*The thread-pointer question.* Before writing any of this: does the
reader establish =%fs= (x86-64 TLS is =%fs=-relative) today? Measured,
not assumed -- raw =arch_prctl(ARCH_GET_FS)= against a freshly built
=target/nelisp= returns success with the base at 0, and
=arch_prctl(ARCH_GET_GS)= likewise, confirming this freestanding,
libc-less, pthread-less reader never calls =arch_prctl= at all (a fresh
Linux process starts with =FS_BASE= at 0; nothing here changes that). So
a TLS access is meaningless, not merely risky, until this loader builds
its own thread control block (TCB) and establishes =%fs= itself -- there
is no real =ld.so= or libc startup sequence in this process to have done
it already. See =nl-ffi-loader.el='s Commentary, "TLS", for the full
evidence and reasoning.

*The model.* GCC's DEFAULT TLS model for =-fPIC -shared= code is
General-Dynamic (a =__thread= variable compiles to =R_X86_64_DTPMOD64=
plus a call to =__tls_get_addr=, needing a dynamic thread vector this
loader does not implement) -- confirmed with =readelf -r= before writing
any loader code. Compiling with =-ftls-model=initial-exec= instead
produces exactly ONE relocation, =R_X86_64_TPOFF64=: an offset, fixed
once at load time, relative to a thread pointer this loader already
controls completely. That is the ONLY TLS relocation type this increment
implements. General-Dynamic/Local-Dynamic and TPOFF64's GOT-indirect/
32-bit-immediate cousins (=R_X86_64_{GOTTPOFF,TPOFF32,TLSGD,TLSLD,
DTPMOD64,DTPOFF32,DTPOFF64,GOTPC32_TLSDESC,TLSDESC_CALL,TLSDESC}=) stay
refused by name (=:tls-relocation=), unchanged.

*What this actually reaches.* A =PT_TLS= segment is allocated real
storage: a single, process-wide, 1 MiB static arena, reserved lazily on
first need, with =%fs= pointed at its high end and each object's block
packed downward from there (standard Variant-II layout) -- a FIXED
ceiling, never grown, since growing would mean moving =%fs= after code
already compiled against the old offsets exists (=:tls-arena-exhausted=
instead). =:tls-offset= is recorded on the object's own handle data so a
caller can see it. Every OTHER TLS relocation type stays refused by
name, and a =STT_TLS=-typed symbol is refused rather than silently
treated as an ordinary address both via an ordinary GLOB_DAT/JUMP_SLOT
relocation (=:tls-symbol-via-relocation=, mirroring the existing IFUNC-
type check) and via =nl-ffi-loader-symbol= (treated as "not found",
mirroring the existing IFUNC handling there).

*Real system libraries still cannot load.* Re-measured against this
host's real =libc.so.6=/=libm.so.6= (not assumed to still match
increment 2's finding): =libc.so.6= itself uses ONLY =R_X86_64_TPOFF64=
internally (16 occurrences, zero General-Dynamic) -- so TLS by itself no
longer stops it. But widening what this loader reaches exposed a real
gap in the EXISTING =DT_RELR= refusal: it matched only the pre-
standardization experimental tag range, not the standardized tag values
(binutils >= 2.38 / glibc >= 2.36) this host's real toolchain actually
emits, so it was silently not firing against modern system libraries.
Fixed (still a pure tag-presence refusal -- no =.relr.dyn= bytes are ever
read or applied). With the fix, =nl-ffi-loader-fixture-needs-dep.so='s
real =DT_NEEDED= on =libm.so.6= now refuses ONE hop down, at =libm.so.6=
itself (=DT_RELR= present there), never reaching =libc.so.6= or its TLS
at all. Real system libraries remain unreachable through this loader,
exactly as after increment 2, but the specific reason changed and had to
be re-verified rather than assumed to still hold -- see
=nl-ffi-loader.el='s Commentary, "TLS", "THE REAL-SYSTEM-LIBRARY
REACHABILITY QUESTION", for the full evidence.

=DT_RELR= decoding (beyond the tag-presence refusal above),
=PT_GNU_RELRO= re-protection, symbol versioning/interposition beyond the
one search order above, and =nl-ffi-loader-close= (unloading) remain out
of scope, each independent, smaller pieces than TLS was.
