#+TITLE: nl-ffi — declarative FFI surface for NeLisp

* Purpose

=nl-ffi= is the declarative layer strategy section 8.1 asks for:
=ffi:library= names a shared library and =ffi:defun= declares a typed Lisp
wrapper around one of its C symbols. It sits entirely on top of the reader
builtin =nl-ffi-call=, which already does the actual call
(=standalone-reader-ffi-smoke= exercises it directly against libc, libm,
SQLite, GnuTLS and FreeType); this package adds named libraries, typed
signatures, argument/result conversion, and named error conditions instead
of a silent nil.

#+begin_src elisp
(require 'nl-ffi)

(ffi:library "libm.so.6")
(ffi:defun nl-ffi-example-sqrt "sqrt" [:double :double]
  "sqrt(3) via nl-ffi-call.")
(nl-ffi-example-sqrt 4.0)
;; => 2.0

(ffi:library "libsqlite3.so.0")
(ffi:defun nl-ffi-example-sqlite-version "sqlite3_libversion" [:pointer]
  "sqlite3_libversion(3) -- SQLite version string (const char*).")
(nl-ffi-get-string (nl-ffi-example-sqlite-version))
;; => "3.45.1" (exact string is whatever libsqlite3 the binary linked)
#+end_src

This package is step 1 of a 3-step rollout; see "Roadmap" below before
assuming more is possible than this.

* Scope: external-library layer only

FFI here is for the libraries Emacs itself treats as external and
dynamically loads: image decoding, font shaping, TLS, compression, XML,
SQLite, crypto. It is not a path into NeLisp's own core (allocator,
evaluator, display, buffer/text substrate) -- that boundary has no stable
C ABI to call across; see =dev/CLAUDE.md= and this repository's own FFI
policy notes. FFI is not a speed argument either: the call floor is the
interpreter, not the glue (=make standalone-call-floor-bench=).

* Symbol resolution: read this before writing =ffi:library=

=nl-ffi-call= is *not* a =dlopen=/=dlsym= loader. It dispatches through one
fixed, build-time table
(=nelisp-standalone--reader-extern-table= in
=scripts/nelisp-standalone-build.el=): rows of ~(SYMBOL SONAME ARITY SIG)~
that drive both the binary's own ELF/PE import list -- resolved *eagerly by
the OS loader when the process starts*, not by anything Lisp calls at
runtime -- and a nested ~if~ chain matching the ~NAME~ argument at the
reader-builtin level.

Resolution is therefore *global and flat*: a C symbol is either already
linked into the currently running binary, or it is not reachable at all,
regardless of which "library" a caller thinks it belongs to. There is no
per-library handle. Consequently:

- =ffi:library= cannot open a new library. It takes a SONAME spelled
  exactly as the table spells it (=libm.so.6=, not =libm= or =math=),
  validates it against =nl-ffi-known-sonames= -- a hand-maintained mirror
  of the table's own SONAME set, checked immediately, unlike per-symbol
  resolution -- and confirms =nl-ffi-call= exists at all; it does not,
  and cannot, make any new C symbol callable. Its registry entry already
  has a =:handle= slot (always nil today, read through
  =nl-ffi-library-handle=) so step 2 below can fill one in without
  changing what =ffi:library= returns or how callers use it. See its
  docstring for the full reasoning.
- =ffi:defun= does not take a library argument, and its signature vector
  never encodes where C-SYMBOL resolves from. A symbol resolves, or does
  not, purely by whether the running binary's build already imported it
  -- adding rows to the extern table (and rebuilding the reader) is the
  only way to add a new symbol today; see "Roadmap" below for what steps
  2 and 3 change (not this call shape).
- A name that is not in the table falls through to a default dispatch arm
  that writes Lisp ~nil~ -- silently, at the =nl-ffi-call= level. Every
  *matched* row, by contrast, always boxes its result as a real Lisp
  integer or float, never ~nil~. =ffi:defun=/=ffi-call= turn that ~nil~
  into the named condition =nl-ffi-unresolved-symbol= instead of passing it
  through.
- Calling =nl-ffi-call= with the *wrong arity* is unsafe, not merely wrong:
  a matched row reads its Nth argument by walking N ~cdr~s of the actual
  argument list, with no bounds check against what the Lisp call site
  supplied. This is why arity is validated in Lisp, first, before
  =nl-ffi-call= is ever reached -- and why =ffi:library= does not probe an
  arbitrary declared symbol by calling it with synthesized arguments:
  without a real, correctly typed call (only available once an =ffi:defun=
  wrapper is actually invoked), a probe call is either unsafe or
  meaningless. "Do not invent a loader" (the brief for this package) also
  means: do not invent an unsafe one.

* Dynamic-reader requirement

=nl-ffi-call= exists only in the dynamic reader, built with
=NELISP_READER_DYNAMIC=1= (see =standalone-reader-ffi-smoke= in the
Makefile). The default static reader has =nl-ffi-call= =fboundp= -- it is
never a void function anywhere -- but calling it there signals the
reader's own catchable =nelisp-unsupported-primitive= condition.
=ffi:defun=-generated functions catch that and re-signal
=nl-ffi-unavailable=, the same condition used when =nl-ffi-call= is
entirely absent (host Emacs, or any other build without it). Build the
gate's own reader with:

#+begin_src sh
make ffi-dsl
#+end_src

which builds the dynamic reader exactly as =standalone-reader-ffi-smoke=
does, then loads =packages/nl-ffi/test/nl-ffi-dsl-standalone-smoke.el=.

* Type vocabulary

: :uint8 :uint16 :uint32 :uint64 :sint8 :sint16 :sint32 :sint64
: :float :double :pointer :void

Matches =dev/nelisp-ffi= (itself a fork of Christopher Wellons's
public-domain [[https://github.com/skeeto/elisp-ffi][elisp-ffi]]), including the vector call shape (=[RET
ARG...]=, return type first) and the =ffi-call=/=ffi-get-string=
compatibility aliases below, so existing elisp-ffi/nelisp-ffi call sites
keep working without the C++/libffi subprocess.

Conversions ( =ffi:defun='s job, done once per call, in
=nl-ffi--convert-arg=):

- a fixed-width integer type requires an integer argument and passes it
  through unchanged;
- =:float=/=:double= pass a float through unchanged, and promote an
  integer argument to a float (an implicit C =int -> double= widening,
  not a mask on a real bug);
- =:pointer= accepts an address (an integer), ~nil~ (-> address 0), or a
  Lisp string, copied into a fresh NUL-terminated buffer for the
  duration of the call (never freed -- see =nl-ffi--string-to-cstring=);
- =:void= is only valid as the return type; a =:void= return discards the
  raw result and always yields ~nil~. (=:void= as an argument type is a
  declaration error: =nl-ffi-unknown-type=.)

=nl-ffi-get-string= reads a NUL-terminated C string at an address into a
unibyte Lisp string (nil for a NULL address); =ptr-read-u8=/=alloc-bytes=/
=ptr-write-u8= are the reader's own minimal raw memory primitives this
package builds string marshalling from -- no new ones were needed.

* Errors

=ffi:defun= signals one of four named conditions instead of ever returning
a silent nil (all children of =nl-ffi-error=):

| condition | when |
|---|---|
| =nl-ffi-wrong-arity= | called with the wrong number of arguments |
| =nl-ffi-unknown-type= | the signature vector used a keyword outside the type vocabulary (fires at =ffi:defun= expansion time -- NAME is never defined) |
| =nl-ffi-unresolved-symbol= | the C symbol is not linked into this binary |
| =nl-ffi-unavailable= | this build/host has no working =nl-ffi-call= at all |

=ffi:library= signals =nl-ffi-unknown-library= for a SONAME outside
=nl-ffi-known-sonames= (checked immediately, unlike per-symbol
resolution -- see "Symbol resolution" above) and =nl-ffi-unavailable=
for the same reason =ffi:defun= does. =wrong-type-argument= (the
standard Emacs condition, not a new one) covers an argument that does
not fit its declared type.

* Public API

| name | kind | signature |
|---|---|---|
| =ffi:library= | function | ~(ffi:library SONAME)~ |
| =ffi:defun= | macro | ~(ffi:defun NAME "c_symbol" [RET ARG...] &optional DOC)~ |
| =nl-ffi-get-string= | function | ~(nl-ffi-get-string PTR)~ |
| =nl-ffi-types= | constant | the type keyword vocabulary |
| =nl-ffi-known-sonames= | constant | SONAMEs =ffi:library= accepts today |
| =nl-ffi-known-soname-p= | function | ~(nl-ffi-known-soname-p SONAME)~ |
| =nl-ffi-library-handle= | function | ~(nl-ffi-library-handle SONAME)~, always nil today |
| =ffi-call= | function (alias) | ~(ffi-call LIBRARY SYMBOL SIGNATURE &rest ARGS)~, elisp-ffi/nelisp-ffi compatible |
| =ffi-get-string= | function (alias) | elisp-ffi/nelisp-ffi compatible alias of =nl-ffi-get-string= |

The =ffi-call=/=ffi-get-string= aliases are only installed when nothing
else has already defined them (=unless (fboundp ...)=), so loading this
package after =dev/nelisp-ffi='s own =ffi.el=/=nelisp-ffi.el= does not
clobber a real subprocess-backed implementation; loading it first gives
every existing =(ffi-call nil "cos" [:double :double] 1.2)=-style call
site the in-process path instead.

* Not covered

- Closures/callbacks (a C function calling back into Lisp).
- Struct layout (arguments/results are scalars and pointers; read/write a
  struct's fields yourself with =ptr-read-*=/=ptr-write-*= at known
  offsets, as the existing SQLite/FreeType smokes already do).
- Variadic C functions.
- Anything on the default static reader -- =ffi:defun= wrappers still
  build there, and calling one signals =nl-ffi-unavailable= rather than
  crashing or returning a wrong answer, but no C symbol is callable.
- Making a new C symbol callable: *today, a symbol is callable through
  this package only if it is already a row in
  =nelisp-standalone--reader-extern-table=; adding one means a table row
  and a reader rebuild, not anything this package's Lisp-level forms can
  do* (see "Symbol resolution" above and "Roadmap" below for what
  changes that).

* Roadmap

This package is step 1 of 3. It does not, by itself, grow which C
symbols are callable -- that is what steps 2 and 3 are for. Neither
changes this package's call shapes (=ffi:library='s SONAME argument,
=ffi:defun='s signature vector); both add a resolution path underneath
=nl-ffi--invoke= for =ffi:defun= to reach transparently.

** Step 2 (later): dlopen/dlsym rows on the dynamic reader

Add =dlopen=, =dlsym=, =dlerror= (and =dlclose=) as ordinary rows in
=nelisp-standalone--reader-extern-table=, then call the address
=dlsym= returns through =ptr-call= instead of going back through
=nl-ffi-call='s name-matching dispatch. Concretely:

- *Table rows.* =dlopen(path, flags)= and =dlsym(handle, symbol)= are
  both arity 2, plain i64 (pointers and a flags int); =dlerror()= is
  arity 0, returning a pointer read with =nl-ffi-get-string=; =dlclose
  (handle)= is arity 1. All four are ordinary rows, no new SIG shape
  needed, unlike the f64 point below.
- *Is libdl already linked?* No. Nothing in
  =nelisp-standalone--reader-extern-table= imports =dlopen=/=dlsym= or
  any =libdl= SONAME today (grep confirms zero hits). On glibc >= 2.34
  these symbols live in =libc.so.6= itself, already a DT_NEEDED entry
  (the =toupper=/=tolower= rows use it) -- so on such a target, adding
  the four rows above with SONAME =libc.so.6= needs no new DT_NEEDED at
  all. An older glibc keeps them in =libdl.so.2=, a genuinely new
  import. Either way this is a small, mechanical addition to the same
  table, not a new mechanism.
- *Can =ptr-call= pass or return doubles?* Not today -- only integers.
  Its one dispatch arm (=scripts/nelisp-standalone-build.el=, the
  =(:lit "ptr-call")= entry) reads all six arguments with =wf_argval=
  and boxes the result with =wf_write_int=, unconditionally; there is
  no f64-classed sibling the way =nl-ffi-call='s per-row =SIG= plist
  gives direct table rows (=:args=/=:ret= =f64=). That per-row
  distinction works because the table is closed and known at BUILD
  time, so the compiler picks the marshalling per symbol; a
  =dlsym='d address is only known at RUN time, so =ptr-call= itself
  would need either a new f64-aware variant or a way to tell it, per
  call, which of its argument/return slots are =f64= -- calling a
  double-taking function like =sqrt= through a =dlopen='d handle needs
  this fixed first. Integer/pointer-only foreign functions (most of
  libc) do not.
- *How would errors surface?* Differently from today's nil-sentinel,
  and this is the part most likely to be gotten wrong by extending
  =nl-ffi--invoke= without noticing. Today a *matched* table row always
  boxes a real number, and only an unmatched NAME ever produces nil --
  so nil unambiguously means "not in the table". =dlopen=/=dlsym= are
  matched rows too: a real call to either always returns a real
  integer, including *0* for "failed" (a C NULL pointer). Nil can no
  longer mean failure here; a genuine dlopen/dlsym failure has to be
  read as "result is 0", with the message fetched by a follow-up call
  to =dlerror()= -- a different check from, and not a replacement for,
  the =null result= sentinel =nl-ffi--invoke= already uses for the
  fixed-table path.

** Step 3 (later still): grow the pure-elisp ELF loader

=dev/nelisp-ffi/nelisp-ffi-pure.el= is a real pure-elisp proof of
concept for a path that needs neither =nl-ffi-call= nor =dlopen=: it
maps a =.so= with primitives already in the default STATIC reader
(=syscall-direct=/=ptr-read-u64=/=ptr-call=), walks its =.dynamic=
section to find =.dynsym=/=.dynstr=, and resolves a symbol's address by
a linear string scan. Its own STATUS note says it works only for *leaf*
functions (its self-test calls =add2=/=mul3= in a tiny demo =.so=); a
real library needs relocations (=.rela.dyn=/=.rela.plt=, so a
non-leaf function's internal GOT/PLT references resolve instead of
jumping through an unfilled slot), transitive =DT_NEEDED= dependency
loading, and -- for the doubles most external libraries actually use --
the same f64 gap step 2 has. In short: mapping one segment and reading
=.dynsym= is the easy 10%; making an arbitrary already-compiled shared
object run correctly is a small dynamic linker, not a one-file addition.
Doc 100 (=docs/design/100-phase-47-dynamic-link-elisp.org=) describes
the alternative actually shipped instead of either: eager =GLOB_DAT=
imports resolved by the real OS loader at process start, which is what
=nl-ffi-call='s fixed table (and therefore this whole package) rides on
today.
