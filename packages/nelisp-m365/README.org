#+TITLE: nelisp-m365 Package

* Summary

=nelisp-m365= is a Model Context Protocol server that gives an AI client
read-only access to a *personal* Microsoft account -- a Microsoft 365
Personal or Family subscription, or a plain outlook.com / hotmail /
live.jp account.  It is written entirely in Emacs Lisp and runs on the
NeLisp standalone runtime.

It exists because the hosted Microsoft 365 connector does not accept
these accounts.  Its documented prerequisite is "a work or school
Microsoft account on a Microsoft Entra tenant (personal accounts such as
outlook.com, hotmail.com, or live.com aren't supported)".  This server
authenticates against the =consumers= tenant instead, which is the
single configuration choice that makes it a personal-account connector.

Teams, SharePoint and Planner are absent on purpose: Microsoft Graph
does not expose them for consumer accounts, so no scope grant can reach
them.

* Status

- Package status: active.  33 read tools always; 12 write tools when
  =M365_ENABLE_WRITE= is set
- Transports: stdio, and Streamable HTTP with OAuth 2.1 through
  =bin/nelisp-m365-http= (see /Remote transport/)
- Platforms: Linux bash launcher and native Windows PowerShell launcher.
  Windows is verified offline with the PE runtime (see /Native Windows/).
- The original 43 tools were verified against a live personal Microsoft account.
  The new metadata tool and guarded publication were verified on 2026-10-02.

* Conditional text editing

Read an existing small text/org file with =m365_get_onedrive_text=. Its
=metadata.eTag= is returned only when the version remains stable across the
content download; a concurrent change requires another read. Never edit a
truncated result.

For an existing-file update call =m365_upload_onedrive_file= with =path=,
=itemId= and the exact quoted =expectedETag= from that read. This addresses
the existing item by identity and sends =If-Match= with the upload. A stale
version fails with HTTP 412; do not retry against a new version without
reading and reconciling its content. Read the result back after success.
The returned upload metadata includes the new eTag. Wildcards and malformed
version strings are rejected before upload. The tool count is now 45, including
=m365_get_onedrive_metadata= for body-free version inspection by id or path.

=m365_download_onedrive_snapshot= downloads raw bytes to an owned temporary
file and verifies matching metadata before and after download. Its default
limit is 8 MiB, with an explicit maximum of 64 MiB. The caller consumes and
removes the returned temporary file. The original download tool is unchanged.
=m365_list_onedrive= supports =compact=true= for identity, size, version,
and folder metadata only; paginated listings accept up to 10,000 results.

For an absent destination use =createOnly=true=. This adds the
~@microsoft.graph.conflictBehavior=fail~ query condition. The live consumer
service ignored =If-None-Match=* on the content PUT alone; the query condition
was verified to reject an existing filename without changing its content.
Text reads accept an explicit =maxBytes= budget up to 8 MiB for bounded local
publication; the ordinary client default remains 256 KiB. UTF-8 BOM and CRLF
are preserved for byte comparisons.

Destination-only uploads retain the older unguarded creation/replacement
behavior. Use conditional item updates for org editing. Conditional uploads
protect cloud concurrency only; they do not reconcile a separate local file
or protect against another program publishing an unconditional replacement.

Verified on 2026-10-02 with a disposable org using the registered WSL/NeLisp
launcher: fresh-version update succeeded, a stale update returned 412, and
readback retained the fresh content and the original repeating schedule.
Offline tests cover missing/malformed conditions, header propagation,
precondition errors without fallback, and changes during content download.

** Write tools

Absent unless =M365_ENABLE_WRITE= is set.  Sending mail is outward-facing
and irreversible; a tool that can do it should not be sitting in the
registry of a session that only meant to read.  The same switch widens
the OAuth scopes, so the grant and the tool surface stay in step -- turn
it on and the account has to consent again.

| =m365_create_draft=          | compose a draft, attachments optional |
| =m365_create_reply_draft=    | reply draft, Outlook's quoting kept   |
| =m365_send_draft=            | send a draft -- irreversible          |
| =m365_send_mail=             | compose and send in one step          |
| =m365_create_event=          | add a calendar event                  |
| =m365_delete_event=          | remove one -- the only destructive tool |
| =m365_upload_onedrive_file=  | upload a local file, up to 60 MB      |
| =m365_create_todo_task=      | add a To Do task                      |
| =m365_delete_mail=           | to Deleted Items, or purge            |
| =m365_delete_onedrive_item=  | to the OneDrive recycle bin           |
| =m365_complete_todo_task=    | mark a task done                      |
| =m365_delete_todo_task=      | remove a task -- no recycle bin       |

Composing is split from sending deliberately: a draft can be read back
and corrected, a sent message cannot be recalled.  The descriptions say
so, and =m365_send_mail= points at the two-step path.

Nothing purges by default.  Mail is *moved* to Deleted Items rather than
DELETEd, because the two do not land in the same place: measured on a
personal account, =DELETE /me/messages/{id}= puts the message in
Recoverable Items -- Outlook's "Recover items deleted from this folder",
a screen most people never open -- and it never appears in Deleted Items
at all.  =permanent= selects the DELETE path and says where the message
went.  A OneDrive item goes to the recycle bin.  Only To Do is
unrecoverable, which its tool reports as =recoverable: false=.

Attachments are encoded by the OS rather than in Lisp, and OneDrive
uploads are streamed by curl, so file bytes never pass through the
runtime -- every string there is UTF-8, and a binary file would not
survive the trip.  Verified by attaching 1046 bytes covering every byte
value 0-255, sending it, downloading it back and comparing SHA-256.

* Microsoft Entra setup

One-time, in the Microsoft Entra admin centre:

1. Register an application.
2. Supported account types: /Personal Microsoft accounts only/, or
   /Any organizational directory and personal Microsoft accounts/.
3. Under Authentication, enable /Allow public client flows/.  The
   device-code grant requires it.
4. Copy the Application (client) ID.

Delegated permissions do not need to be pre-registered.  The v2.0
endpoint consents dynamically, so the scope list in
=nelisp-m365-scopes= can grow without touching the portal; the next
sign-in simply shows a fresh consent screen.

Default scopes, all read-only apart from the refresh-token grant:

#+begin_src text
offline_access User.Read Mail.Read Calendars.Read
Files.Read Contacts.Read Tasks.Read Notes.Read
#+end_src

=Files.Read= turned out to be enough for the Excel workbook endpoints
and for =sharedWithMe=, both of which the documentation suggests might
need more.

The tenant must be =consumers=.  A refresh token issued through the
=common= authority is rejected at its first refresh, so a session
authenticated that way dies about an hour after sign-in.

* Configuration

The launcher reads =$XDG_CONFIG_HOME/nelisp-m365/config.sh=
(default =~/.config/nelisp-m365/config.sh=).  Environment variables
already set for the launcher take precedence.

#+begin_src sh
M365_CLIENT_ID=00000000-0000-0000-0000-000000000000
M365_TENANT=consumers
M365_TOKEN_CACHE="$HOME/.local/state/nelisp-m365/token.json"
M365_DOWNLOAD_DIR="$HOME/.local/state/nelisp-m365/downloads"
M365_LOG_FILE="$HOME/.local/state/nelisp-m365/mcp.log"
# Uncomment to expose the write tools; re-run m365_authenticate after.
# M365_ENABLE_WRITE=1
#+end_src

=NELISP= overrides the runtime binary, which defaults to
=<repo>/target/nelisp=.

** Token storage

The token cache is JSON written with mode 0600.  It holds a refresh
token in the clear: anyone who can read the file can read the account
until the token is revoked.  There is no OS keychain integration --
=@azure/msal-node-extensions= wraps DPAPI through a native addon, and
this runtime has no FFI.  Revoke at
https://account.live.com/consent/Manage if the file is exposed.

** Downloads

=m365_save_mail_attachment= and =m365_download_onedrive_file= write into
=M365_DOWNLOAD_DIR= and nowhere else.  File names arrive from whoever
sent the mail or shared the file, so path separators, drive letters and
leading dots are stripped before the name is used.

** Codex

Point an MCP server entry at =bin/nelisp-m365-mcp=; it speaks plain

** Native Windows

No WSL or bash is needed. Use Windows PowerShell 5.1, a Windows NeLisp
standalone executable, and the system =curl.exe=. From the repository root:

#+begin_src powershell
claude mcp add --scope user --transport stdio m365-personal-nelisp -- powershell.exe -NoProfile -NonInteractive -ExecutionPolicy Bypass -File "$PWD\packages\nelisp-m365\bin\nelisp-m365-mcp.ps1"
#+end_src

The default runtime is =../nelisp/target/nelisp.exe= relative to this
repository. Set =NELISP= in config or the MCP command's environment to
select another build. The launcher never invokes a shell for curl: the
runtime passes individual arguments to the Windows subprocess API.

Create =%APPDATA%\nelisp-m365\config= as UTF-8 plain text. It is a simple
=KEY=value= file, not a PowerShell script. Blank lines and lines starting
with =#= are ignored. Values are literal, trimmed, and unquoted; spaces,
backslashes and additional equals signs are allowed. Environment values
override config values; =M365_CONFIG_FILE= selects a different config.
Unknown keys and malformed lines fail startup. Example:

#+begin_src conf
M365_CLIENT_ID=your-public-client-application-id
# Optional; enables write tools and their delegated scopes:
M365_ENABLE_WRITE=1
# Optional runtime override; use your own absolute path:
# NELISP=C:\path with spaces\nelisp.exe
#+end_src

The supported keys are =NELISP=, =M365_CLIENT_ID=, =M365_TENANT=,
=M365_TOKEN_CACHE=, =M365_SCOPES=, =M365_DOWNLOAD_DIR=,
=M365_ENABLE_WRITE=, =M365_LOG_FILE= and =M365_CURL=. Tenant defaults to
=consumers=. Only =M365_ENABLE_WRITE=1= enables writes. Read scopes match
the Linux launcher; enabling writes adds its write scopes unless an
explicit =M365_SCOPES= overrides them. Reauthenticate after changing scopes.
Paths may be absolute or relative to the launcher's working directory.

Defaults under =%LOCALAPPDATA%\nelisp-m365\= are =token.json=,
=downloads\= and =mcp.log=. An empty =M365_LOG_FILE== disables diagnostics.
=M365_CURL= defaults to =%SystemRoot%\System32\curl.exe= and can select an
offline test executable. Do not put tokens in the config file.

The launcher gives an existing token cache an NTFS ACL for only the
current Windows user's SID before starting NeLisp. Token and pending-grant
writes replace inherited and explicit permissions using .NET
=FileSecurity= (the equivalent of a current-user-only =icacls= ACL),
before writing secrets; an ACL failure prevents the write. Unix still
uses mode 0600. Use NTFS or another filesystem supporting Windows ACLs.
The cache remains plaintext; this does not use DPAPI or a keychain.

The generated UTF-8 bootstrap and subprocess request/output files live
in a unique directory under =%TEMP%= whose ACL is restricted before
creation. Windows paths are escaped as Lisp literals. The launcher
copies stdin/stdout/stderr as bytes, preserving UTF-8 and LF framing,
closes NeLisp stdin at EOF, and removes the bootstrap directory on normal
exit or a handled failure. NeLisp's raw stdout writer emits MCP frames;
=kill-emacs= prevents the final =--load= return value from polluting stdout.
Forced termination of PowerShell itself can prevent its cleanup handler.

*** Migrating a WSL token cache

Stop the old WSL MCP server first. Copy its existing token JSON from
the configured WSL token-cache path to the Windows =M365_TOKEN_CACHE=
path, without printing its contents. Keep the same client id, tenant and
scopes: the cache JSON format is unchanged. Start the native launcher,
which restricts the copied file's ACL before loading it, then call
=m365_status=. If refresh fails or scopes changed, use
=m365_authenticate= followed by =m365_authenticate_finish=. Remove the
old copy when migration succeeds. No migration reads a token automatically
from WSL; the launcher uses only its configured Windows path.

*** Offline Windows gates

Run from the repository root, passing the desired Windows runtime:

#+begin_src powershell
python packages/nelisp-m365/test/run-windows-tests.py --runtime $env:NELISP --cold-load-sleep-sec 45
#+end_src

Python 3 and Windows PowerShell compile =test/fake-curl.cs= into a private
temporary executable. That fixture has no networking code and rejects
unknown requests. Tests isolate APPDATA, LOCALAPPDATA, config, token,
downloads, log and temp paths; they never load the user's config/cache.
The suite runs all existing package tests plus Windows regressions via
the repository's ERT shim on NeLisp, verifies curl exit 23, and drives
initialize, tools/list, profile and To Do creation through the real
Windows launcher. It checks environment precedence, spaces/apostrophes
in paths, Japanese/emoji/quoted request text, current-user-only token ACLs,
exact UTF-8/LF stdout, and cleanup. No mail or note is sent anywhere.

=--gate unit= or =--gate native= selects one gate for a focused rerun;
the default =all= always runs both. Process timeouts include the cold-load
allowance; timeout cleanup kills only the process tree started by the test.

** Remote transport

=bin/nelisp-m365-http= serves the same 30 tools over the Streamable HTTP
transport.  The runtime has no socket primitives at all --
=make-network-process= and =open-network-stream= are both void -- so the
adapter owns the socket and drives the runtime over the same stdio pipe
the local transport uses.  No tool implementation changes.

It is Python standard library only: no pip install, and nothing to keep
patched beyond the interpreter.

| =POST /mcp=   | JSON-RPC request or notification; answers JSON |
| =DELETE /mcp= | ends the session named by =Mcp-Session-Id=     |
| =GET /mcp=    | 405; this server never initiates a stream      |

One NeLisp child is shared by all sessions, serialised by a lock.  A
child per session would multiply a ~120 MB baseline for no benefit --
the runtime holds no per-session state, only the token cache.  If the
child dies the next call restarts it and returns a JSON-RPC error
instead of taking the adapter down with it.

*** Bearer token, for a tunnel you control

#+begin_src sh
bin/nelisp-m365-http --port 8765 --token "$(openssl rand -base64 32)"
#+end_src

Binds to loopback by default.  =--no-auth= is refused on any other
address.

*** OAuth 2.1, for a claude.ai custom connector

A custom connector expects OAuth 2.1 with PKCE, so =--oauth= serves the
endpoints it discovers:

| =/.well-known/oauth-protected-resource=   | RFC 9728 resource metadata |
| =/.well-known/oauth-authorization-server= | RFC 8414 server metadata   |
| =POST /register=                          | RFC 7591 dynamic registration |
| =GET/POST /authorize=                     | consent, then an auth code |
| =POST /token=                             | code exchange and refresh  |

#+begin_src sh
bin/nelisp-m365-http --host 127.0.0.1 --port 8765 --oauth \
  --base-url https://m365.example.com \
  --passphrase "$(cat ~/.config/nelisp-m365/passphrase)"
#+end_src

Then point a TLS terminator -- Cloudflare Tunnel, Caddy, whatever you
already run -- at that port, and add =https://m365.example.com/mcp= as a
custom connector.  Claude registers itself through DCR, sends you to the
consent page, and you approve with the operator passphrase.

This server has exactly one user by construction, so there is no user
database: the consent page is gated on a single operator passphrase.
=--oauth= refuses to start without =--passphrase= (the page would
otherwise approve anyone who finds the URL) or without =--base-url= (the
metadata and the redirect would name loopback instead of the tunnel).

Only S256 PKCE is accepted; =plain= is refused rather than quietly
downgraded.  A =redirect_uri= that is not registered for the client is
rejected outright and never echoed into a redirect, so the endpoint
cannot be used as an open redirector.  Authorization codes are single
use, and a refresh token is replaced on every use.

Registered clients and tokens are persisted at =--oauth-store= with mode
0600, so restarting the adapter does not silently break an
already-connected client.

*** Exposure

Everything behind this reads a live mailbox.  Do not run it on a public
address without =--token= or =--oauth=, and prefer a tunnel that you can
revoke over opening a port.

* Runtime substrate

The standalone runtime implements a subset of Emacs Lisp.  These gaps
were measured against the 2026-08-19 Linux build and the 2026-08-13
Windows PE build, and they shape the code far more than the Graph API
does.  =nelisp-m365-compat.el= closes each one in a single place.

| Primitive                     | Linux        | Windows PE  |
|-------------------------------+--------------+-------------|
| =make-network-process=        | void         | void        |
| =match-beginning= / =-end=    | nil          | nil         |
| =format-time-string=          | nil          | nil         |
| =float-time=                  | works        | nil         |
| =sit-for=                     | no delay     | no delay    |
| =getenv= / =command-line-args=| nil          | getenv works|
| =load-path=                   | empty        | empty       |
| =file-attributes=             | non-standard | nil always  |
| =set-file-modes=              | works        | errno -38   |
| =write-region=                | byte/char bug| byte/char bug|
| =call-process=                | works        | works       |
| =read-stdin-bytes=            | works        | works       |

Buffers exist only as containers: =with-temp-buffer=, =insert=,
=insert-file-contents= and =buffer-string= work, but =goto-char=,
=point=, =search-forward=, =delete-region=, =re-search-forward=,
=looking-at= and =char-after= are all void, so a buffer cannot be
navigated or edited.  Text processing has to be done on strings.

Three consequences worth restating:

- *No regexp capture groups.*  =match-beginning=, =match-end= and
  =match-data= all return nil, so only the index from =string-match= and
  =string-search= is usable.  Every parser here is built from literal
  search plus =substring=.
- *No environment and no argv.*  Configuration cannot be passed in, so
  =bin/nelisp-m365-mcp= resolves everything and writes a bootstrap file
  containing absolute =load= calls and =setq= forms.
- *=write-region= cannot write non-ASCII.*  The stub compares the number
  of bytes it wrote against the number of characters it was given and
  signals when they differ, so any file containing Japanese fails
  outright -- "wrf returned 305 (expected 227)".  Request bodies are
  therefore escaped to pure ASCII with =\uXXXX= before being written;
  JSON says an escape means exactly the character it names, so the
  server sees the same text.  The ASCII check is a length-versus-bytes
  comparison rather than a scan, so a multi-megabyte base64 attachment
  skips the escaping pass entirely.
- *A broken builtin can be uncatchable.*  A genuinely missing builtin is
  fine -- it signals =void-function=, which =condition-case= catches.
  But a builtin that is declared and broken is not: =nelisp--syscall=
  aborts the form without signalling, and =alloc-bytes= and
  =ptr-read-u64= take SIGSEGV and kill the process outright, even with
  valid arguments.  Nothing here calls those.

The table above records the historical builds, not current capability.
The tested Windows runtime supports file attributes and the clock.
The native launcher supplies a Windows temporary directory, avoiding the
runtime's POSIX =/tmp= default, and pins the platform and curl path rather
than probing Linux paths. See /Native Windows/ for setup and offline gates.

* Allocation

The runtime never collects garbage on its own, and several string
primitives allocate far more than their input size suggests.  Getting
this wrong is not a performance nuisance here -- it is what killed the
server mid-session, at a different tool each run, until the cause was
found.  Measured on the 2026-08-19 Linux build:

| Operation                             | Allocated |
|---------------------------------------+-----------|
| =string-replace= on a 7 KB string      | 376 MB    |
| =downcase= of a 7 KB string            | 163 MB    |
| =string-search= with START, 600 calls  | 89 MB     |
| =substring=, 600 slices of 7 KB        | 158 MB    |
| =nelisp-json-parse-string=, 16 KB      | 2.7 MB    |

Rules that follow, and that any change here has to keep:

- *Never call =string-replace=.*  One call costs more than the entire
  rest of a request.
- *Never build a whole-document copy*, including =downcase=.
- *Never pass START to =string-search=*; it allocates in proportion to
  the remaining haystack, which makes any tag-by-tag walk quadratic.
  Use =nelisp-m365-compat-find=, which searches in bounded slices.
- *Collect after every request.*  =nelisp-m365-mcp-collect-garbage=
  runs =garbage-collect= once the response is on the wire.  It does not
  return pages to the OS -- resident size plateaus rather than dropping
  -- but reclaimed memory is reused, which is the difference between a
  flat 142 MB and a linear climb to 438 MB over five rounds of the same
  work.

JSON parsing, by contrast, is well behaved and scales linearly; it was
suspected early and cleared by measurement.

* JSON encoding rules

=nelisp-json-encode= reads a list as an alist, so =("a" "b")= encodes as
={"a":"b"}= and a list of alists aborts the encoder.  It also rejects
floats outright, reporting them as NaN or infinity.  Three rules follow,
all of which also hold for the host =json-encode=, which keeps the
package dual-target:

- JSON arrays are *vectors*; use =nelisp-m365-compat-json-array=
- JSON booleans are =t= and =:json-false=; a bare nil encodes as null,
  so use =nelisp-m365-compat-json-bool=
- timestamps are *integers*; =nelisp-m365-compat-now= truncates

Parsing is pinned to the same representation, and the host parser's
output is normalised: it spells =:array-type= as =array= rather than
=vector=, and interns object keys as symbols where =nelisp-json= leaves
them as strings.

* Known limitations

- =read-stdin-bytes= is wrapped in =String::from_utf8_lossy=, so a
  request larger than the 64 KiB read chunk can lose a multi-byte
  character at the chunk boundary.  Normal requests are consumed whole.
- =$search= is index-backed, so a message that just arrived or was just
  moved, and a file uploaded moments ago, can be missing from
  =m365_search_mail= and =m365_search_onedrive= while plainly existing.
  Use =m365_list_mail= or =m365_list_onedrive= to answer "is it there?".
- Paging stops at =nelisp-m365-graph-max-pages=; results say so through
  the =truncated= flag rather than implying completeness.
- The Linux launcher still uses =--load= directly, so a stray =nil= reaches
  stdout after the client closes stdin on the historical Linux build.
  Native Windows explicitly exits before the runtime prints that result.
- Thread retrieval sorts on the client: Exchange answers
  =InefficientFilter= when =$orderby= is combined with a
  =conversationId= filter.
