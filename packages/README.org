#+TITLE: NeLisp Packages

* Purpose

The =packages/= tree is the extraction point for optional libraries
that ship alongside the NeLisp core but live outside the core =src/=
directory.  This is the package-split pattern intended for the
post-v1.0 library breakout work.

* Convention

Each package lives at =packages/<name>/= and follows this layout:

#+begin_src text
packages/<name>/
├── README.org
├── src/
│   └── <name>.el
└── test/
    └── <name>-test.el
#+end_src

Rules:

- Keep the library entry file name aligned with the provided feature.
  Example: =src/nelisp-json.el= must continue to =(provide 'nelisp-json)=.
- Keep ERT coverage beside the package in =test/=.
- Keep =packages/<name>/manifest.el= in step with the code:

  #+begin_src elisp
  (:name "nelisp-http"
   :requires ("nelisp-process" "nelisp-state" "nelisp-sys"))
  #+end_src

  =:requires= names packages, not features; host libraries such as
  =cl-lib= are not listed.  Every package has one, and =make pkg-graph=
  fails when a manifest and the code disagree — so adding a cross-package
  =require= means updating the manifest, which is one command:

  #+begin_src sh
  make pkg-manifest-update PKG=<name>
  #+end_src

  =:version= is optional; nothing consumes one yet.  See
  =packages/nelisp-pkg/README.org=.
  =:stability= is also optional; when present it must be one of the
  four labels below (checked by =nelisp-pkg-validate-manifest=, the same
  place that types =:version=) -- see "Stability".
- Claim a namespace prefix and stay inside it.  Elisp has one obarray,
  so a second definition of a name silently wins; =packages/nl-ns/=
  reports definitions outside their file's prefix, references to another
  file's =--= private names, cross-file references with no =require=,
  and host definitions shadowed without an =fboundp= guard.  Check a
  package with =tools/ai/nelisp-ai.sh ns packages/<name>/src/*.el=, and
  the tree with =make ns-inventory= (ratcheted to a baseline, so the
  count may not grow).
- Do not rewrite callers when extracting a package.  Existing
  =(require 'feature)= forms should continue to resolve through the
  build's load-path.
- Package-specific dependency and usage notes live in the package
  =README.org=.

* Promotion criteria

Keep new standalone functionality package-ready even while it still
lives in =lisp/=, =src/=, =scripts/=, or a launcher.  A feature should
move toward =packages/<name>/=, and later a separate repository if that
becomes useful, when it has:

- A stable public =(require 'feature)= entry point.
- Focused ERT or standalone smoke coverage that does not depend on a
  full CLI/tarball run.
- No direct dependency on Anvil command parsing, release packaging, or
  one host OS.
- A small host boundary: file/OS/process access should enter through
  =nelisp-emacs= or another explicit shim.

Reusable runtime substrate belongs below application launchers.  Good
package candidates include array/vector computation, text/XML/JSON
helpers, portable file and OS shims, batch-edit primitives, and other
data-processing libraries.  Anvil/CAD/SVG workflow policy should stay
above that line and call these libraries through narrow APIs.

* Build Integration

The root =Makefile= adds =packages/*/src= and =packages/*/test= to the
Emacs load-path for compile and test targets.  This keeps package
libraries and their tests discoverable without special-case per-package
rules.

* Pilot

=packages/nelisp-json/= is the pilot extraction.  Doc 45 can reference
it as the canonical example for future library moves.

* Stability (§9.2)

A manifest's optional =:stability= key states one promise about future
API changes, so a caller does not have to read source or ask someone to
find out how much a package's shape might still move.  State it
honestly: a brand-new package is not =stable= merely because its tests
pass today.

- =stable= :: the public API (function signatures, error conditions,
  return shapes) is settled.  A breaking change would go through a
  deprecation period, not land in the next commit that happens to touch
  the file.
- =provisional= :: heading toward =stable=.  The shape is believed
  right, but has not yet been exercised by another package or by real
  callers long enough to promise it will not move; a breaking change is
  possible but would be a deliberate, called-out decision, not routine
  churn.
- =experimental= :: actively being explored.  Scope, coverage, or the
  API itself may change significantly as understanding improves; no
  promise of stability is made at all. A reader whose supported subset
  is expected to grow, or a package still finding its own shape,
  belongs here.
- =internal= :: not meant for use outside this repository, or not meant
  for use by other packages even inside it (a checking pass like
  =nl-check=/=nl-ns=, or a package that only exists to support one
  caller).  May change or be removed without the notice a public
  package would get.

A manifest with no =:stability= key makes no promise either way -- most
packages predate this convention and have not been individually
reviewed against it.  Absence is not a fifth label meaning "stable" or
"experimental"; it means "not yet labeled."

First used by =packages/nelisp-uuid/= and =packages/nelisp-log/=
(=provisional=) and =packages/nelisp-toml/= (=experimental=: its
supported TOML subset is deliberately narrow today and expected to
grow -- see that package's README.org).

* The nl-* extension family (Doc 168)

=nl-prelude= / =nl-condition= / =nl-safe= / =nl-contract= /
=nl-check= / =nl-ns= are opt-in LANGUAGE extension libraries
(Doc 168-170), not extractions from the core: they never ship
loaded, and the root Makefile globs both the
=nelisp-*= and =nl-*= name families for compile and test.  Each
follows the same layout as above plus a
=test/<name>-standalone-smoke.el= runner that executes the identical
ERT bodies on =target/nelisp= (which has no ert) through a minimal
shim -- copy that pattern for new nl-* packages.

=nl-check= and =nl-ns= are the exceptions to the dependency rule: they
are checking passes (Doc 170 section 10; Doc 169 defect #6), so they
depend on the feature packages and *nothing depends on them*.  Keep
that arrow one-way; the point is that a checker can always be deleted.
=nl-check= reads one form at a time (must-use, resource linearity,
unsafe calls); =nl-ns= reads a whole file set at once (cross-file name
collisions, stray definitions, private-boundary references).
