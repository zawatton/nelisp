* Addendum (2026-09-05): the `:extra STRING' qualifier is now supported

§2.2 and §3.5 below, as originally SHIPPED, treated `:extra' as just
another rejected qualifier ("anything but none" signals at
`cl-defmethod' macroexpansion time).  That turned out to be a real gap,
not a theoretical one: real Emacs's own =lisp/emacs-lisp/cl-lib.el= (and
=cl-generic.el= itself) define several `:extra'-qualified methods on
`cl-generic-generalizers' at their own top level, guarded by
=(when (fboundp 'cl-generic-define-method) ...)= — harmless under real
Emacs (where that guard is normally false before `cl-generic' has fully
loaded), but this subset's `cl-defmethod'/`cl-defgeneric' are
unconditional, so any consumer whose `(require 'cl-lib)' reaches that
guarded form (e.g. =eat.el='s own `(require 'cl-lib)') hit this subset's
loud qualifier-rejection error at real-init audit time.

`:extra' is now implemented with real Emacs's own semantics, verified
against host Emacs 31.1 this session (not just internally consistent):
several `:extra'-qualified methods can share one specializer, coexisting
rather than one replacing another, chained via `cl-call-next-method' in
definition-recency order (newest first), ending at the plain
\(non-`:extra') primary method if one exists; redefining an `:extra'
method with the SAME string replaces it AT ITS EXISTING LIST POSITION
\(matching real Emacs's own `cl-generic-define-method' comment: "Keep the
ordering; important for methods with :extra qualifiers"), not moving it
to the front and not reordering its siblings.  `:extra' may also combine
with exactly one of `:before'/`:after'/`:around' — real Emacs's own
grammar requires `:extra STRING' to come FIRST when combined with a
combinator (confirmed this session: real Emacs itself rejects the
reverse order, `:around :extra "x"'); this subset now implements the
same before/primary/after/around combination real Emacs's
`cl--generic-standard-method-combination' does, reachable via `:extra'
plus a combinator or via a bare standard qualifier.  A new
`cl-no-primary-method' signal
(real Emacs's own condition name/message) covers the one new edge case
this makes reachable: applicable methods that are entirely
before/after/around, none of them primary.

Landed in both mirror copies (=lisp/nelisp-cl-macros.el= and
=scripts/nelisp-stdlib-prelude.el=, identically, per this doc's own
mirror-consistency convention).  Test coverage: 8 new `ert-deftest' cases
in =test/nelisp-cl-generic-test.el= (several of them parity forms with an
exact real-Emacs-31.1 transcript in their own docstring/commentary,
measured this session), plus a direct standalone-binary probe (`target/
nelisp --eval', both the exact real-world trigger form and a `:extra'
+`:before'/`:after'/`:around' combination) — before/after transcripts for
both the unfixed and fixed binary are in the T50 task's own report. All
22 pre-existing =nelisp-cl-generic-test.el= cases still pass unchanged
\(30/30 total).  This addendum's own claims are not yet covered by a
fresh =#+VERIFIED-BY= entry (that requires the project's own doc-claims
gate migration, out of this task's scope) — read this as a documented,
tested extension pending that formal step, not as a second SHIPPED
declaration superseding the one above.

* Addendum 2 (2026-09-05): the =(head SYMBOL)= specializer is now supported

§2.1's table below, as originally SHIPPED (and still unchanged by
Addendum 1 above), listed "head/list-head specializers" as *no*, citing
"no evidence any real call site needs this."  That evidence arrived: with
Addendum 1's =:extra= support landed, loading the real =eat.el= (the

(cl-defmethod cl-generic-generalizers ((_specializer (head subclass)))

established matters for this consumer.

** Semantics implemented, verified against host Emacs 31.1

Real =cl-generic.el= source read directly
(=cl--generic-head-generalizer=, =cl-generic-generalizers='s own
=:extra "head"= method, both at =lisp/emacs-lisp/cl-generic.el= lines
~1399-1417 in Emacs 31.1) plus five throwaway host-Emacs 31.1 probes this
session, not just internally-consistent assertions:

- =(head VALUE)= matches an argument that is a cons whose =car= is =eql=
  to VALUE (real Emacs's own docstring: "These match if the argument is
  a cons cell whose car is `eql' to VAL.").  VALUE is taken *literally*,
  never evaluated — confirmed by a probe where a lexically-bound variable
  named the same as the head symbol had no effect on which cons matched.
- Generalizer priority is 80 — strictly between =eql= (100) and any
  =cl-typep=-style type match, including =cons=/=list= (10, real Emacs's
  =cl--generic-typeof-generalizer=) — and above the unspecialized
  catch-all (=t=, priority 0).  Confirmed directly, not assumed, by a
  probe generic with methods on a bare (unspecialized) arg, =cons=,
  =(head foo)=, =(head bar)=, and =(eql 42)=, printing which method(s)
  run and in what order for a table of arguments (host Emacs 31.1
  transcript, this session):

  | argument | real Emacs 31.1 call chain (=cl-call-next-method=, most-specific first) |
  |---|---|
  | =42= | =(eql-42 t)= |
  | =(foo 1 2)= | =(head-foo cons list t)= |
  | =(bar)= | =(head-bar cons list t)= |
  | =(baz)= | =(cons list t)= |
  | =5= | =(t)= |
  | ="str"= | =(t)= |
  | =nil= | =(list t)= |

  (=cons= sorting ahead of =list= for a real cons argument, and =nil=
  matching =list= but not =cons=, are real Emacs's own =cl-typep=-lattice
  behaviour on the *type* tier, unrelated to this addendum and unchanged
  by it — this subset's =§2.1a= type tier still has no lattice and still
  treats two different builtin type-names both matching as ambiguous,
  §2.1a below, exactly as before.)
- Two *different* =(head SYMBOL)= specializers can never both apply to
  one call (only one symbol can be =eql= to a given =car=), so unlike the
  builtin-type tier's already-documented ambiguity (two type names both
  matching one value), the =head= tier never signals ambiguous dispatch.
- =eql= still outranks =head= when both apply to the very same object
  (confirmed with a shared, globally-bound cons matched by both an
  =(eql ...)= specializer and a =(head foo)= specializer: =eql='s method
  runs first, chains into =head='s via =cl-call-next-method=); a
  *different* cons with the same =car= symbol, not =eql= to the baked-in
  value, only reaches the =head= method.
- =:extra='s coexistence/chaining/redefinition-keeps-position machinery
  (Addendum 1) applies to =head= specializers exactly as it already does
  to =eql=/type specializers, unmodified — confirmed with the identical
  parity shape Addendum 1 already proved for =eql=/type: primary +
  =:extra "e1"= + =:extra "e2"=, defined in that order, calls
  =(e2 e1 primary)=; redefining ="e1"= afterward keeps its position,
  =(e2 re-e1 primary)=.
- A DELIBERATE divergence, not an oversight: =(head foo bar)= (more than
  one VALUE) macroexpands without error in real Emacs 31.1, which simply
  ignores the trailing token (its own generalizer method only ever reads
  =(cadr specializer)=) — measured this session.  This subset stays
  loud-failure-first (§2.2, §3.5's whole discipline) and signals a loud
  =error= for this shape instead of silently accepting and ignoring it.

** Implementation, reusing Addendum 1's own machinery (no parallel code paths)

Landed as a dispatch specializer *kind* (=:kind 'head=, alongside
=unspecialized=/=type=/=eql=/=subclass=) plumbed through every place the
other kinds already flow, adding nothing structurally new:
=nelisp-cl-generic--parse-specializer= (new =(head VALUE)= clause,
value stored unevaluated, quoted through =cl-defmethod='s expansion
exactly like =:type-name=), =nelisp-cl-generic--same-specializer-p= (one
more field compared, =:head-value=, so redefinition-keeps-position and
=:extra= coexistence fall out for free — no new logic), the dispatch
table (one more static bucket, =:head=, partitioned/newest-first exactly
like =:eql=/=:type=), a new =nelisp-cl-generic--head-matches= (one
=dolist= filtering by =(and (consp value) (eql head-value (car value)))=
— structurally identical to the existing =--eql-matches=, not a new
matching strategy), and =nelisp-cl-generic--applicable-methods='s
=append= chain gaining one more term between the =eql= and *type*
calls, matching the measured priority order (eql > head > subclass > type >
unspecialized).  =cl-call-next-method=/=cl-next-method-p=,
=cl-no-applicable-method=/=cl-no-primary-method=, and the =:extra=
qualifier grammar are all untouched — a =head= method is just another
entry in the same applicable-methods list those already walk.

Landed in both mirror copies (=lisp/nelisp-cl-macros.el= and

* Addendum 3 (2026-09-06, T81): =cl-defgeneric= default-method bodies and OPTIONS-AND-METHODS are now supported

§3.1's original grammar (still accurate for the P0-P3 baseline) allowed
only =(cl-defgeneric NAME ARGLIST [DOCSTRING])= -- any other trailing
form was a loud macroexpansion-time =error= ("default-method body not
supported by this subset"). That turned out to be the consumer's very
next real blocker behind Addendum 2's =(head SYMBOL)= fix: loading the
real =eat.el= now gets past the whole =cl-lib=/EIEIO =:extra=/=head=
chain (Addenda 1-2) and stops on real Emacs's own
=lisp/emacs-lisp/eieio.el=, at its *first* =cl-defgeneric= call:

#+begin_src elisp
(cl-defgeneric eieio-object-name-string (obj)
  "Return a string which is OBJ's name."
  (or (gethash obj eieio--object-names)
      (format "%s-%x" (eieio-object-class obj) (sxhash-eq obj))))
#+end_src

-- a plain default-method BODY, exactly the shape this doc's original
§3.1 rejected. Real GNU =cl-defgeneric='s actual grammar (read directly
from =lisp/emacs-lisp/cl-generic.el= lines 230-320, not guessed) is
=(cl-defgeneric NAME ARGS [DOCSTRING] [OPTIONS-AND-METHODS...] &rest
DEFAULT-BODY)=: OPTIONS-AND-METHODS is any run of forms whose CAR is a
keyword or the symbol =declare=, each consumed left to right; the first
form whose CAR is neither ends that run, and everything remaining
(however many forms) is "assumed to be a default method body". Real
=cl-defgeneric='s own expansion literally lowers every =(:method
...)= form AND the trailing default body to ordinary =(cl-defmethod
NAME ...)= calls, in source order, executed right after the generic
itself is declared -- confirmed by reading =cl-defgeneric='s own
=let*= construction of its expansion, not assumed.

** Semantics, verified against host Emacs 31.1 (not assumed)

Five throwaway probes this session, plus real =lisp/emacs-lisp/cl-
generic.el= source read directly (the exact macro quoted above):

| form | real Emacs 31.1 (this session's probe transcript) |
|---|---|
| default body + specialized struct methods, dispatch order | =(dog animal default)= / =(animal default)= / =(default)= -- the default body is just the LEAST-specific method in the SAME =cl-call-next-method= chain, no separate mechanism |
| =cl-next-method-p= called from inside the default body itself (nothing less specific than it) | =nil= -- =(default-fallback nil)= |
| redefining the generic with a NEW default body | replaces ONLY the default method, in place; a previously-defined specialized method is untouched: =(int default-v1 42)=/=(default-v1 "s")= before, =(int default-v2 42)=/=(default-v2 "s")= after |

The =(declare ...)=/=(:documentation ...)= *content* is accepted but NOT
applied by this subset (no =function-put= for =indent=, no installed
docstring) -- purely editor/byte-compiler metadata with zero cl-generic
dispatch-semantic effect either way, and this subset has never installed
a generic's docstring anywhere (true before this addendum too). Only the
*syntax* is accepted, so a real-world =cl-defgeneric= call carrying one
is not rejected merely for having it -- the same "accept the form,
don't apply the content" choice this doc already made for other purely-
cosmetic real-Emacs constructs. =(:argument-precedence-order ...)= is
accepted and records the named required-argument order; multiple dispatch
positions are compared lexicographically in that order, defaulting to
source order, as in real =cl-generic=.

** Implementation: the default body is an ordinary method, not new machinery

Landed as a single new helper, =nelisp-cl-generic--parse-defgeneric-
methods=, reproducing real =cl-defgeneric='s own left-to-right
OPTIONS-AND-METHODS walk (form for form, not a stricter re-derivation)
and returning a list of method forms in source-definition order:

- Every =(:method QUALIFIERS ARGS BODY...)= form's cdr, verbatim --
  QUALIFIERS/ARGS/BODY flow through =cl-defmethod='s own, UNCHANGED
  parsing and loud-failure matrix, so e.g. a bare =:around= (no
  =:extra=) inside a =(:method ...)= form is rejected exactly as it
  would be at a top-level =cl-defmethod= call (this doc's §2.2
  divergence, unmodified by this addendum) while =(:method :extra
  STRING :around ...)= reaches the ALREADY-supported Addendum-1
  combination unchanged.
- Then, if anything remains once that OPTIONS-AND-METHODS run ends, one
  final method =(ARGLIST . REMAINING-BODY)=: the generic's own ARGLIST,
  verbatim, with NO specializers at all -- an ordinary =:kind
  unspecialized= primary method, i.e. exactly the same shape a bare
  =(cl-defmethod NAME ARGLIST BODY...)= call already produced before
  this addendum. This is the whole point: the default body needs no new
  dispatch machinery whatsoever. It is just another entry in the same
  method table =nelisp-cl-generic--register-method=/
  =nelisp-cl-generic--applicable-methods= already maintain, so it
  participates in specificity ordering, chains via
  =cl-call-next-method=, and -- because
  =nelisp-cl-generic--same-specializer-p= already treats two
  no-=:extra=/no-combinator =:kind unspecialized= entries as the SAME
  identity -- a later =cl-defgeneric= redefinition's new default body
  REPLACES the old one in place via the pre-existing
  =nelisp-cl-generic--register-method= logic, never duplicating it and
  never disturbing a specialized method, with zero new code for that
  behavior.
- =cl-defgeneric='s own macro body shrank to one =mapcar= over this
  helper's result, splicing =(cl-defmethod ,name ,@m)= for each --
  structurally the same technique real Emacs's own =cl-defgeneric=
  uses (=(mapcar (lambda (method) \`(cl-defmethod ,name ,@method))
  (nreverse methods))=), independently arrived at.

=cl-call-next-method=/=cl-next-method-p=,
=cl-no-applicable-method=/=cl-no-primary-method=, the =:extra=
qualifier grammar, and every specializer kind (§2.1, including
Addenda 1-2) are all completely untouched -- this addendum is entirely
inside =cl-defgeneric='s own macro, adding one parsing helper and
reusing every existing piece of §3's dispatch machinery unmodified.

Landed in both mirror copies (=lisp/nelisp-cl-macros.el= and
=scripts/nelisp-stdlib-prelude.el=, identically -- the new helper and
the =cl-defgeneric= macro body are byte-for-byte equal between the two

=cl-defgeneric=/=cl-defmethod= (and EIEIO's =defclass=, which is built on
the same =cl--class= machinery) are completely absent — every direct
symbol probed is =fboundp= nil (§1.1). =cl-defstruct= and =cl-typep=,
which this doc has to build on, are both present, but =cl-typep=

builtin-type allowlist with zero knowledge of =cl-defstruct=-generated

=(dog-p a-dog)= answers =t= (§1.2). The primitive a type-specializer
dispatcher actually needs — walking a struct's =:include= ancestry — is
a *different*, already-working function, =nelisp-cl-macros--struct-isa=
(=scripts/nelisp-stdlib-prelude.el:4019-4030=), confirmed live and
correct for multi-level inheritance by direct probe (§1.2).

There is *no in-repo evidence* for what specializer kinds or method
qualifiers real =cl-defgeneric=/=cl-defmethod= call sites actually use —
zero real call forms exist anywhere in this tree (a repo-wide grep for
=(cl-defmethod =/=(cl-defgeneric = returns nothing but linter/indexer
vocabulary lists that recognize the *syntax* without ever seeing a real
instance, and no vendored copy of =transient.el=/=magit.el=/=eieio.el=
exists to measure against). This doc says so plainly rather than
presenting invented usage as measured (§1.3) — the specializer/qualifier
scope below is a first-principles design choice, not a repo-measured one.

The load-bearing prior art is Doc 157 (=docs/design/157-builtin-class-
type-lattice.org=), a 2026-06-23 attempt at porting *real*
=cl-generic.el= wholesale. Its own §5 hit a wall this doc treats as
authoritative: with =compiled-function-p= correctly bound (this runtime
has no byte-compiler), =cl-generic.el='s own eager
=cl--generic-prefill-dispatchers= tries to =(eval BIG-NESTED-LAMBDA t)=
~15-20 dispatchers at *require* time and did not finish inside a 280
second budget. The recorded decision — withhold =compiled-function-p= so
=cl-generic= stays "loadable but inert" rather than hanging the whole
load — is *still live today*, verified by a comment at
=scripts/nelisp-stdlib-prelude.el:4634-4645= and a direct probe (§1.4).
This is a real go/no-go signal, not narrative: *porting real
=cl-generic.el= is not viable on this interpreter; a hand-rolled subset,
built with a bounded, per-generic dispatch-table cost rather than an
eager global prefill, is the only direction that does not re-hit the same
wall.*

*Decided direction*: a hand-rolled =cl-defgeneric=/=cl-defmethod=
subset with *type* and *eql* specializers (structs dispatch via
=nelisp-cl-macros--struct-isa=, not via widening =cl-typep=), *primary*
methods plus =cl-call-next-method=/=cl-next-method-p= (needed for
struct-inheritance dispatch to be worth having at all), building each
generic's effective-method table once at =cl-defmethod= time rather than
eagerly at load time (§3.4, directly avoiding Doc 157's wall). Every
unsupported form — a method-combination qualifier, a specializer kind
other than type/eql/unspecialized, more than one dispatch argument — is a
loud, macroexpansion-time =error=, never a silent no-dispatch or a
silent wrong method (§3.5).

** §1.2 What =cl-defstruct=/=cl-typep= already give this doc

Two divergent =cl-defstruct= implementations exist —
=lisp/nelisp-cl-macros.el:439-472= (older, no =:conc-name=/=:predicate=
option support) and =scripts/nelisp-stdlib-prelude.el:4001-4037=

by matching the live macroexpansion byte-for-byte against this copy, not
the other). =scripts/nl-ns-accepted.el:9= tracks this exact duplication
as an accepted, known =ns-collision-divergent= finding — it is not a
surprise this doc discovered, but the *consequence* (which copy is live,
and what it supports) had not been traced through to a dispatch design
before.

Runtime representation: structs are tagged records
(=nelisp--make-record=/=-record-ref=/=-record-type=/=recordp=), *not* a
vector with an ad-hoc slot-0 tag — =nelisp--record-type= reads the type
symbol directly. A parallel elisp-level registry,
=nelisp-cl-macros--struct-info= (alist =NAME -> (:slot-names ... :parent
...)=), is rebuilt at both macroexpansion time and runtime-eval time of
every =cl-defstruct= form.

=:include= inheritance is *fully working*, confirmed empirically:

#+begin_src elisp
(cl-defstruct animal name)
(cl-defstruct (dog (:include animal)) breed)
(animal-p (make-dog :name "Rex" :breed "lab"))  => t   ; parent predicate over child record
(dog-p (make-animal :name "generic"))            => nil ; child predicate excludes parent
(animal-name (make-dog :name "Rex" :breed "lab")) => "Rex" ; parent accessor works on child record
#+end_src

via =nelisp-cl-macros--struct-isa= (=scripts/nelisp-stdlib-prelude.el:
4019-4030=), a plain recursive chain-walk over the =:parent= field in
=nelisp-cl-macros--struct-info=. *This is the primitive a type-specializer
dispatcher needs for struct ancestry, and it already exists, independent
of =cl-typep=.*

=cl-typep= (=scripts/nelisp-stdlib-prelude.el:1539-1546=):

#+begin_src elisp
(defun cl-typep (val type)
  (cond ((eq type 'integer) (integerp val))
        ((eq type 'number) (numberp val))
        ((eq type 'float) (floatp val))
        ((eq type 'string) (stringp val))
        ((eq type 'symbol) (symbolp val))
        ((eq type 'cons) (consp val))
        ((eq type 'list) (listp val))
        ((eq type 'vector) (vectorp val))
        ((eq type 'null) (null val))
        ((eq type 't) t)
        (t nil)))
#+end_src

A hardcoded ten-symbol allowlist with a =(t nil)= catch-all — *zero*
knowledge of =cl-defstruct=-generated types. Confirmed empirically:
=(cl-typep (make-dog ...) 'dog)= => =nil=, even though =(dog-p ...)= =>
=t= and =(nelisp--record-type (make-dog ...))= => =dog=. *This is the
single most load-bearing gap for this doc*: a dispatcher that calls
=cl-typep= naively will silently fail to dispatch on any struct-derived
type today — it must either extend =cl-typep=, or bypass it for
record-typed specializers. §2 decides which.

* §2 Decided direction

** §2.1 Specializer set: type + eql, structs via =struct-isa= not =cl-typep=

| specializer | supported | mechanism |
|---|---|---|
| unspecialized (bare arg, implicit =t=) | yes | always matches, lowest specificity |
| =(ARG TYPE)=, TYPE a =cl-typep= builtin (integer/string/...) | yes | =cl-typep= unchanged (§2.1a) |
| =(ARG TYPE)=, TYPE a =cl-defstruct= name | yes | =nelisp--record-type= + =nelisp-cl-macros--struct-isa= (§2.1a) |
| =(ARG (eql VALUE))= | yes | =eql= comparison, highest specificity; bare symbol VALUE is literal data, while compound VALUE forms are evaluated at definition time |
| =(ARG (head VALUE))= | yes (T59 addendum, see Addendum 2 above) | cons whose =car= is =eql= to VALUE; priority between =eql= and any type match |
| =(ARG (subclass CLASS))= | yes (T102 addendum) | class designator or =(subclass CLASS)= data form equal to CLASS or one of its known parents; priority below =head= and above ordinary types |
| list-head grammar beyond plain =(head VALUE)=, e.g. multiple VALUEs | *no* | loud error if written (§3.5) -- a deliberate, documented stricter-than-real-Emacs choice (Addendum 2) |
| =&context=, custom specializer forms | *no* | same |

*§2.1a — resolves §1.2's open question explicitly*: do NOT widen
=cl-typep= in place. =cl-typep='s existing ten-symbol contract stays
frozen — other callers of plain =cl-typep= must not observe a behavior
change from this doc landing. Dispatch instead through a new, dispatch-
only predicate, =nelisp-cl-generic--type-match= (§3.2), which tries
=cl-typep= first for the ten built-ins and falls back to
=nelisp--record-type=/=nelisp-cl-macros--struct-isa= for anything
=recordp=. This keeps =cl-typep= composable with ordinary code exactly as
it is today, and keeps this doc's dispatch logic in one place rather than
smeared across a widened general-purpose predicate.

** §2.2 Method combination: primary + =cl-call-next-method=, everything else out

*In scope*: primary methods (no qualifier), ordered by specificity
(eql > struct-child > struct-parent > builtin-type > unspecialized),
=cl-call-next-method=/=cl-next-method-p= to continue down that ordering.
Without this, struct-inheritance dispatch (§2.1's main real capability)
is far less useful — the common shape a class hierarchy actually needs is
"child method does its own thing, then calls into parent behavior," which
is exactly what =cl-call-next-method= is for.

*In scope*: standard bare =:before=/=:after=/:around= qualifiers use the
same before/primary/after/around combination as real Emacs.  Before methods
run most-specific first, after methods least-specific first, and around
methods wrap the whole combination through =cl-call-next-method=.  Auxiliary
return values do not replace the primary result; an applicable set without a
primary signals =cl-no-primary-method=.

*Out of scope, loudly rejected*: any method combination beyond the standard
primary/next-method combination and these three standard qualifiers (with or
without the =:extra= extension below).  A =cl-defmethod= form using a
qualifier this subset does not implement signals a loud, macroexpansion-time
error (§3.5) — never a silently-ignored qualifier.

*Addendum (2026-09-05), see the top-of-doc note*: the =:extra STRING=
qualifier — real Emacs's own name for "another method on the same
specializer, distinguished by STRING" — turned out to be needed for real
(real Emacs's own =cl-lib.el= uses it on =cl-generic-generalizers=, hit
transitively by =(require 'cl-lib)=) and is now implemented, including
its combination with exactly one of =:before=/=:after=/=:around=. Bare
=:before=/=:after=/=:around= is now supported directly as well; arbitrary
method combinations remain out of scope.

** §2.3 Dispatch-table construction: per-generic, at define-time — not Doc 157's wall

Each =cl-defgeneric='s effective-method table is built once, when its
methods are complete enough to be called (i.e., lazily on first
=funcall=, memoized, OR eagerly at the closing =cl-defmethod= of a given
generic — §3.4 picks one), and costs work *proportional to that one
generic's own method count*. This is the direct, explicit answer to
Doc 157's wall (§1.4): that port's 280-second failure came from *eagerly
prefilling ~15-20 dispatchers at require time* via full-generality
=eval=-based dispatcher compilation. Nothing in this design does anything
at require time beyond defining macros; the first per-generic cost is
paid when that specific generic is actually used.

* §3 Design

** §3.1 =cl-defgeneric=/=cl-defmethod= macro shape

#+begin_src elisp
(cl-defgeneric render (obj))              ; declares the generic, no methods yet
(cl-defmethod render ((obj widget)) ...)  ; type specializer
(cl-defmethod render ((obj (eql 'special))) ...) ; eql specializer
(cl-defmethod render (obj) ...)           ; unspecialized fallback
#+end_src

Required arguments may carry specializers at any position.  When multiple
positions are specialized, applicable methods are ordered lexicographically
by their specializer priority in =:argument-precedence-order= (defaulting to
source argument order), matching real =cl-generic=.  This subset keeps the
dispatch table lazy and scans only the methods of a generic that uses a
nonzero dispatch position.

** §3.2 =nelisp-cl-generic--type-match=

#+begin_src elisp
(defun nelisp-cl-generic--type-match (val type)
  (cond
   ((memq type '(integer number float string symbol cons list vector null t))
    (cl-typep val type))
   ((and (recordp val) (nelisp-cl-macros--struct-isa (nelisp--record-type val) type))
    t)
   (t nil)))
#+end_src

Reuses =cl-typep= for the ten builtins exactly as-is (§2.1a) and
=nelisp-cl-macros--struct-isa= (already correct, §1.2) for structs — no
new type-matching logic, only composition of two already-working
functions.

** §3.3 Specificity ordering for structs

=nelisp-cl-macros--struct-info='s =:parent= chain (§1.2) gives an exact
ancestry depth for any two related struct types — a method specializing
=dog= is strictly more specific than one specializing =animal= for a
=dog= instance, computed by walking the chain and counting steps.
=eql= specializers outrank every type specializer (an exact-value match
is always more specific than a type match); unspecialized is always
least specific. Two methods whose specializers are unrelated types (or
tie) for a given call is an ambiguous-dispatch condition — signaled
loudly (§3.5), not resolved by definition order, since silently picking
"whichever was defined last" is exactly the kind of implicit, surprising
behavior this doc's loud-failure discipline exists to avoid.

** §3.4 Per-generic table construction: build lazily, on first call

Resolves §2.3's open choice: build the effective-method table *lazily*,
on the generic's first invocation, cached on the generic's symbol
property list, invalidated by a new =cl-defmethod= for that generic name
(the common case — Doc 157's own wall was about *eager*, *global*
prefilling; a lazy, per-symbol cache sidesteps it entirely and also
avoids paying for generics that are defined but never called, which
=cl-defgeneric='s own "declare it before you have all its methods" idiom
makes common). Invalidating on redefinition, rather than rebuilding
eagerly, keeps a live-patching workflow (redefine one method, re-eval)
cheap — only the next actual call pays the rebuild.

** §3.5 Loud failure — the specific error shapes

| condition | contract |
|---|---|
| unsupported qualifier (unknown qualifier, duplicate/invalid shape, or any method-combination form beyond bare or =:extra STRING= + one standard qualifier) | =error= at =cl-defmethod= macroexpansion time, names the qualifier |
| =:extra= not followed by a string | =error= at =cl-defmethod= macroexpansion time (addendum, 2026-09-05) |
| unsupported specializer form (not a type name, not =(eql V)=, not =(head V)= (Addendum 2), not =(subclass CLASS)= (T102), not a bare unspecialized arg) | =error= at macroexpansion time, names the form |
| specializer on an optional/non-required argument | =error= at macroexpansion time or ordinary optional-argument parsing |
| call with no applicable method | =signal 'cl-no-applicable-method (list generic-name args)= — same symbol real Emacs uses, a genuine parity point (§6.2) |
| two applicable primary methods, neither strictly more specific (§3.3) | =error= naming both, at *call* time (this one cannot be caught earlier — it depends on the runtime argument, not the =cl-defmethod= form alone) |
| several methods at one specificity tier differing only by =:extra= string | *not* ambiguous — coexist, newest-defined-first, chained via =cl-call-next-method= (addendum, 2026-09-05) |
| applicable methods exist but none is primary (only bare or =:extra=+before/after/around) | =signal 'cl-no-primary-method= — same symbol/message real Emacs uses (addendum, 2026-09-05) |
| =cl-call-next-method= called with no next method | =signal 'cl-no-next-method= (mirrors real Emacs's own error symbol) |

Every one of these is a real, catchable Lisp signal — never a bare
=funcall= on something that turns out void (the exact failure family
=scripts/nelisp-standalone-build.el:17936-17945= documents as already
live and being actively patched elsewhere in this codebase, §1.5). This
is the concrete answer to the task's "fails loudly rather than silently
mis-dispatching" requirement: every boundary this subset draws produces
a signal a caller can =condition-case= around, at the earliest point the
information to raise it exists.

* §4 Phased plan with costs

Effort estimates are engineer-days for an implementer following this
doc, on the pattern of Doc 164 §6.

** P0 — =cl-defgeneric=/=cl-defmethod= macros, primary-only, type+eql, single-arg (2-3 d)
- The macro pair (§3.1), =nelisp-cl-generic--type-match= (§3.2), the
  specificity ordering (§3.3), the lazy per-generic table (§3.4), and the
  full loud-failure matrix (§3.5) — this phase is the whole subset's
  correctness core, sized together because splitting dispatch-order from
  loud-failure would let one land without the other's safety net.
- *Exit*: the =against-the-bug= cases in §6.1 all pass; a =cl-defmethod=
  with an =:around= qualifier or a head specializer signals at
  macroexpansion time, verified by =should-error= at =eval= time on the
  =defmethod= form itself, not at first call.

** P1 — =cl-call-next-method=/=cl-next-method-p= (1 d)
- Threading the remaining effective-method list through the dispatcher's
  call frame (a dynamic variable bound around each dispatch, restored on
  return — the standard =cl-generic.el= technique, scoped down).
- *Exit*: a three-level struct chain (grandparent/parent/child methods,
  each calling =cl-call-next-method=) produces the same call order as
  real Emacs's =cl-generic= for the equivalent hierarchy (parity form,
  §6.2).

** P2 — =cl-no-applicable-method=/=cl-no-next-method= signal parity (0.5 d)
- Wire the two named-signal cases from §3.5's table.
- *Exit*: =(condition-case e (render 5) (cl-no-applicable-method 'caught))=
  returns =caught= when no method applies to a plain integer with no
  unspecialized fallback defined.

** P3 — ambiguous-dispatch detection (1 d)
- The "two applicable primaries, neither more specific" case (§3.3's
  last row) — genuinely needs care to avoid false positives on legitimate
  unrelated-type overload sets that never collide at a real call site.
- *Exit*: two methods on unrelated struct types, called with an instance
  of neither, correctly signals =cl-no-applicable-method= (not ambiguity —
  neither applies); two methods on sibling structs under a shared,
  ambiguous multiple-inheritance-like shape (this subset doesn't support
  multiple =:include=, so this case may turn out unreachable and P3 could
  shrink — verify against what =:include= actually allows before costing
  further work here).

Total: *4.5-5.5 engineer-days*. P0 alone is independently useful (single-
dispatch-argument, primary-only generic functions with correct struct
inheritance ordering) even if P1-P3 slip.

* §6 Open questions

** §6.1 Multiple =:include= / diamond inheritance

=cl-defstruct='s =:include= is single-parent only (confirmed by
=nelisp-cl-macros--struct-info='s =:parent= field being a single slot,
not a list) — so §3.3's specificity ordering and P3's ambiguous-dispatch
detection may be simpler than a full diamond-aware =cl-generic= would
need. Worth confirming this is a hard =cl-defstruct= limit (not just an
unexercised path) before finalizing P3's scope, since if it is hard, an
entire class of ambiguity this doc costs for (P3) may not be reachable at
all.

** §6.2 Whether P0's scope should include struct slot-value specializers

Real =cl-generic= (via =cl-generic-generalizers=) supports specializing
on more than "is-a-type" — e.g., a struct's own custom generalizer
forms. Nothing in this doc's evidence base (§1) suggests any consumer
needs this, and adding it multiplies §2.3's dispatch-table complexity
for no measured benefit. Left out by default; flagged so a future
revision with real usage evidence has an explicit place to reopen it
rather than silently expanding scope.

** §6.3 Should =nelisp-cl-generic--type-match= be exposed as public API

§3.2's helper is dispatch-internal, but it is also exactly the "does
=cl-typep= but also knows about structs" predicate ordinary user code
might reasonably want directly (e.g., outside a =cl-defmethod= body).
Whether to expose it as e.g. =cl-typep-including-structs= or keep it
=nelisp-cl-generic--=-internal is a naming/API-surface call this doc does
not make — both are compatible with §2.1a's "don't widen =cl-typep=
itself" decision either way.

** §6.4 Reusing the five staged Doc-157 primitives

§1.1 found =cl--find-class=/=with-memoization=/=closurep=/=ignore=/
=always=/=interpreted-function-p= already baked into the prelude
specifically as cl-generic prerequisites, currently unused by anything.
This doc's hand-rolled subset does not need any of them (§3's design
uses only =cl-typep=, =nelisp-cl-macros--struct-isa=, and
=nelisp--record-type=) — whether to reuse them anyway (for naming
consistency with a possible *future* fuller port) or leave them
untouched and unused is a judgment call for the implementer, flagged so
a future reader does not assume their presence implies more
cl-generic-adjacent infrastructure exists than actually does.
