#+TITLE: Common Lisp (SBCL) features missing from NeLisp, and how to fill them
#+DATE: 2026-11-07
#+STATUS: ACCEPTED (2026-11-07) — owner confirmed the decisions below; nothing here is implemented
#+SCOPE: What SBCL offers that NeLisp lacks, which gaps are worth filling, at which layer, and in what order
#+EVIDENCE: docs/design/evidence/cl-gap-20261107/

* Summary

NeLisp's goal is a practical Emacs-compatible runtime, not ANSI Common Lisp
conformance.  This document therefore does not propose making NeLisp a Common
Lisp.  It records the gaps and picks a fill for each one: a library, a runtime
change, a third-party package, or an explicit decision not to fill it.  The owner
decisions that govern the scope are in "Owner decisions".

Three findings matter most:

1. Common-Lisp-equivalent threads already exist, but not on =origin/main=.
   Doc 214 on =origin/feat/cl-threads= provides closures on real OS threads,
   locks, condition variables, semaphores, atomic integers, interrupt and destroy
   as =nl-bt-*=.  On =origin/main= only the Doc 199 =clone(2)= primitives are
   available, and =emacs-lib-core='s =make-thread=, =make-mutex=, =condition-wait=
   and =make-finalizer= are stubs.  The thread gap is an integration task, not a
   design task.
2. Restarts in =nl-condition= miss primitive errors, because =nl-handler-bind=
   only sees =nl-signal=.  Bridging to the built-in =handler-bind= reaches them, but on
   the binary that handler runs after unwinding (Doc 245 D8), so the fix is only
   partial until the core changes.
3. Heap exhaustion aborts the process with exit code 88.  SBCL signals a
   catchable condition.  Of the gaps here, this is the one most likely to
   matter to a long-running editor or server regardless of any CL goal.

* Governing constraints

These come from existing rules, and this document does not relax them.

- *Stock Elisp stays stock.*  Fills are opt-in, and unannotated code behaves as
  GNU Emacs does (Doc 196, Doc 198).  =(/ 1 3)= stays =0=.
- *L1 first* (Doc 168).  L1 is macros and functions in a package, L2 is a compiler
  pass, L3 is evaluator or reader extension.  L2 or L3 work starts only after an
  equivalent L1 version has shipped and produced real usage data, and a feature
  judged to need L3 at design time goes to Doc 90.
- *Minimal native surface* (=AGENTS.md=).  A new native needs a named clause, a
  measurement, a Lisp reference, and an inventory entry.  "Faster" does not
  qualify.  Rust stays at zero.
- *Naming.*  New CL-like API uses the =nl-= prefix.  It must not claim =cl-= names
  or bare CL names, which belong to GNU Emacs and vendored =cl-lib=.  A reused or
  forked third-party package keeps its upstream public names.  Check that those names
  do not collide with GNU Emacs or vendored =cl-lib=.
- *Progress.*  Each work package adopted below needs a ledger under =tools/ai/=
  before implementation, ending in an end-to-end criterion.

* Work packages

** WP1: complete nl-condition

The defect: =nl-handler-bind= keeps its own =nl--handler-stack=, so =(car 1)= under
=nl-handler-bind= never reaches the handler (probe).  The built-in =handler-bind= ran its
handler on the same error, but a later probe showed that on the binary it runs after
unwinding, unlike GNU Emacs (Doc 245 D8).  The original wording here said "before
unwinding"; the first probe did not test that.

Plan:

- Reimplement =nl-handler-bind= on the built-in =handler-bind=, or have it install
  both, so that primitive errors can invoke restarts.  Keep working on host Emacs
  versions that have =handler-bind=, and state the behavior on those that do not.
- Add =nl-with-simple-restart=, =nl-restart-bind=, =nl-cerror=, and the standard
  restarts =abort=, =continue=, =muffle-warning=, =use-value=, =store-value=, all
  =nl-= prefixed.
- Add correctable =nl-check-type= and =nl-assert=.
- Add =nl-signal-condition=, which returns nil when unhandled.  Today a non-error
  symbol passed to =signal= fails with "Invalid error symbol" (probe).
- Keep conditions as =(SYMBOL . DATA)= with =define-error= hierarchies.  Do not add
  =define-condition= slot objects until a consumer needs them.

Open point: an interactive debugger that offers restarts is a separate REPL
feature.  It belongs with =nelisp-repl-development= and depends on this package.

Acceptance: a restart chosen by a handler recovers from a real primitive error on
=target/nelisp= and on host Emacs, with a negative control where no restart exists.

** WP2: integer and float functions in nl-num

Add =nl-ldb=, =nl-dpb=, =nl-byte=, =nl-boole=, =nl-integer-length=, =nl-logtest= and
hyperbolics with their inverses, working with tag-13 bignums.  The core binary also lacks
the six trigonometric functions (Doc 245 D2), which is a parity defect rather than part of this package.  Provide =float-pi=
compatibility only where GNU does, which is a parity matter rather than a CL one.

=logcount=, =frexp=, =ldexp= exist only in =emacs-lib-core=.  Whether they should
move down to the core is a Doc 141 boundary question, and is not decided here.

Acceptance: differential test against SBCL over generated fixnum and bignum inputs.

** WP3: format directives, by evaluating an existing package

MELPA =cl-format= (=gitlab.com/akater/elisp-cl-format=, GPL-3.0-or-later, no
dependencies beyond Emacs) defines 28 directives in =cl-format-builtins.el=,
including =~R ~D ~F ~A ~S ~{ ~[ ~< ~/ ~?=.  The code dates from 2012.

Result (2026-11-07): Doc 245 records the evaluation and its verdict, which is to fork.  It
also found NeLisp defects to fix first, including =lexical-binding= handling.

Plan: run it on =target/nelisp= with its =cl-format.ert= from the upstream repository
(the MELPA tarball omits it).  Then decide, in this order of preference:

1. Works, or nearly so: import it as an optional package under the conditions in
   "Owner decisions", and fix NeLisp defects exposed along the way, following
   =nelisp-defect-peel=.
2. Needs substantial changes: vendor it with attribution under GPL-3.0-or-later.
3. Unsuitable: write =nl-format= with the same directive set.

Pretty printing (=pprint-logical-block=, =pprint-dispatch=) is deferred; =pp= and
=cl-print-object= cover current needs.  MELPA =ppp= is formatting only and does not
fill this gap.

Acceptance: differential test against SBCL =format= over a directive corpus.

** WP4: nl-array

Records holding a dimension list and a flat row-major vector.

- =nl-make-array=, =nl-aref=, =gv= setter, =nl-array-dimensions=, =nl-array-rank=,
  =nl-array-row-major-aref=.
- Fill pointers and adjustment for rank-1 arrays: =nl-vector-push=,
  =nl-vector-push-extend=.
- Displacement through an offset and shared backing vector.
- =:element-type= recorded and checked, with no specialized storage initially.

Stock =aref= stays untouched.  Specialized storage belongs to the native compiler
after usage data exists (L2), and to the off-heap regions of Doc 237 for large
numeric data.  No archive package fills this gap (=vector-utils= is not arrays).

Acceptance: differential test against SBCL, plus a native-compiled numeric workload
measured against nested vectors.

** WP5: nl-stream

Elisp's stream convention (buffers, markers, functions, =t=) is kept for stock code.
=nl-stream= adds objects: =cl-defstruct= classes with =cl-defgeneric= operations
=nl-stream-read-char=, =-unread-char=, =-write-char=, =-read-byte=, =-write-byte=,
=-file-position=, =-close=, in the spirit of Gray streams.

Concrete classes: string input and output, file, broadcast, two-way, echo,
concatenated.  Also bridge to function-valued =standard-output= so that stock
=princ= can write to an =nl-stream=.

File backend: start with =insert-file-contents-literally= and =write-region=.
Unbuffered descriptor access needs a callable path to the OS; =nelisp-sys= is a typed
AOT subset, not ordinary dynamic Elisp, so it needs a thin adapter or
=syscall-direct=.

GNU ELPA =stream= is lazy lists, not I/O, and does not apply.

** WP6: pathnames

Write a small =nl-pathname= struct after =nl-stream=.  =expand-file-name= and friends
keep serving ordinary Elisp code.  MELPA =f= covers convenience, but it pulls in =s= and
=dash=, so it stays a user choice rather than a dependency.

** WP7: CLOS extensions

=cl-generic= and EIEIO already handle multiple inheritance, multiple dispatch, =eql=
specializers and =:before= / =:after= / =:around= (probe).

- *Method combination.*  Define =nl-define-method-combination= over =cl-generic='s
  own extension points.  Doc 185's fast subset covers primary methods and
  =cl-call-next-method= only, so check that such a generic reliably takes the full
  path.
- *MOP introspection.*  A read-only =nl-mop= over =eieio-class-slots=,
  =eieio-class-parents=, =cl-find-method=: class slots, precedence list, applicable
  methods.  Writable MOP is out of scope.
- *=change-class=.*  Records have fixed length, so in-place change cannot be written
  in L1 when the slot count grows.  An L1 =nl-change-class= returning a new object
  loses identity and must be named accordingly.  True identity-preserving change
  needs a native "become" primitive (clause 1) or forwarding, which conflicts with
  the non-moving collector's assumptions and needs its own justification.  Defer.
- *=&whole= in =cl-defmacro=*: this is a limit of the vendored =cl-macs=.  Do not patch
  the vendor copy.
- *=define-symbol-macro=*: global symbol macros require =macroexpand-all= to treat free
  variables specially, which is outside stock semantics.  Defer until requested.

** WP8: threads are owned by Doc 214; integrate them

This package does not design threads.  Doc 214 already does.

Doc 214 is on =origin/feat/cl-threads= (tip =eccec35d3=, 2026-10-18).  It holds 18
commits absent from =origin/main=, while =origin/main= holds 3596 commits absent from
it (merge base 2026-10-17).  Its document file is not on =origin/main=, whose two
Doc 214 files cover other subjects.

=nl-bt-*= API on the branch: thread make, join, yield, interrupt, destroy; plain and
recursive locks; condition variables; semaphores; atomic integers with CAS.

Measured on Linux x86-64 at =eccec35d3= on 2026-11-07:

|------------------------------------------+-----------------------------------------|
| All eight =tools/nelisp-bt-*-smoke.el=   | Pass                                    |

| Fixed work, loop only, 1 vs 4 threads    | 2.63x and 3.00x faster on 4 threads     |
| Fixed work, consing, 1 vs 4 threads      | 2.53x and 2.57x faster on 4 threads     |

SKIP counts as not done.  Windows was not run here, so the Windows stages remain
unverified by this document.  The timings are single runs of two rounds on a machine
with other load, so they show real parallelism rather than a performance figure.

State of =origin/main= (source):

| Name                       | State                                                        |
|----------------------------+--------------------------------------------------------------|
| =thread-spawn=, =nelisp-thread-join= | Real =clone(2)= threads (Doc 199 Tier 3b)          |
| =atomic-fetch-add=         | Callable                                                     |
| =atomic-compare-exchange=  | AOT DSL form only, not =fboundp= in ordinary Lisp            |
| =make-thread=              | =emacs-lib-core= stub: =funcall= runs synchronously          |
| =make-mutex=               | =emacs-lib-core= stub: a record with no locking              |
| =condition-wait=           | =emacs-lib-core= stub: always signals                        |

Doc 214 section 0 settles the API question: =nl-bt-*= is a separate opt-in namespace
and the =make-thread= family keeps Emacs semantics.  This document follows that.

The stubs still matter on =origin/main=.  Code using =make-thread= for background work
silently runs in the foreground.  They are defensible as parity placeholders, but they
should be documented as such, and the documentation should point at =nl-bt-*=.

Integration plan (owner decision, 2026-11-07):

1. Document the stubs now.  This does not depend on the port.
2. Do not merge into a speedup branch, and do not start while the overlapping work
   is active.  A dry-run =git merge-tree= conflicts in the same seven files against
   =origin/main=, =feat/sbcl-native-impl-f12-20261031= and =fix/f12-gates-20261107=:
   =nelisp-aot-compiler.el=, =nelisp-cc-env-lookup-function.el=,
   =nelisp-cc-nlstr-direct-ops.el=, =nelisp-cc-rootstack.el=, =nelisp-cc-sf-while.el=,
   =nelisp-static-linker.el= and =nelisp-standalone-build.el=.  The cause is the growth
   of =origin/main= since 2026-10-17, not any one speedup branch.
3. After the =fix/main-ci-reds-*= and f12 work lands on =origin/main=, create
   =port/214-cl-threads= from =origin/main=.  It is the only writer of the overlapping
   files for its duration.
4. Treat it as a port, not a conflict resolution.  Doc 214's audit found about 210
   literal sites of per-process state.  Code added since the fork, including native
   fast paths, must be audited against the same per-thread rules, because a clean
   text merge does not show that it is thread-safe.
5. Done means =tools/ai/214-cl-threads-progress.org= measured on the port branch with
   both the Linux and Windows binaries, the eight smokes passing, and a paired
   single-thread regression check against the =origin/main= merge base.

=nelisp-actor= and =nl-clj-async= remain the higher-level models.  MELPA =semaphore=,
=aio= and =futur= are not needed for this gap.

** WP9: catchable heap exhaustion

Under a 3 GiB address-space cap, an allocation loop inside =condition-case= ends with
=nelisp: memory exhausted (memory-full)= and rc=88, while SBCL under a similar test
reported =HEAP-EXHAUSTED-ERROR= to its handler (probe).

Plan: keep a reserve region released on first failure, signal =memory-full= from the
allocation slow path at a safe point, and re-arm the reserve after a successful GC.
GNU Emacs has the same concept, which makes this a parity improvement as well.  The
hard part is making the slow path safe to signal from every allocation site,
including native code and worker threads.  Those sites should be enumerated first.
If only the evaluator path can be made safe, ship that and keep aborting elsewhere.

** WP10: weak references, finalizers, GC controls

- =weak-ref= (MELPA, =github.com/skeeto/elisp-weak-ref=) is a one-entry weak hash
  table with =:weakness t=.  NeLisp's weak tables work with =:weakness 'key= (probe).
  Test the =t= case, then write a small =nl-weak-ref= with the same technique, since no
  consumer justifies an import yet.
- =make-finalizer= in =emacs-lib-core= never runs its function (source).  Real
  finalizers need a post-mark hook: a native change under clause 2.
- =gc-cons-threshold= is not bound in the core (probe).  Whether allocation pacing
  should be user-tunable depends on Doc 234 and is not decided here.

** WP12: reader syntax

Probe results: =#.=, =#+=, =#-=, =#2A=, =#*= are invalid syntax; =1/3=, =1.5f0= read as
symbols.  There is no readtable.  =?\N{...}= also failed on the probe, which is a GNU
parity defect rather than a CL gap and should be fixed on its own.

This is L3, so Doc 168 sends it to Doc 90.  Requirements if it proceeds:

- Opt-in per =read= call or per file, using the Doc 189 reader-hook precedent
  (=nelisp-read-namespace-resolve=, default nil).
- Stock =read= output remains byte-identical.
- =#.= defaults to off because it evaluates during =read=.

The L1 versions come first: =nl-rational=, =nl-make-array= and =featurep= cover the
semantics without new syntax.  Doc 196 Phase 5 remains deferred.

** WP13: FFI callbacks

=nl-libffi= states no callback or varargs support.  Callbacks need libffi closures,
rooting for the Lisp function, and a rule for calls arriving on foreign threads.
=emacs-ffi= is a GNU dynamic module and will not help.  Write a separate design when a
consumer appears.

** Not pursued for now

=sb-simd= and =sb-rotate-byte=: =sb-simd= needs a vector IR in the native compiler, and
no consumer asks for either.  =sb-unicode= normalization: =charprop.el= is present in
=emacs-lib-core=; revisit if the Emacs-parity work needs =ucs-normalize=.

* Archive search results with no usable candidate

The archives returned nothing usable for restarts, rationals, complex numbers,
multidimensional arrays, readtables, method combination, MOP, FFI, or thread pools.
Names that look close but do not apply: =stream= (lazy lists), =multi= (Clojure-style
multimethods), =yaxception= (Java-style exceptions), =bitpack= (binary packing).  The
search covered names and one-line descriptions only, so absence is not proof.

License check before any reuse: NeLisp is GPL-3.0.  GPL-2.0-only code cannot be
combined, and repositories GitHub reports as unlicensed need their file headers read.

* Recommended order

Ordered by value for cost and by independence from each other.

| Order | WP                  | Why now                                                    |
|-------+---------------------+------------------------------------------------------------|
|     1 | WP8 stub documentation | No code risk; prevents silent misuse                    |
|     2 | WP1                 | Small, pure Lisp, repairs a real defect in a shipped package |
|     3 | WP3 evaluation      | One test run decides reuse or rewrite                      |
|     4 | WP2, WP10 weak refs | Small and independent                                      |
|     5 | WP11 GNU tools      | Vendoring GNU files also exposes substrate defects         |
|     6 | WP9                 | High value, but needs site enumeration first               |
|     7 | WP8 Doc 214 port    | After current work lands on =origin/main=; see WP8         |
|     8 | WP4, WP5, WP6, WP7  | Library family; a consumer moves an item forward           |
|     - | WP12, WP13          | Runtime work, outside the library family; Doc 90 or separate design |

* Owner decisions (2026-11-07)

1. *Threads: port, do not merge into a speedup HEAD.*  =feat/cl-threads= goes through
   =port/214-cl-threads= from =origin/main= after the current work lands, as set out
   in WP8.  It is not scheduled for a fixed date.
2. *CL scope: build a library family (revised the same day).*
   - Runtime capability that SBCL exemplifies (threads, GC, images, startup, native
     calls) is a goal, as Docs 199, 214 and 230-243 already show.  Work that needs the
     runtime stays outside the family: threads, heap exhaustion, finalizers, reader
     syntax, FFI callbacks.
   - The library-shaped gaps are built as extractable packages: WP1 to WP7, weak
     references, and the developer tools.
   - The consumer rule no longer gates starting.  It orders the work: an item with a
     consumer moves forward.
3. *Third-party packages: reuse or fork by rule (revised the same day).*  Run the
   candidate's own test suite on =target/nelisp= and decide from the result:
   - Passes unchanged, or fails only on NeLisp defects: reuse a pinned commit and fix
     NeLisp.
   - Needs package changes and upstream is active: send the change upstream and pin the
     fixed commit.
   - Needs package changes and upstream has been dormant for 24 months or more: fork
     into =packages/=, keeping the public names and license.
   - No candidate: write an =nl-*= package.

   Any import must meet all of these:
   - Not required by the core or the cold image, and loaded only by an explicit
     =require=.  =nl-*= packages may depend on it only through a declared manifest entry.
   - Commit and SHA-256 pinned, with origin and license recorded, as =vendor/= does.
   - A standalone smoke that loads and exercises it.
   - A GPL-3.0-compatible license confirmed in the file headers.

The library family's structure and extraction criteria are to be set in Doc 245, after
the =cl-format= evaluation.

These decisions followed a review by the advisor, requested by the owner.

* Reproducing the probes

=docs/design/evidence/cl-gap-20261107/= holds the name probe output
(=name-probe.out=, columns: name, SBCL kind, then =F= / =V= for bare function or variable
and =f= / =v= for the =cl-= prefixed form), the feature probe driver
(=feature-probe.py=, run from a source checkout with =target/nelisp= built; it requires
one unused positional argument and prints to stdout), and its output
(=feature-probe.out=).  In that output values
appear twice, because =--eval= also prints the value when it is the sole action.  The
follow-up probes for EIEIO details, heap exhaustion and =nl-handler-bind= are not in
that driver; the results are quoted in this document.

The WP8 timings come from =thread-speedup.el=, run on the =feat/cl-threads= binary with
=-L packages/nelisp-bt/src --load=.  Its output is =thread-speedup.out=.
