* §0 TL;DR

Four implementations of "text you can edit" coexist, and none of them is
what the shipped binary actually runs on the standard names. Two — a
full-featured gap buffer with real markers/overlays
(=src/nelisp-buffer.el=, 593 lines) and a =display-concept-0= gap buffer
that Doc 33 (LOCKED) names as the sanctioned core primitive
(=src/nelisp-text-buffer.el=, 484 lines) — are both entirely absent from
=target/nelisp= (fboundp nil for every function either defines, confirmed
by probe). The one that *is* live is a third, ad-hoc implementation in
=scripts/nelisp-stdlib-prelude.el= — real for =generate-new-buffer=/
=get-buffer=/=kill-buffer=/=with-current-buffer=, but =insert= writes to
a disconnected variable no reader ever consults (§1.3, reproduced live),
and =point=/=goto-char=/=current-buffer=/=set-buffer=/=re-search-forward=
are simply void-function. A fourth partial copy in
=lisp/nelisp-stdlib-misc.el= is honest about being stubs but is neither
what ships nor what anything else builds on. On top of all four, ~4100
LOC across four packages (textprop-hook/keymap/display, overlay) assume a
bare, ambient =(current-buffer)= — the host-Emacs primitive, not any of
this tree's own — and one of them installs an =add-hook= call,
unconditionally, at load time, for a function that does not exist in this
tree at all.

Every one of the 258 ERT tests covering this surface runs under host
Emacs (=$(EMACS) --batch=, =Makefile:16=); zero run against
=target/nelisp=. What this doc's own probes found on the actual binary —
the disconnected =insert=, the void =set-buffer=, the hardcoded-=1=
=point-min=/=point-max= — was invisible to the existing suite by
construction, not merely unmeasured.

- "What Magit/Org-grade packages need first — cite recipes/README's own

*Decided direction*: =src/nelisp-buffer.el='s data model (1-indexed
=point=, real markers, real overlays, flat text-property intervals) is
the substrate of record — not =nelisp-text-buffer.el='s 0-indexed cursor
model, which Doc 33 locks in but which nothing else in the tree, including
the four already-built packages, was ever written against. Adopt
=nelisp-text-buffer.el='s *gap-buffer byte/UTF-8 implementation
technique* underneath =nelisp-buffer.el='s *1-indexed point API* — this
keeps Doc 33's real intent (a fast primitive underneath a compatibility
layer) while dropping the one piece of it (0-indexing) that is
incompatible with every real consumer measured in this doc, including
Emacs itself. Port =nelisp-buffer.el= to load in the standalone reader,
wire the prelude's standard names to delegate to it instead of the
disconnected ad-hoc vector, and land the already-designed, currently-
unmerged generic =add-hook= (Doc 184 §1's sibling finding) *first*,
since one of the four packages already depends on it unconditionally at
load time. §6 asks Doc 33's owner to reconcile the LOCKED text explicitly
rather than this doc silently overriding it.

* §1 Problem — measured evidence

** §1.1 =src/nelisp-buffer.el= (593 lines) — real, feature-complete, host-only

A genuine two-string gap buffer (=before-gap=/=after-gap= string fields
on =cl-defstruct nelisp-buffer=, =:30-41=), not a list-of-chars or a
naive single string. =nelisp-goto-char= rebalances the gap by re-slicing
the concatenated string (=:293-303=); =nelisp-point= is =(1+ (length
before-gap))=, i.e. genuinely 1-indexed, matching Emacs.

Marker and overlay support is real, not stubbed: =cl-defstruct nelisp-
marker= (=:43=) and =cl-defstruct nelisp-overlay= (=:53=), plus four
shift helpers that walk the buffer's marker/overlay/text-property lists
on every insert/delete and apply Emacs's exact insertion-type/front-
advance/rear-advance semantics (=:199-289=). =nelisp-insert= (=:306=)
and =nelisp-delete-region= (=:324=) both call them. Text-property
intervals are a flat =(START END PLIST)= list (=:41=).

*Wiring*: load-bearing, but exclusively under host Emacs. =(require
'nelisp-buffer)= appears in =test/nelisp-buffer-test.el:17=,
=test/nelisp-marker-test.el:28=, =test/nelisp-editor-test.el:30=,
=packages/nelisp-redisplay/src/nelisp-redisplay.el:11= (+ its test),
=examples/nelisp-editor/main.el:34=. Every one of these is driven by
=make test= -> =$(EMACS) --batch= (=Makefile:16,54-60=) — host Emacs, not
=target/nelisp=. Zero references to any of this file's names exist in
=scripts/nelisp-stdlib-prelude.el= or =scripts/nelisp-standalone-build.el=
(grep count 0 in both). Direct probe on =target/nelisp=:

#+begin_example
(nelisp-generate-new-buffer-fn nil nelisp-goto-char-fn nil
 nelisp-insert-fn nil make-text-buffer-fn nil text-buffer-insert-fn nil)
#+end_example

Provenance: header cites "Doc 13 Phase 5-B.1... §2.6 is LOCKED 'Parallel'
(Doc 13 §5)" (=:7-9=). =docs/design/13-phase5b-core-substrate.org=
(dated 2026-04-24) is marked =STATE: SHIPPED 2026-04-24=. This is the
design doc this file implements.

** §1.2 =src/nelisp-text-buffer.el= (484 lines) — Doc-33-sanctioned, zero consumers

A byte-level gap buffer — =bytes= (a unibyte string with an embedded
gap), =gap-start=/=gap-end= (byte offsets), =char-count=/=byte-count=,
=cursor-char=/=cursor-byte= (=:37-58=), plus real UTF-8 char/byte
translation helpers (=:91-129=) — meaningfully more sophisticated at the
byte level than =nelisp-buffer.el='s substring-based gap.

The header (=:1-28=) states its design intent almost verbatim from Doc
33 §5.3 (§1.6 below): "no point/marker/overlay/face/major-mode/buffer-
local var/undo... intentionally a distinct type name from Emacs's
=buffer=... =nelisp-elisp-compat='s =buffer= implementation is meant to
use =text-buffer= internally and build marker/overlay/text-property on
top." This file is the intended Layer-1 primitive per the currently-
locked architecture doc.

*Incompatibility with §1.1, load-bearing for §2's decision*: =text-
buffer-cursor= is *0-indexed* (=:353=, doc comment "0-indexed char") vs.
=nelisp-buffer.el='s =nelisp-point=, which is *1-indexed*, Emacs's own
convention (=:155-157=). These cannot be merged by simple delegation —
every caller crossing the boundary needs an explicit +1/-1, a real
adaptation cost, not a rename.

*Wiring*: dead code outside its own test. A repo-wide grep for =require
'nelisp-text-buffer= returns exactly one hit,
=test/nelisp-text-buffer-test.el:10=. Nothing in =src/=, =lisp/=,
=packages/=, or =examples/= requires it. Probe confirms
=(fboundp 'make-text-buffer)= and =(fboundp 'text-buffer-insert)= are
both nil on =target/nelisp=.

=insert= (5797) and =buffer-string=/=insert-file-contents= (5880-5893)
read and write *different state* — this is the disconnected-variable bug,
reproduced live this session:

#+begin_example
(let ((b (generate-new-buffer "probe")))
  (with-current-buffer b (insert "abc"))
  (prin1 (list 'with-temp-file-contents-var nelisp--with-temp-file-contents
               'buffer-slot2 (aref b 2))))
=> (with-temp-file-contents-var "abc"  buffer-slot2 "")
#+end_example

=insert= silently "succeeds" (no error, correct =nil= return per Emacs's
own contract) and leaves the buffer's actual content slot untouched. This
is a *known, tracked* divergence, not an undiscovered landmine — the
repo's own name-collision gate (=scripts/nl-ns-accepted.el=, generated
2026-08-21) already carries =\"ns-collision-divergent insert lisp/
nelisp-stdlib-misc.el scripts/nelisp-stdlib-prelude.el 2f43c6e88852\"=
— but "accepted" there means only that a human signed off that the two
bodies *differ*, via a content hash; nothing in that gate checks that
either resulting *behavior* is correct, which is exactly the gap this
probe closes (§7.4 has the full accepted-entry list this doc's fixes
touch).

Worse than the disconnected variable alone: =point=, =goto-char=,
=current-buffer=, =set-buffer=, =erase-buffer=, =delete-region=, =re-
search-forward=, =search-forward=, =buffer-substring=, and =get-buffer-
create= are simply *absent* — void-function on =target/nelisp=, confirmed
by direct probe. An honest first attempt at =(set-buffer buf)= crashes
outright:

#+begin_example
nelisp: uncaught error: void-function: (set-buffer)
#+end_example

=point-min=/=point-max= exist but are hardcoded constants returning =1=
unconditionally, regardless of buffer state or content
(=scripts/nelisp-stdlib-prelude.el:247-250=).

** §1.7 What actually blocks first: navigation, not existence

=recipes/README.org:69= (no Magit/Org-specific enumeration exists in this
file, contrary to this doc's starting brief — corrected in §0):

#+begin_quote
=goto-char=, =re-search-forward=, =mapatoms= — void.  Buffers exist,
but buffer *navigation* does not.
#+end_quote

This matches §1.3/§1.4 precisely: object-level operations
(=generate-new-buffer=/=get-buffer=/=kill-buffer=/=buffer-live-p=) are
real in the prelude; everything that *moves through* a buffer's content
(=point=, =goto-char=, =re-search-forward=, =search-forward=) is void.
Any future Magit/Org-shaped consumer needs navigation before it needs
markers or overlays — this doc's phase order (§4) follows that, not the
brief's original, unverified framing.

* §2 Decided direction

** §2.1 Substrate of record: =nelisp-buffer.el='s model, =nelisp-text-buffer.el='s technique

| option | mechanism | verdict |
|---|---|---|
| Keep =nelisp-text-buffer.el= (0-indexed) as the sole core primitive, per Doc 33's literal text, build a new Layer 2 on top from scratch | matches the LOCKED doc exactly | *rejected as literally written* — every real consumer measured in this doc (=nelisp-buffer.el='s own markers/overlays, all four packages, Emacs itself) is 1-indexed; building a fresh Layer 2 from a 0-indexed Layer 1 means an index-shift adapter at every call site, for a primitive with zero current consumers, when a working 1-indexed alternative with real markers/overlays already exists |
| Keep the prelude's ad-hoc vector buffer as-is, patch only the disconnected =insert= | smallest possible diff | *rejected* — does not add markers, overlays, or navigation; leaves =point=/=goto-char=/=re-search-forward= void, which §1.7 shows is the actual first blocker |
| Adopt =nelisp-buffer.el='s 1-indexed, marker/overlay-complete data model as the substrate of record; port =nelisp-text-buffer.el='s byte/UTF-8 gap-buffer *technique* underneath it as an internal storage optimization | reuses the most feature-complete existing code, keeps Emacs-compatible indexing, and still gets Doc 33's real motivation (a fast gap-buffer core) — just not its 0-indexed API surface | *accepted* |

This keeps Doc 33's *intent* (§5.3: a fast primitive underneath a
compatibility layer) while dropping the one piece of its *literal text*
(0-indexing) that is incompatible with every real consumer this doc
measured, including the four already-shipped packages and Emacs's own
contract. §6.1 asks Doc 33's owner to amend the locked text to match,
rather than this doc silently overriding a LOCKED decision on its own
authority.

** §2.2 Standard-name wiring layer

The prelude's =generate-new-buffer=/=get-buffer=/=kill-buffer=/=buffer-
live-p=/=with-current-buffer=/=with-temp-buffer= stay — they are real
and correct today (§1.3) — but are repointed to allocate and read/write a
ported =nelisp-buffer= struct (§2.1) instead of the current bare vector,
closing the disconnected-=insert= bug as a side effect of using one real
representation instead of two. =point=/=goto-char=/=current-buffer=/
=set-buffer=/=insert=/=delete-region=/=buffer-substring= become thin
wrappers over =nelisp-buffer.el='s already-correct functions (=nelisp-
point=/=nelisp-goto-char=/etc., §1.1) rather than new code. =misc.el='s
three surviving stub copies (§1.4) get replaced by =(unless (fboundp
'NAME) ...)=-guarded delegates to the same real implementation, per this
codebase's own established idiom, rather than staying as a fourth
independent no-op.

** §2.3 Migration order: =add-hook= first, then navigation, then the packages

1. *Land generic =add-hook=/=run-hooks=* (already fully designed on
   =origin/feat/stdlib-hooks-map-fixnum=, commit =84950ad30=, not yet
   merged — cross-referenced with Doc 184 §1's independent finding of
   the same gap from the process/timer side). This is a hard prerequisite,
   not an optimization: §1.5 already showed =nelisp-textprop-hook.el=
   crashes at load time without it, and that package is otherwise ready
   to attach to a real =current-buffer= the moment one exists.
2. *Port =nelisp-buffer.el= to load in the standalone reader* (§2.1) —
   the buffer object model plus =point=/=goto-char=/=insert=/=delete-
   region=, no marker/overlay wiring yet.
3. *Wire the prelude's standard names to it* (§2.2), closing §1.3's
   disconnected-=insert= bug and §1.3/§1.4's void-function gaps for the
   navigation primitives §1.7 identified as the actual first blocker.
4. *=re-search-forward=/=search-forward=*, literal-then-simple-regexp
   scope, matching Doc 33 §4.2a's own reduced bar (and Doc 186's =\sC=
   groundwork, if that doc's regex work has landed by then — a soft
   dependency, not a hard one, since literal search does not need syntax
   classes at all).
5. *Markers*, ported from =nelisp-buffer.el= (already correct, §1.1) —
   this is where the "why markers matter" payoff becomes externally
   visible (a =re-search-forward= followed by =set-marker= that survives
   a subsequent =insert= earlier in the buffer).
6. *Overlays*, same source. At this point =packages/nelisp-overlay=
   (§1.5) can very likely attach with *no changes to its own logic* —
   it already calls only =(current-buffer)= plus generic overlay
   accessors under its own =nelisp-ovly-= prefix, deliberately avoiding
   =nelisp-buffer.el='s struct (§1.5) — reconciling that avoidance (reuse
   vs. keep parallel) is flagged as §6.3, not decided here.
7. *=nelisp-textprop-hook=/=-keymap=/=-display=* attach last, once (1)
   and their own =(current-buffer)= assumption (6) both hold.

§1.1 confirmed it is *not currently loaded* by the standalone build but
did not identify a specific blocking dependency the way Doc 184 traced

=cl-defstruct nelisp-overlay= to dodge an accessor-name collision. Once
§2.1 makes =nelisp-buffer.el= the substrate of record, that collision
reason may no longer apply the same way — but reconciling two overlay
implementations (which one is source of truth for a given overlay
object?) is real integration work Doc 41's original authors explicitly
chose not to do. Not resolved here; P6's cost estimate brackets both
outcomes.

** §6.4 =nelisp-stdlib-misc.el='s stub-vs-delegate transition

§2.2 proposes replacing =misc.el='s three no-op stub copies with guarded
delegates to the real implementation. Whether that edit belongs in
=misc.el= itself (keeping the file as "the fallback layer," now pointing
at real code instead of no-ops) or should instead retire those
definitions entirely in favor of the prelude's own guarded defuns is a
small naming/ownership call left to the implementer.

** §9.1 What shipped

Per §3's own P2 scope ("=current-buffer=/=set-buffer=/=with-current-
buffer=/=with-temp-buffer=/=buffer-substring=/=erase-buffer= wired to
P1's real object; =misc.el='s three stub copies (§1.4) replaced with

first time"):

- =current-buffer=, =set-buffer=, =buffer-substring=, =erase-buffer=
  are new standard-name wrappers in =scripts/nelisp-stdlib-prelude.el=,
  thin delegates onto P1's already-ported =nelisp-current-buffer=/
  =nelisp-set-buffer=/=nelisp-buffer-substring=/=nelisp-erase-buffer=
  (same threading discipline as P1's =point=/=goto-char=: only
  =nelisp--current-buffer=, never the ported file's own ambient
  =nelisp-buffer--current=). =with-current-buffer=/=with-temp-buffer=
  are unchanged -- P1 shipped both ahead of §3's original schedule, as
  part of its own "coherent lifecycle set" (top =#+STATUS2=); §3's P2
  bullet re-lists them only because §3 was drafted before P1 landed.
- =set-buffer='s error wording and =buffer-substring='s argument-order
  handling and out-of-range signal are probed against Emacs 30.1
  (§9.2), not guessed: a missing name signals =(error "No buffer named
  %s")=, a killed buffer object signals =(error "Selecting deleted
  buffer")= (distinct cases -- =get-buffer= already returns a dead
  buffer object unchanged per P1, so =set-buffer= has to check
  liveness itself), and =buffer-substring= accepts START/END in either
  order and signals =args-out-of-range= (data = buffer, START, END, in
  the caller's original unsorted order) outside [=point-min=,
  =point-max=]. The underlying =nelisp-buffer-substring= (ported
  verbatim from =src/nelisp-buffer.el=, kept byte-identical for
  =ns-gate=) does neither of those on its own, so both are handled in
  the wrapper instead of touching the ported file.
- =erase-buffer='s one known gap, disclosed rather than silently
  papered over: real Emacs widens before deleting (probed: erasing a
  narrowed buffer resets =point-min= back to 1); the ported =nelisp-
  erase-buffer= does not reset narrowing. Unreachable from this
  phase's own surface, since no standard name through P2 can SET
  narrowing (=narrow-to-region=/=widen= are still unwired) -- named
  here so a future phase that DOES wire narrowing standard names knows
  to check this, not so it goes unnoticed.
- P0 (generic =add-hook=/=run-hooks=) turned out to already be
  shipped, not by this change: =84950ad30= ("stdlib: hooks, a map.el
