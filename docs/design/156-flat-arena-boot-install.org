* 0. Purpose

The flat-arena cold-loader (scripts/nelisp-flat-arena-probe.el, boot-wiring 5–14,
merged 439ac529) proves the dump→file→load→relocate→root-recovery MECHANISM, but
only as a READ-ONLY VERIFY (loads into a scratch =alloc-bytes= buffer; "live
runtime untouched").  The remaining work to make it usable (fast cold-load of a
loaded heap, ~9.2x vs .repl replay) is the production INSTALL: a fresh process
that loads an image into its REAL arena, relocates against the real base, installs
the EvalCtx roots, and skips the normal bootstrap.  This doc fully scopes that.

Motivation: the full nemacs bundle (=./bin/nemacs --driver=nelisp=, .repl replay)
cold-loads in 30–66 min and is OOM-prone (~11–15 GB RSS); package-breadth driving
needs the bundle (cl-lib/seq/pcase/macroexp/...).  A flat-arena image of the
loaded heap would load fast and unblock breadth — IF a one-time dump can be
created (the dump still needs ONE slow load; vendor-core subset is lighter).

* 2. Image format (=bf_arena_dump_image_to_file=, header 64 B)

| off | field | source |
|-----+-------+--------|
| 0  | magic 1179407692 ("FLAT") | literal |
| 8  | slen (chunk-0 region bytes) | cursor − 1024 |
| 16 | isz (interned region bytes, 8-aligned) | abase+832 .. abase+840 |
| 24 | tlen (relocation-table entries) | nl_fa_roots + bf_arena_mr_chunks |
| 32 | gbox image-offset (globals root) | nl_img_off of env+8 |
| 40 | fbox image-offset (frames root)  | nl_img_off of env+40 |
| 48 | ubox image-offset (unbound root) | nl_img_off of env+72 |
| 56 | intern-region base (split-loader name-ptr fix) | abase-relative |

File body = [header][reloc table: tlen × u64][chunk-0 region: slen][interned
region: isz].  Reloc entry F: =image[F] += newbase= (chunk-0-relative pointers).
The interned region's open-addressing name-buffer ptrs (slot+8) live INSIDE the
interned region, so =nl_fa_field= (chunk-0-only) does NOT table them; they retain
absolute OLD pointers and must be fixed by base-delta on load (see the dump
comment + =bf_arena_load_split_verify=).

EvalCtx (env) layout (gdb-verified, from the dump + line ~2682):
- env reached via published safepoint ctx: =env = ptr-read-u64 (ctx+64)= when
  =ptr-read-u64 ctx 0 != 0=.
- globals box @ env+8, frames box @ env+40, unbound box @ env+72.

* 3. The remaining work: production INSTALL

** 3.1 New builtin =bf_arena_boot_install (args out)= (adapt =bf_arena_boot_load_verify=)

=bf_arena_boot_load_verify= already: opens file, reads header, reads table+image
into a SCRATCH =alloc-bytes img=, applies the reloc table (=image[f] += img=),
reconstructs a rootslot (tag 12, ptr = img+goff), verifies it is a valid Record.

INSTALL差分:
1. Load the chunk-0 region into the REAL arena chunk-0 data area (=sstart=, i.e.
   =arena_base + 0x400=) instead of a scratch buffer; load the interned region
   into the real interned region (=ib=).
2. Relocate against the REAL base delta (=newbase = sstart_new − slen_origin_base=),
   not the scratch base.  Apply the table AND the interned-region base-delta fix
   (mirror =bf_arena_load_split_verify=).
3. Seed arena chunk metadata (cursor/used/chunk-count at offsets 0x2c0.., see the
   =nelisp-standalone--arena-chunk-*-offset= consts) so the arena is well-formed
   for subsequent allocation (the image cursor = slen+1024).
4. INSTALL the EvalCtx roots: set env+8 = sstart+goff (globals Record),
   env+40 = sstart+foff, env+72 = sstart+uoff.  (Where -1 = immediate, rebuild
   inline per =bf_arena_image_root_verify=.)

** 3.2 New driver mode =exec-arena-image IMAGE FORM...=

In =nelisp-standalone--reader-driver-source= (line ~9708):
- Add matcher =nl_cstr_eq_exec_arena_image= for ="exec-arena-image"= (alongside
  the existing =nl_cstr_eq_exec_runtime_image= etc., ~lines 155–162 / 9866–9868).
- Add it to the mode-dispatch chains (3 sites: ~310–316, ~10021–10055,
  ~10689–10693).
- Handler: =nl_arena_init= (reserve real arena) → =bf_arena_boot_install(IMAGE)=
  (loads heap + installs env roots) → SKIP the normal bootstrap/prelude load (the
  image already contains the prelude + everything) → eval FORM through the normal
  eval path with the installed env → print.

Key invariant: the baked prelude must NOT be re-installed on top of the image
(the image already has it).  The handler replaces the boot, it does not augment.

* 5. Risks / caveats

- The install writes the REAL arena before the eval loop runs — a relocation or
  metadata-seed error → SIGSEGV on the first variable lookup.  Debug with the
  scratch value-survival (step 1) FIRST to isolate relocation correctness from
  install correctness.
- Interned-region name-ptr base-delta (slot+8) is the most error-prone part
  (=bf_arena_load_split_verify= is the reference).
- This is the spike owner's active area (boot-wiring 5–14); coordinate to avoid
  duplicating the install they may already be drafting.
- The one-time dump still needs ONE full load; the flat-arena win is on RELOAD,
  not the first dump-creation.  The host OOM on the first load is orthogonal and
  unsolved (vendor-core subset mitigates by being lighter).
- *Cold-load + setf-on-struct-accessor edge* (2026-06-23): over a cold-loaded
  image, =(setf (STRUCT-SLOT r) v)= aborts in the setf-place macro expander
  (=(setf x …)=, =(setf (car l) …)=, =push= all work; the struct-accessor place is
  the only failure, fresh OR pre-dump record).  =(aset r i v)= and
  =nelisp--record-set= work directly over cold-load, so it is the gv/plist
  setf-expander survival, not record mutation.  READING cold-loaded structs
  (predicate + accessor) works, and normal-boot struct setf works fully — so
  breadth driving (read + call) is unaffected.  Likely a pre-existing cold-load
  limitation for plist-based macro expanders, surfaced only now that struct

* 7. Increments MC-1 / MC-2 / 3 (multi-chunk cold-load, 2026-07-04)

§4 Item 4 (2026-06-23) identified the single-chunk cold-loader's structural
ceiling: the flat-arena DUMP of anything past a single reserved chunk-0
aborted regardless of =NELISP_LINUX_ARENA_SIZE= (tried up to 4 GiB), because
both the relocation-table scratch (dump side) and the fixed
single-destination load target (install side) assumed a single chunk.  That
was "moot" for the full nemacs bundle only because
=(load "build/nemacs-bootstrap.el")= already makes that breadth usable in
~12 s without a cold-load image at all; it remained a real ceiling for
cold-loading anything the standalone reader itself builds past one chunk —
e.g. the ~60-file Org vendor chain used to drive/probe Org support, which
coalesces past 600 MiB across 7 chunks.  Branch
=feat/multi-chunk-cold-load= (worktree =nelisp.wt-coldload=) lifts this
ceiling in two increments, then Increment 3 built a reproducible
verification harness around them.

** MC-1: multi-chunk streaming dump (commit 5eb0fd81)

Root cause: =bf_arena_dump_image_stream= placed its relocation-table scratch
(the per-pointer-field offset table built during the in-place swizzle pass)
in whatever free tail happened to exist past the live bump cursor — chunk-0's
own mmap tail for a single-chunk heap, or the 64 MiB interned-symbol region's
unused tail for a multi-chunk heap.  Both placements are bounded by leftover
mmap space, not by the actual heap size, so a large heap overruns them and
writes relocation-table entries past the mapped region, causing a SIGSEGV.
This was never exercised at chunk-count > 1 before: a 7-chunk, ~602.5 MiB
heap (94% of a 640 MiB reservation, produced by loading the ~60-file Org
vendor chain) crashed both the streaming path (before this fix) and the
older =bf_arena_dump_image_to_file= (which still crashes, exit 139 — out of
scope for this increment).

Fix (=scripts/nelisp-standalone-build.el= ~3810-3886,
=bf_arena_dump_image_stream=): allocate a DEDICATED scratch mmap via
=nl_os_alloc_chunk= (the same platform-abstracted raw mmap
=nl_chunk_alloc_new= already uses for heap growth) instead of reusing
leftover space.  It is not linked into the chunk chain, so it stays
invisible to =nl_mc_write_chunks=/=nl_mc_total= and is never itself dumped
as heap data.  Size is a mathematical upper bound: at most one relocation
entry per 8-byte pointer-field word across the coalesced region.

** MC-2: multi-chunk boot-INSTALL (commit 1f486838)

Makes the boot-time cold-load INSTALL path (=nl_cold_load_arena= /
=nl_cold_overwrite_globals=) work with the multi-chunk coalesced images MC-1's
streaming dump now produces.  Previously the loader always targeted a single
fixed destination (=ds = base+1024= inside the fresh process's default
256 MiB chunk-0), which cannot hold a multi-hundred-MiB coalesced heap.

Destination strategy: read the image header first (header+8 = the coalesced
=slen=, format unchanged since MC-1) to compute the exact bytes needed —
1024-byte control block + =slen= + the relocation table (=tlen= * 8 bytes) +
8 MiB slack, 64 KiB aligned.  If that exceeds the current chunk-0's
reservation (=nl_cold_grow_chunk0=), allocate ONE new contiguous mmap via
=nl_os_alloc_chunk= sized to fit, point the driver-owned =nl_arena_base= bss
slot at it, and reinitialize its control block + chunk-0 descriptor via
=nl_cold_realloc_chunk0= — reusing the existing
=nelisp-standalone--arena-init-metadata-forms-dynamic= generator (the same
one =nl_arena_init= uses) with the new base/size as RUNTIME symbols instead
of a literal.  The interned-region pointer pair (+832/+840) is copied across
the swap; the OLD default chunk-0 mmap is deliberately left un-munmap'd (a
harmless orphaned mapping).  When the image already fits, the grow path is
skipped and the loader is byte-for-byte the original single-destination
code.

Also adds a =--cold-load-from PATH= CLI flag so callers/tests can cold-load
an explicit image without clobbering the fixed
=/tmp/nelisp-cold-image.bin= marker file that existed at the time (2026-09-28:
that default marker file is REMOVED — see the SECURITY FIX status entry near
the top of this doc; =--cold-load-from PATH= is now the ONLY way to
cold-load).  This required moving argv parsing earlier in =driver='s =let*=,
ahead of the cold-load gate, so the gate can recognize the flag before
deciding whether/what to cold-load.  =PATH= consumes the arg2 slot, so only
arg3 remains free for =--no-prompt=/=--no-print= (one fewer slot than plain
=--repl=); the branch otherwise runs the identical REPL-loop body.

Buffer-level smoke (=(with-temp-buffer (org-mode) ...)=) was also
attempted per this task's "report what's feasible" allowance, and is
reported honestly as NOT working cleanly: =(with-temp-buffer major-mode)=
already returns =nil= (even with no mode call at all, and even after an
explicit =(fundamental-mode)=), while =(default-value 'major-mode)=
correctly returns =fundamental-mode= — so per-buffer =major-mode= tracking

to discard the =with-temp-buffer= body's subsequent return value (no
stderr output, no non-zero exit — silent, not a crash).  This is a
buffer/major-mode substrate gap orthogonal to the =define-derived-mode=
bridge fix and to MC-1/MC-2 cold-load faithfulness (both of which are
about whether =org-mode= is =fboundp=/=commandp=-true and whether cold-load
reproduces that faithfully, which it does); it is left unchased here as
out of scope, consistent with this doc's existing practice of not chasing
gaps beyond the caveat under investigation.
