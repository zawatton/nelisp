#+AUTHOR: NeLisp
#+STATUS: DRAFT (strategy revised 2026-09-25; original measurements 2026-09-21)
#+STATUS2: Historical measurements in §1 are evidence from 2026-09-21. The revised P5 strategy is proposed; partial proofs do not mean P5 is complete.

* §0 TL;DR

As of 2026-09-21, the standalone interpreted Lisp functions outside compiled
DSL primitives; one interpreted step cost 5-15 µs. Three candidate ways out
were measured then. These are historical measurements, not current benchmarks:

| path | measured | verdict |
|---|---|---|
| keep interpreting, make the evaluator cheaper (segment H) | empty loop -41%, standard loop -31%, ~130 lines | real, but a constant factor |
| run the shipped bytecode VM (=src/nelisp-bytecode.el=, Doc 08, SHIPPED 2026-04-24) on the standalone | same loop: interpreter 0.325 s, **VM 349.7 s** — 1077x *slower*, same answer | unusable as-is |
| the shipped JIT (=packages/nelisp-jit=) | translates NeLisp to *host* Elisp and calls the *host* =byte-compile= | host-bound by design, cannot run here |

The VM result is the important one, and it is not a defect in the VM: bcl is
itself written in interpreted Lisp, so every bytecode instruction costs several
interpreted steps.  On the host it rides Emacs's byte-compiled runtime, which
is why Doc 08 measured ~1.2x there and pivoted to a JIT.

So the conclusion is structural: **the execution layer itself has to be
compiled**.  Either the VM's dispatch loop becomes native code, or the
standalone gets a JIT that emits machine code.  No arrangement of interpreted
Lisp fixes this.

What this document proposes:

1. **Make the byte-code execution layer native** (§3.1).  Keep GNU Emacs's own
   byte compiler — ordinary Lisp, already vendored — as the compiler, and write
   only the dispatch loop and its opcodes in the build DSL, where each opcode
   delegates to a primitive that already exists.  Bounded work, and it is the
   same shape as the DSL work we already do.
2. **Then a standalone JIT** (§3.2), reusing the AOT chain that builds the
   runtime (=nelisp-asm-x86_64-*=, =nelisp-elf-write-binary=).  That chain
   today accepts only the low-level DSL, so this step is where the real
   compiler work lives: tagged values, GC roots, closures, dynamic binding,
   non-local exit.
3. **DSL primitives only where the DSL is unavoidable** (§2): the 144 that
   touch representation ordinary Lisp cannot reach.  The other 126 are ordinary
   Lisp and must not be hand-written in the DSL — they get fast for free once
   (1) lands.

** §1.2 Why interpreting is the whole cost

Segment G3 established this the hard way.  =string-match= was assumed to
recompile its pattern on every call; it does not — the 1024-entry LRU cache
has been there since =3b3215678= and hits 499/500.  With the cache warm a
single cached literal match still performs **~7,800 allocations**, and a
character class **~18,900**, none of which scale with the subject's length.
They scale with the number of interpreted forms evaluated.  The regexp engine
was never the problem; the evaluator is.

Segment G1 confirmed the other side of it: making eight list functions DSL
primitives moved them 5-35x, and left everything that calls them untouched.

** §1.3 What the existing AOT compiler does and does not give us

=lisp/nelisp-aot-compiler.el= (21,189 lines) compiles a Lisp form to a
static-linked ELF64 executable, and the runtime itself is built through that
chain.  It is *not* a compiler for ordinary Elisp: its input is the same
restricted DSL the runtime is written in.  Its own test feeds it

: (seq (defun f () (let ((found 0) (pass 0)) (while (< pass 2) (setq pass (+ pass 1))) …)) (exit (f)))

— machine integers, =exit= as the program's end, and a free symbol is a
=nelisp-aot-compiler-error=.  No cons cells, no symbols as values, no strings
as Lisp objects, no GC, no closures, no dynamic binding, no signals.  "Point
the compiler we already have at user Lisp" is therefore not available.

* §2 The split: what must be a DSL primitive

A function must be written in the build DSL if and only if it **creates or
observes representation that ordinary Lisp cannot reach** — buffer text, OS
handles, raw bytes, hash-table internals, machine arithmetic, the reader and
printer.  Everything else is ordinary Lisp that happens to be slow because we
interpret it, and belongs in §3, not in the DSL.  Writing it in the DSL means
writing manual =alloc-bytes= / =ptr-read-u64= / =nl_gc_free_block= code: two
memory defects surfaced in segment G1 alone, one of them a SIGSEGV on
=(append '(1 2 . 3) nil)=.

Applying that criterion to the 270 (=tools/nelisp-c-primitive-classification.txt=):

| group | count | examples |
|---|---|---|
| buffer and text | 47 | =insert=, =goto-char=, =buffer-substring=, =forward-line=, =point-min= |
| file system | 22 | =insert-file-contents=, =file-attributes=, =directory-files= |
| process and OS | 18 | =call-process=, =make-process=, =accept-process-output= |
| bytes, codecs, time | 13 | =base64-encode-string=, =encode-coding-string=, =format-time-string= |
| machine arithmetic | 12 | =expt=, =log=, =exp=, =ash=, =logand= |
| reader and printer | 11 | =read=, =prin1-to-string=, =format= |
| vector and marker | 10 | =aref=, =aset=, =vconcat=, =copy-marker= |
| hash table | 6 | =gethash=, =puthash=, =maphash= |
| keymap | 5 | =define-key=, =lookup-key= |

The 126 are the proof that the DSL is the wrong tool for most of the list: each
is expressible in ordinary Elisp over values the runtime already has, and each
would be fast for free once ordinary Lisp stops being interpreted.

* §3 The execution model

** §3.1 Step one: a native byte-code execution layer

The compiler half is already written and maintained by somebody else.  GNU
Emacs's byte compiler is ordinary Lisp — =bytecomp.el= (256 KB), =byte-opt.el=
(136 KB), =cconv.el= (43 KB), =macroexp.el= (38 KB) — all four already vendored
in =nelisp-emacs-lib/vendor/emacs-lisp/=, and segment I showed the standalone
loads vendored Emacs Lisp once eight load-time names exist.

The execution half is what the standalone lacks: =make-byte-code=, =byte-code=
and =fetch-bytecode= are void today (=byte-code-function-p= exists and answers
nil).  Writing it in the DSL is tractable because the instruction set is fixed
and most opcodes are one call to a primitive we already have:

- stack: =stack-ref=, =dup=, =discard=, =constant=
- calls: =call0=…=call6=, =callN=
- control: =goto=, =goto-if-nil=, =goto-if-not-nil=, =goto-if-nil-else-pop=, =return=
- binding: =varref=, =varset=, =varbind=, =unbind=
- list and sequence: =car=, =cdr=, =cons=, =list1=…=list4=, =length=, =aref=, =aset=, =nth=, =memq=
- arithmetic and predicates: =plus=, =diff=, =mult=, =quo=, =max=, =min=, =eq=, =equal=, =gtr=, =lss=
- non-local exit: =pushcatch=, =pushconditioncase=, =unwind-protect=

The existing bcl (=src/nelisp-bytecode.el=, 2,293 lines, 135 tests) stays as
the semantic reference it was kept for: the native loop must agree with it, and
bcl is how we test that cheaply on the host.

Placement, in the order the phases take it: compile the prelude at build time
(the stdlib stops being interpreted without any runtime compiler), then compile
vendored and user =.el= at load time.

** §3.2 Step two: a JIT for the standalone

A byte-code VM, even a native one, is roughly Emacs's byte-code performance —
50-100x its own interpreter, not native speed.  Closing the rest needs machine
code per function, and the chain that emits machine code already exists here:
=nelisp-asm-x86_64-*= encodes instructions, =nelisp-elf-write-binary= writes the
image, and =lisp/nelisp-aot-compiler.el= (21,189 lines) drives both.  The
runtime itself is built through it.

What that chain does *not* accept is ordinary Elisp.  Its own test feeds it

: (seq (defun f () (let ((found 0) (pass 0)) (while (< pass 2) (setq pass (+ pass 1))) …)) (exit (f)))

— machine integers, =exit= as the program's end, a free symbol is an error.  No
cons cells, no symbols as values, no GC, no closures, no dynamic binding, no
signals.  A standalone JIT is therefore the work of connecting that chain to
tagged values and the runtime's object model. The original sequencing and
limitations above describe the 2026-09-21 proposal; the revised staged P5
design below defines the current proposed path. §0's measurements remain its
historical motivation, not a claim that a VM or JIT has since been built or
benchmarked.

* §4 Phases and exit criteria

Each phase states what must be true to call it done. P1-P4 retain their listed
exit criteria. Bounded P5 infrastructure and vendor investigation may proceed
in parallel with unfinished P1-P4 when dependencies are explicit; this does
not mark a predecessor complete. P1-P4 measurements remain required to set
P5's quantitative performance target and final performance acceptance.

The first census intersected name lists out of the build script, which counted

** P1 — the native byte-code execution layer

Write the dispatch loop and opcodes in the build DSL: =make-byte-code=,
=byte-code=, =fetch-bytecode=, and a decoder that knows each opcode's operand
width.  Order the work by an opcode histogram over the vendored corpus rather
than by opcode number.  bcl (=src/nelisp-bytecode.el=) is the semantic
reference: every opcode's behaviour is checked against it on the host.
*Exit:* a byte-code object produced by *host* Emacs and embedded in a test runs
on the standalone and returns what Emacs returns, for at least 200 functions
drawn from the vendored files; the same loop that costs 0.325 s interpreted and
349.7 s under bcl runs at or below 0.05 s; every opcode the suite exercises is
implemented or signals explicitly.

** P2 — compile the prelude at build time

The prelude is baked in as source and interpreted from startup.  Byte-compile
its =defun=s during =make standalone-reader= and ship byte-code, keeping the
source path behind a flag for debugging.
*Exit:* the ~126 ordinary-Lisp primitives of §2 are byte-code, not source; the
=nth=-class functions are within 3x of their DSL-native counterparts; the
agent-host census does not regress; =make test= is at its one known flake.

** P3 — load-time compilation

=(require 'rx)= and friends compile on load and cache the result.  Needs
segment I's vendored tree and =bytecomp.el= loading on the standalone.
*Exit:* loading the vendored corpus costs no more than today plus one
amortised compile, and the loaded functions execute as byte-code.

** P4 — DSL primitives, by measured need only

Work the §2 DSL list in cost × call-site order, starting with buffer and text
(47 functions: =insert= 5.2 ms, =goto-char= 7.7 ms, =buffer-substring= 6.2 ms,
=forward-line= 11.1 ms per call today).
*Exit:* each matches Emacs 31.1 on a probe table including edge cases, and its
per-call cost is within 5x of Emacs's.

** P5 — the standalone JIT

P5 changes direction from reconstructing a Lisp expression for each function
and temporarily compiling source with AOT. Its proposed baseline is a native
JIT over verified byte-code, using a shared value/ownership contract and an
execution frame. The frame carries arguments, value stack, GC roots, binding
depth, and handler/unwind state. Preserve closures, dynamic binding,
=unwind-protect=, =condition-case=, and non-local exits. Reuse the existing
native generator, loader, and VM runtime helpers; do not port GNU Emacs's C
implementation wholesale.

Stage the work in this order:

1. Define the shared frame and native entry ABI, with precise ownership and
   root visibility rules.
2. Add one common call gateway for C primitives, Lisp functions, and byte-code
   functions/closures. Inspect the actual =nl_apply_function= contracts before
   fixing the gateway ABI.
3. Build a verified control-flow-graph IR with basic blocks and stack slots.
4. Generate native code directly from that IR through the existing native
   generator.
5. Add optimizations only after the baseline is measured.

*P5 compilation/execution separation — opt-in staged path and boundary hook implemented*

The Lisp module now has an opt-in deferred-preparation path. With
=nelisp-bytecode-jit--deferred-preparation-enabled= non-nil, dispatch queues
requests and continues in the VM; preparation is bounded and deduplicated,
failed attempts are memoized by byte-code/runtime/ABI identity, and a candidate
is validated before its ready handle is published. The flag defaults to nil,
so the normal runtime still uses its existing synchronous preparation behavior.
This staged path does not yet change the default dispatch policy.

The automatic service point is after a successful outermost top-level
evaluation returns, while its recorded GC context remains live. Requests
raised during nested evaluation or =load= must stay queued until that outermost
boundary. The drain's dynamic busy guards prevent compilation-triggered
evaluation from re-entering preparation. The integrated driver hook remains
opt-in and preserves the user result through callback GC. Five standalone
smoke cases pass, with a no-callback candidate failing the same test; these
cases use a stub service to verify boundary, GC, and error contracts. A
separate two-action standalone probe uses ordinary =funcall=: the first call
queues one request and executes in the VM, the boundary compiles it, and the
second call returns nil with one native call, one compiled function, and an
empty queue. This verifies the opt-in scheduler with the transitional backend,
not the complete P5 JIT or GNU artifact registration.
Later background preparation is optional and is not part of this initial
design.

*Artifact compatibility target.* Migrate the specification toward genuine GNU
Emacs =.eln= artifacts; acceptance requires the same GNU Emacs 31.1-produced
file to load and execute in both Emacs and standalone, without recompiling or
converting its on-disk contents. This binary-compatibility scope was explicitly
confirmed by the user. The current =.neln= emitter and loader are
transitional private-format evidence and do not meet this target. A generated
constant function returned 17 as GNU's tagged immediate =0x46=; its leaf
needs no object relocation. The 99-byte =top_level_run= takes a compilation
unit and calls =comp--register-subr= through GNU runtime relocation state to
register the callable native subr. Loading therefore requires the GNU
ABI/version and relocation contract, correct entry registration, and matching
=Lisp_Object= tags. General results also need compatible heap identity, GC
roots, and object relocations; matching ELF format or architecture alone is
insufficient. This target is not yet implemented; never stub the registration
path to claim compatibility.

Keep the verified IR independent of either physical value representation.
GNU-compatible artifact entries and GNU runtime calls use the producer's
64-bit =Lisp_Object= ABI; NeLisp's existing 32-byte Sexp slots are an internal
runtime representation, not an interchangeable native ABI. The NeLisp side
must adapt these representations while preserving identity, mutations, roots,
and non-local exits. Sharing the VM frame contract means sharing those
semantics and ownership rules, not passing Sexp-slot addresses where GNU
expects Lisp words. Emitted artifacts must not require NeLisp-only external
symbols that GNU Emacs cannot resolve. The production JIT emitter must also
produce the agreed =.eln= format; consuming GNU-produced artifacts while
continuing to publish private =.neln= JIT output is not the requested migration.

The integrated =nelisp-eln-emitter= now emits a genuine GNU-compatible
=ET_DYN= unit from a zero-argument constant-integer AOT IR function, using
the existing Lisp ELF object writer and =ld -shared=. The production emission
path does not invoke the Host compiler. Its initial profile is explicitly
pinned to GNU 31.1, x86-64 Linux, ABI hash =ba35c031= and registration slot
1030. Mutable relocation cells have disjoint storage; =top_level_run= calls
the real registration entry through the runtime table. Root reproduced the
standalone-to-GNU smoke on candidate =6d05ca62...=: artifact =75b88728...=
loads as a native subr, has arity =(0 . 0)=, returns 17, rejects excess
arguments, and keeps the same hash after execution. A corrupted ABI hash is
rejected. General IR lowering and NeLisp-side registration of the same unit
remain required.

Deferred JIT preparation now selects the GNU emitter for admitted zero-argument
nonnegative integer literal IR, publishes a managed NativeSubr handle, and
dispatches through that callable. Other IR still uses the transitional private
backend or VM. Root validation on immutable =0f5c83d8...= with the integrated
JIT source returns 17 cold and warm; the cold call queues preparation and the
warm call increments =native-calls= to 1 with a retained =.eln= artifact.
The existing JIT tests plus focused adapter tests pass 58/58. Failed emission
preserves the primary error and retains cleanup work for retry; invalidation
defers module close and artifact deletion until callable leases permit it.
This connects the real JIT dispatch for the admitted subset, not full GNU
registration or complete removal of the private emitter.

The integrated =test/nelisp-eln-same-artifact-smoke.sh= closes the separate
fixture gap: standalone emits one unit, GNU registers and executes it, and
NeLisp calls that exact file through its managed NativeSubr API three times.
Root reproduced this on =22dcae1a...= with the corrected Lisp FFI source;

The emitter also lowers a one-argument AOT =ref= body to a GNU ABI identity
leaf (=mov rax,rdi; ret=), with truthful =(1 . 1)= registration metadata.
Host ERT passes 6/6, including fixnum boundaries, cons/string =eq= identity,
wrong arity, unsupported IR, and the existing constant/profile checks.
Standalone emission followed by GNU registration passes on =0f5c83d8...=
with artifact =c007655a...=. NeLisp's managed entry admission still accepts

The existing =nl-ffi= pure-Elisp ELF loader already works in the static
standalone executable. =test/nelisp-eln-leaf-smoke.sh= uses public

The artifact ABI hash is checked against its producer, not asserted compatible
with NeLisp. The smoke does not invoke =top_level_run= or register GNU native

=nl-ffi-loader-open= now accepts an optional per-load runtime function
provider. Local definitions take precedence; provider entries resolve only
undefined function imports in the root object, never dependency imports.
The standalone smoke verifies FUNC/JUMP_SLOT and NOTYPE/JUMP_SLOT calls,
rejects ambiguous NOTYPE/GLOB_DAT imports, and checks provider isolation and
recovery after a failed load. This does not bypass =DT_NEEDED= resolution or

handle lifetime. This is relocation infrastructure, not an implementation
of GNU handlers, =setjmp=, or native subroutine registration.

=test/nelisp-eln-callback-smoke.sh= additionally compiles and runs the same
GNU =random(1)= wrapper in both runtimes. It checks the emitted tail-call's
relocation slot against the producer's subroutine index, then routes that

calls return zero, and context restoration is checked. A separate arity
failure preserves the output sentinel and the runtime signal. The smoke
requires clean stderr, an exact marker, and unchanged artifact/binary hashes.
The C fixture remains an independent control, not a production core bridge.
Its error status is
out of band and is not GNU non-local exception propagation. It does not run
=top_level_run= or establish general native subroutine registration.

The native DSL implementation in =lisp/nelisp-cc-eln-callback.el= now passes
the separate =test/nelisp-eln-dsl-callback-smoke.sh= on the same GNU artifact.
It uses caller-pinned slots and the shared gateway, with eight bounded LIFO
contexts owned by one thread. The smoke covers nested entry with GC,
overflow, invalid pop order, foreign-owner rejection, non-fixnum input, and
the gateway's wrong-arity signal without overwriting the result slot.
Bridge-list equality is checked before building; a deliberately reordered

of band. It does not implement GNU non-local exits or a general heap-object
ABI, and its passing test does not establish those contracts.

Registration also requires a wider incoming signature: GNU 31.1
=comp--register-subr= receives seven Lisp words (name, C name, minimum and
maximum arity, type, rest metadata, compilation unit). SysV passes the seventh
word on the stack. The integrated =nelisp-cc-eln-callback7= adapter now
preserves all seven raw words and uses independent GC root slots for each
activation. Root validation on immutable candidate =9494692a...= passes
distinct arguments, signed fixnum boundary results, nested entry, GC with

A C caller measures equal root marks immediately around each callback.
Intermediate Lisp-side samples differ by 32 bytes at different evaluator
boundaries; that separate observation remains unattributed. This proves the

The adapter still reports errors out of band.

The integrated =nelisp_eln_callback7_entry_word= sibling accepts a checked
dotted pair of unsigned 32-bit halves and returns the exact 64-bit word.
The original fixnum-return entry is unchanged. Candidate =c43801e0...=

This supplies the return transport for a GNU subr view, not object decoding
or the complete registration implementation.

For the admitted emitter entry, =top_level_run= passes the compilation-unit
word unchanged to slot 1030; it does not dereference private unit fields.
The NeLisp registration callback must authenticate that word and perform the
required operations through its real loader owner. GNU's own =make_subr=
dereferences its own unit handle; reproducing that operation does not require
identical private runtime storage. Keep actual =eq=/=equal= registration
tables in traced NeLisp owner state, and reject entries that expose or access
unmaterialized GNU fields before execution. GNU hash-table memory mirrors are
therefore not a prerequisite for this single-registration path. This is a
restricted representation adapter, not permission to replace observable
metadata with fabricated values or to claim arbitrary =.eln= support.

The integrated =nelisp-eln-registration-objects= owns persistent unit views
and temporary subr views, authenticates reverse decoding, caches subr identity
within an activation, and closes the loader before freeing persistent unit
storage. Constructor cleanup retains failed releases without masking the
primary error; publication allocates its lists before exposing an entry.
Root reproduced its smoke on =c43801e0...= using the GNU-produced
=nelisp-eln-symbol-info-byte-fixture.eln=, with empty stderr. This tests the
object/ownership layer, not =top_level_run= registration.

The integrated =nelisp-eln-registration-vectors= supplies flat docs/data
vectors with real GNU headers and slot words. Its focused standalone checks
cover layout, mutation rejection, child activation leases, and retryable
cleanup. Nested unsupported objects and cross-unit reuse of the same source
vector are rejected before allocation; general shared vector support is not
claimed. These components must now be connected through the existing
same-artifact runner rather than a new validation framework.

The incoming-call bridge must follow GNU's native exception protocol as well
as its calling convention. In GNU 31.1 =src/comp.c=,
=emit_limple_push_handler= calls =push_handler= through the runtime table,
takes the address of the returned handler's jump buffer, and calls the
imported =setjmp= variant directly. A nonzero return selects the handler
block. Returning an error sentinel or nil from a NeLisp callback would let
the GNU caller continue and is not compatible error propagation. Before
admitting general native functions, implement the matching handler layout,
non-local transfer, binding/root cleanup, and reentry ownership. A successful
scalar callback fixture is evidence for the calling convention only.
Object conversion must also preserve identity and visible mutations across
native entry, callbacks, and return; per-call copies without a traced lifetime
and identity contract do not satisfy the shared-artifact target.

Raw native buffers need an explicit lifetime separate from Lisp roots.
The loader regression exposed a managed C-string allocation whose integer
address did not retain its block: the packed header reported FREE before
=openat=, and the kernel received a free-list pointer instead of the path.
=packages/nl-ffi/src/nl-ffi-memory.el= provides caller-owned anonymous mappings,
address access, and explicit release. Its standalone tests cover GC retention,
normal and exceptional cleanup, mapping failures, and unsupported platforms.
Loader call sites must bracket temporary owners with =unwind-protect=.
External memory is not scanned for Lisp references; future relocation tables
still require separate traced owners for every referenced Lisp object.

=lisp/nelisp-eln-metadata.el= now validates root-owned serialized blobs,
producer hash, lengths, relocation storage capacities, and reader identity
semantics before exposing metadata. Host tests cover Unicode, circular data,
uninterned symbols, and the unique =#$= placeholder used by GNU's loader.
The native lexer/parser now carries a distinct =#$= token and caller-supplied
reader context; the interpreted fallback follows the same dynamic binding.
The isolated =c5161310...= candidate passes the genuine GNU metadata fixture
that the earlier candidate rejected. Mixed circular, shared, and uninterned
objects preserve their identities alongside =#$=. This proves the tested
metadata path, not native function registration. Property preservation for
serialized strings is still a runtime requirement.

Canonical symbol-name identity now has a collector-visible sidecar. The
isolated =15389bac...= candidate preserves the input name of =make-symbol=
and a fresh =intern=, keeps an existing interned name on subsequent hits,
and retains names through GC and table growth. The same focused smoke passes
on Host Emacs; the previous =6d8f5e1b...= candidate fails its first input-name
identity assertion. Mutation and printing of live names are covered. This
does not establish interner lookup parity after mutating an interned name,
global =unintern=, or the private membership predicate's negative branch.

Persistent compilation-unit ownership cannot use the existing exclusive,
temporary native pin frame. A module registry must retain canonical Lisp
values and identity mappings for its external GNU-layout views, with mutation
synchronization at native/callback boundaries and explicit mapping lifetime.
Even the constant-17 artifact's =top_level_run= requires real symbol, string,

* §5 Risks, and what this document does not claim

- **A VM is not native speed.**  The 2026-09-21 rationale estimated Emacs's
  byte-code at roughly 50-100x its own interpreter. This is historical context,
  not a current P5 speed target; quantitative acceptance awaits P1-P4 data.
- **The VM's semantics are the dangerous part.**  Dynamic binding,
  =unwind-protect= and =condition-case= unwind through the VM's stack.  Getting
  those wrong is silent breakage, not a crash, which is why P1's exit criterion
  is a 200-function differential against host Emacs and bcl.
- **bcl stays.**  It is the semantic reference and 135 tests already pin it.  It
  is not the performance path on the standalone and this document does not try
  to make it one.
- **Vendoring is not a speed measure.**  Segment I replaced hand-written subsets
  with GNU Emacs's own files; those files are still interpreted.  Both efforts
  are needed and they are independent.
- **The 1099 absent C primitives are out of scope.**  Most are X11, fonts and
  terminal handling that a headless runtime has no use for.
- **This document was nearly wrong.**  Its first draft proposed writing a
  byte-code VM from scratch, without checking that Doc 08 had shipped one in
  April.  The check that found it — grep the tree before designing — is the same
  one segment F skipped when it hand-wrote an =rx= that was already vendored.
