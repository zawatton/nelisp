* §0 TL;DR

=nelisp build= runs the AOT compiler and linker *as a host Emacs process*
(=tools/nelisp-project.py:676-678=), behind an unconditional
=shutil.which= guard at =:651-653=.  Doc 204 P5 established that the
syntax layer is not what blocks it.  This document establishes what does.

The headline is that the 32,485-line builder is *not* the problem.  Loaded
on =target/nelisp= it reads completely and both entry points become
=fboundp= — the only thing in its way was =load-path=.  What blocks the
build is seven specific gaps, measured one at a time by running the real
builder and reading the error:

| # | gap | kind | size |
|---+-----+------+------|
| 1 | =scripts/= missing from =load-path= | configuration | one entry |
| 2 | eight standard names unbridged | bridge | 8 forms, every internal already exists |
| 3 | =forward-comment= does not skip newlines | one predicate | one clause |
| 4 | =utf-8-unix= rejected by the coding accept-list | name list | 4 files, must move together |
| 5 | =max-lisp-eval-depth= unbound | *NOT A GAP* | measured: real builds never reach the ceiling |
| 6 | =file-expand-wildcards= absent | rewrite | 1 call site |
| 7 | =secure-hash= absent | *design decision* | see §1.7 — the pure-elisp answer costs ~5.6 hours |

Six of the seven are small and mechanical.  The seventh is not, and it is
the reason this document exists rather than a patch: the runtime has no
message-digest primitive at all, the pure-Elisp implementation in
=packages/nelisp-secure-hash= is byte-correct but runs at ~6.3 ms/byte,
and the builder hashes 3,187,974 bytes before it compiles anything.

The control that makes all of this legible: *host Emacs 30.1 performs the
same build in 7 seconds*, reporting =0 runtime units recompiled=, and
produces an 8,239,040-byte ELF.

* §1 Problem — measured evidence

Every number below came from running something, on =target/nelisp= at
=18367284e=, with =EMACS=emacs-gtk= (30.1) wherever a host oracle was
needed.  Where a hypothesis was ruled out, §1.8 records the control that
ruled it out, because four of this investigation's hypotheses were wrong
and the next reader should not re-form them.

** §1.1 Where Doc 204 P5 stopped, reproduced

P5 recorded =nelisp-standalone--project-source= raising =(void-function
eobp)= when driven directly on =target/nelisp=, past the Python gate.
That reproduces exactly:

#+begin_example
run 1 (tree as it stands) -> (void-function eobp)
#+end_example

The function it stops inside is =scripts/nelisp-standalone-build.el:32392=,
and its body is the whole of P1's requirement in eight lines:

#+begin_src elisp
(with-temp-buffer

  (emacs-lisp-mode)        ; Doc 204 P5 shipped this
  (check-parens)           ; Doc 204 P5 shipped this
  (goto-char (point-min))
  (while (progn (forward-comment (point-max)) (not (eobp)))
    (let ((form (read (current-buffer))))
      ...
#+end_src

=read= taking a buffer as a stream was checked separately and works:
=(read (current-buffer))= on ="(alpha 1) (beta 2)"= answers =(alpha 1)=
and leaves point at 10.

** §1.2 The builder is not the barrier; =load-path= was

Loaded on the standalone, =scripts/nelisp-standalone-build.el= stopped at
=(file-missing . nelisp-runtime-reload-telemetry)=.  That is not a language
gap: seven of the builder's eight =require= forms resolve to =lisp/=, and
the eighth lives in =scripts/= — which the standalone's =load-path= does
not carry (it has =lisp/=, =src/=, =packages/*/src=).  Host Emacs passes
=-L scripts= explicitly, which is why this never showed up there.

With =scripts/= prepended, measured:

#+begin_example
telemetry now: ok
builder load:  ok
build-application fboundp=t
project-source    fboundp=t
#+end_example

All 32,485 lines read.  Whatever else is true, the builder is not too big
to load.

|---------------+-------------------------------------|

** §1.4 =forward-comment= skips comments but not newlines

This is the one genuine defect in code Doc 204 shipped.  With the eight
bridges in place the builder gets further and then fails differently:

#+begin_example
run 2 (with bridges) -> (end-of-file #<buffer  *temp*>)
#+end_example

Traced by comparing against host Emacs 30.1 at the exact call:

| step | standalone | host 30.1 |
|------+------------+-----------|
| after =read= | point=38 | point=38 |
| =(forward-comment (point-max))= | nil | nil |
| point after | *38* | *39* |
| =(eobp)= | *nil* | *t* |

Host skips the trailing newline and leaves the =while= loop; the
standalone does not, so the loop runs once more and =read= hits the end.

The cause is =nelisp--forward-comment-1= (prelude:9119), whose
whitespace loop tests only for syntax class =?\s=:

#+begin_src elisp
(while (and (< p hi) (eq (nelisp--syntax-lookup ... ) ?\s))
  (setq p (1+ p)))
#+end_src

In the Emacs-Lisp syntax table a newline is class =?>= (comment-ender),
not =?\s=.  Measured on both runtimes, which agree exactly: space 32, tab
32, *newline 62*, =;= 60, =a= 119, =(= 40, =)= 41.

Two candidate fixes were written and both were run against an eight-case
table (spaces-only, newline-only, trailing-newline, comment-only,
comment+space, space-then-comment, at-end, two-comments).  *Both match
host Emacs on all eight*, and neither disturbs the comment-terminator
loop below, because that loop is only entered after a =?<= is found:

- A: compare the character to =?\n= directly.
- B: accept syntax class =?>= alongside =?\s=.

§2 chooses B.

Note for whoever edits this function: =nelisp--motion-char-at= answers nil
past the end and =nelisp--syntax-lookup= *signals* on nil
(=(wrong-type-argument number-or-marker-p nil)=), so the =(< p hi)= guard
is a contract, not a nicety.

** §1.5 =utf-8-unix= is rejected, and only it should be added

Past =forward-comment=, the public entry point fails with
=(coding-system-error utf-8-unix)=.

=encode-coding-string= / =decode-coding-string= carry an explicit
accept-list, =(utf-8 latin-1 binary no-conversion us-ascii undecided
prefer-utf-8)=, and =utf-8-unix= is not in it.  The builder names
=utf-8-unix= nine times; five are =let= bindings of
=coding-system-for-write= / =-for-read=, which are *inert* here —
=write-region= and =insert-file-contents= never read those variables —
and four are direct =encode-coding-string= calls at =:32429-32439=.

Which aliases belong in the list was settled against host Emacs rather
than by eye.  All six of =utf-8=, =utf-8-unix=, =utf-8-emacs=,
=raw-text=, =raw-text-unix=, =binary= encode ="a<U+65E5>b"= to the same
five bytes — but =coding-system-base= separates them:

| name | base |
|------+------|
| =utf-8-unix= | *=utf-8=* |
| =utf-8-emacs= | =utf-8-emacs= |
| =raw-text= / =raw-text-unix= | =raw-text= |
| =binary= | =no-conversion= |

Only =utf-8-unix= is a true alias of =utf-8=.  The first provisional patch
written here mapped all four to =utf-8= and was wrong for three of them;
the byte-identity of one test input hid it.

*The accept-list exists in four places* —
=lisp/nelisp-stdlib-misc.el:705,726= and
=scripts/nelisp-stdlib-prelude.el:7332,7356= — currently identical.  The
misc copy's own comment records what happens otherwise: "Same change as
the prelude's own copy of this function; they are read by different
consumers and both were wrong (v1.2.1 parity gap 6)."

** §1.6 =file-expand-wildcards=: one call site, one replacement

Absent everywhere in the tree; one call site, =scripts/nelisp-standalone-build.el:20248=,
expanding =packages/*/src=.  Instrumented at runtime, the argument is
exactly that pattern and nothing else.

=directory-files= + =file-directory-p= (both present) reproduce host
Emacs's answer exactly: *count 43*, same first
(=packages/nelisp-actor/src=) and same last (=packages/nl-static/src=).

** §1.7 =secure-hash=: the one that is a decision, not a patch

=secure-hash=, =sha1=, =md5=, =secure-hash-algorithms= and =buffer-hash=
are *all absent*.  The reader's builtin table carries no message digest —
its only hash-named entry is =sxhash-eq=, which is identity hashing.

The builder needs it in three places, and nowhere else:

| line | call | note |
|------+------+------|
| 1376 | =(secure-hash 'sha1 (current-buffer))= | *buffer argument* |
| 1399 | =(secure-hash 'sha1 (concat ...))= | string |
| 2863 | =(secure-hash 'sha256 bytes)= | string |

*** Option A — the pure-Elisp package: correct, and unusable

=packages/nelisp-secure-hash= exists and =(require 'nelisp-secure-hash)=
succeeds, but it publishes =nelisp-hash-sha1= / =-sha256= / =-md5= /
=nelisp-hash-secure-hash= and does *not* define the standard name, which
is why requiring it leaves =(fboundp 'secure-hash)= nil.

Its answers are right.  Against host =secure-hash= on ="abc"=: sha1 40
chars =a9993e364706816a...=, sha256 64 chars =ba7816bf8f01cfea...=, md5 32
chars =900150983cd24fb0...= — identical on both runtimes.  (=sha512= is
unsupported; the builder never asks for it.)

Its cost is the problem:

| input | pure Elisp | host =secure-hash= |
|-------+------------+--------------------|
| 1,000 B | 5.17 s | ~0.0000 s |
| 10,000 B | 68.82 s | ~0.0000 s |
| 100,000 B | *632.08 s* | 0.0001 s |

Roughly linear at ~6.3 ms/byte.  =nelisp-standalone--toolchain-digest=
hashes =nelisp-standalone--dep-files=, which is five files totalling
*3,187,974 bytes*:

| file | bytes |
|------+-------|
| =scripts/nelisp-standalone-build.el= | 1,800,642 |
| =lisp/nelisp-aot-compiler.el= | 1,009,230 |
| =src/nelisp-cc-runtime.el= | 194,026 |
| =lisp/nelisp-elf-write.el= | 134,066 |
| =lisp/nelisp-static-linker.el= | 50,010 |

At 6.3 ms/byte that digest alone is *≈5.6 hours*, and it is computed
before any unit is compiled.  This is the whole explanation for an
instrumented build that ran 30 minutes at 100% CPU and wrote *nothing* to
the unit cache: it was not looping and it was not compiling — it was
hashing.  Three wrong hypotheses died here (§1.8).

It does not end at the digest.  =nelisp-standalone--unit-cache-key= runs
once *per unit*, and the last real build linked *112 units*.  Only 13 of
the unit sources are reachable as =--source= defvars, and those alone
=prin1= to 209,413 bytes (largest: =applyfn-baked-source=, 115,212).  That
209,413 is a floor, not a total — but even the floor is ~22 minutes of
pure-Elisp hashing.

*** Option B — the external helper: fast, correct, and not self-contained

=call-process= and =executable-find= both exist on the standalone, and
=/usr/bin/sha1sum= and =/usr/bin/sha256sum= are found.  Measured from
=target/nelisp= over the 1.8 MB builder source:

#+begin_example
bare name 'sha1sum'   rc=0  0.052s   a00cd062cbe0d3ecf6ea16f40affe4fd07da2387
absolute path         rc=0  0.014s   a00cd062cbe0d3ecf6ea16f40affe4fd07da2387
#+end_example

Byte-identical to the shell's own =sha1sum=.  A bare name works, so
=call-process= does search PATH here — unlike =nelisp-call-process=, whose
absence of PATH search the builder's own generated fallback documents.

At ~0.014 s per invocation, 112 unit keys plus one digest is under two
seconds.  The cost is conceptual, not temporal: a self-hosted build that
shells out to coreutils is not self-contained, and the builder's own
generated fallback (=:21575=) takes this route only for =sha256= and
errors on anything else — so it cannot serve the two =sha1= call sites as
written.

*** Option C — a native primitive

None exists.  Adding one is real work in the runtime, not a bridge, and it
is the only option that leaves the result both fast and self-contained.

*** Option D — change what the digest hashes

The digest's job is cache invalidation: "any toolchain source newer than a
cache entry forces recompile" (its own docstring).  A cheaper key —
mtime + size per dep file — would serve that job at ~zero cost, at the
price of the property the current scheme has: content addressing survives
a touch, a checkout, and a clock skew, and mtime does not.

*This document does not choose between B, C and D.*  See §2.

** §1.8 Ruled out, with the control that ruled it out

Recorded because each of these was believed at some point in this
investigation, and three of them shaped a wrong plan before the control
arrived.

- =max-lisp-eval-depth= :: *this entry was wrong, and P2 corrected it.*

  What is true: =rec_max= is written at build time as a fixed 16000
  (=:19286=, =:27542=), a bare =defvar= plus =let= binding does *not* move
  the real ceiling (measured: depth 20000 still signals
  =excessive-lisp-nesting= under =(let ((max-lisp-eval-depth 40000))
  ...)=), and a real build never reaches the ceiling — the requested 40000
  is headroom, not use.  All of that was measured and all of it holds.

  What was wrong: concluding from it that the name needs nothing.  The
  builder's four sites bind it as =(max max-lisp-eval-depth N)=, which
  *reads* it, so an unbound variable raises =void-variable= long before
  any recursion gets deep.  P2's acceptance run found exactly that, where
  §3 P2 had predicted =(void-function secure-hash)=.

  The fix is a =defvar= in the prelude, seeded to 16000 so a reader is not
  misled about where the ceiling sits, with a docstring saying plainly
  that binding it moves nothing.  No ceiling work; the original
  measurement stands.

  The lesson is narrower than "measure more": *reaching a limit and
  binding its name are independent questions*, and the first was measured
  carefully while the second was never asked.
- =print-circle= :: bound on by =--unit-cache-key= to dodge Emacs's
  200-level "apparently circular" heuristic on deep-but-acyclic data.  It
  is inert here (measured: identical output with it t and nil).  That does
  not matter, because the deepest top-level form in the builder is *28*
  levels.
- printer depth :: the standalone printer does have a ceiling —
  =excessive-lisp-nesting= somewhere between 1,000 and 2,000 levels,
  unchanged by =print-circle=.  Irrelevant at depth 28.
- =locate-library= :: suspected of returning nil and silently changing the
  digest's input.  It resolves all four libraries to correct absolute
  paths; the negative control answers nil.
- =buffer-size= :: appeared as a =void-function= during this work.  The
  builder uses it *zero* times; it was a probe's own bug.  (=nelisp-buffer-size=
  exists, so bridging it later is one line.)
- circular printing :: =prin1-to-string= on a genuinely circular list does
  not signal here — it *hangs* (killed at 20 s; host Emacs signals).  A
  real defect, but not on the builder's path, which hashes acyclic
  structure.  Filed here rather than folded in.

* §2 Decided direction

1. *Bridges go to the existing internals, in the existing block.*  All
   eight names in §1.3 are added to =scripts/nelisp-stdlib-prelude.el='s
   bridge block in the shape already used there,
   =(unless (fboundp 'NAME) (defun NAME ... (nelisp-NAME ... nelisp--current-buffer)))=.
   No new buffer code.

2. *=forward-comment= is fixed by syntax class, not by character.*  Fix B
   from §1.4.  Both fixes measure identically on the eight-case table, so
   this is a judgement, not a measurement: a table that redefines the
   newline's class should carry the predicate with it, and a literal
   =?\n= comparison would be left behind.  Recorded as a judgement so the
   next reader can overturn it without re-running the table.

3. *Only =utf-8-unix= joins the accept-list, and all four copies move in
   the same commit.*  §1.5 measured =raw-text= and =utf-8-emacs= to have
   different bases; they stay out.  The four-file rule is not hygiene, it
   is the exact failure the misc copy's comment already records.

4. *=file-expand-wildcards= is replaced at its one call site* rather than
   implemented generally.  §1.6 measured the replacement exact for the
   only pattern it is ever passed.  A general implementation is a larger
   promise than the tree needs and than this measurement supports.

5. *The hash route is Option B, the external helper* (decided 2026-09-18).
   §1.7 measured it at 0.014 s over 1.8 MB from =target/nelisp=, answering
   byte-identically to the shell's own =sha1sum=; 112 unit keys plus one
   digest is under two seconds against host Emacs's 7.

   What this buys and what it costs, stated plainly so the trade is not
   forgotten: a self-hosted =build= that shells out to coreutils is *not*
   self-contained, which is the property Option C would have preserved and
   this one does not.  It keeps content addressing, which Option D would
   have traded away, and it lands now rather than after new runtime work.
   If the runtime later grows a native digest, this is the call site to
   repoint, and P3's bridge is deliberately written as one function so
   that is a one-place change.

   Two constraints follow from the measurement and must survive into P3:
   the helper must be located through =executable-find= (a bare name works
   because =call-process= searches PATH here, unlike =nelisp-call-process=),
   and it must cover =sha1= as well as =sha256= -- the builder asks for
   =sha1= twice and =sha256= once, so the generated fallback at =:21575=,
   which is =sha256=-only, cannot serve as-is.

6. *Every exit criterion is measured against =target/nelisp=.*  Same
   reason as Doc 204 §2.5: =(unless (fboundp 'X) ...)= bridges are inert
   under host Emacs, so a host-side green says nothing about this work.
   The host is used only as an oracle for what an answer *should* be.

* §3 What each phase ships

** P1 — load-path and the eight bridges (0.5-1 d)

Ships: =scripts/= added to the standalone's =load-path=; the eight
bridges of §1.3.

Exit criterion, measured on =target/nelisp=: =nelisp-standalone-build.el=
loads without =file-missing=, and =nelisp-standalone--project-source=
advances past =(void-function eobp)=.  It will *not* complete yet — it
reaches =(end-of-file ...)=, which is P2's subject, and the phase is done
when it fails *there* rather than earlier.

*LANDED 2026-09-18.*  Measured on a reader rebuilt with both changes
(=NELISP_STANDALONE_READER_OUTPUT=, 8,263,416 bytes; =target/nelisp=
untouched at 8,230,592), with =scripts/= NOT added by hand — it is baked
in now:

#+begin_example
1. builder require -> ok
2. build-application fboundp -> t
   bridge eobp / bobp / buffer-name / get-buffer-create
        / narrow-to-region / widen / beginning-of-line / end-of-line   all t
3. project-source -> (end-of-file #<buffer  *temp*>)
#+end_example

The =load-path= entry went into
=nelisp-standalone--reader-tree-load-path=, which is the single producer
every bootstrap reads — its own docstring records what happened the last
time a path was added to one entry point only ("Same feature, different
answer per entry point").  =scripts/= was never deliberately excluded:
the function lists =lisp/=, =src/= and =packages/*/src= and filters for
existence, and =scripts/= simply was not in the list.

Ratchets, measured rather than assumed, because the same eight names moved
two of them the last time the prelude grew (Doc 204 P1-P5):

| gate | result |
|------+--------|
| =emacs-compat= | PASS — 8,819 → 8,827 names, deferring 264 → 272, *shadowing 268 unchanged* |
| =ns-inventory= / =ns-gate= / =fallback-inventory= | PASS, unchanged |
| =substrate-presence-corpus-check= | went stale at 932 names; regenerated with the gate's own =NELISP_SUBSTRATE_PRESENCE_GEN_WRITE=1= |
| =make compile= | rc=0 under =byte-compile-error-on-warn= |

The =emacs-compat= row is the one worth noting: that ratchet was brought
to exactly 268/268 earlier the same day, with zero margin, so eight new
standard names would have turned CI red had any of them landed unguarded.
All eight are =(unless (fboundp ...))= and all eight are prelude-only,
checked before the edit rather than after.

** P2 — the three real defects (1-2 d)

Ships: the =forward-comment= predicate; =utf-8-unix= in all four
accept-lists; the =file-expand-wildcards= call site.

Exit criteria, each measured:

- =nelisp-standalone--project-source= returns the generated program text
  rather than signalling.  (Already demonstrated with provisional
  versions of all three: it returns a =(progn (setq command-line-args-left
  ...) ... (demo-main) (nelisp--exit-process 0))= string.)
- The eight-case =forward-comment= table matches host Emacs 30.1.
- =make emacs-parity=, =make compile=, =make ns-gate=, =make
  fallback-inventory= stay green — the coding accept-list and the printer
  are both parity surface.
- =nelisp-standalone-build-application= reaches =(void-function
  secure-hash)= — i.e. P2 is complete when the *only* thing left is §1.7.

*LANDED 2026-09-18, and it took four changes rather than three.*  Measured
on a reader rebuilt from them (8,283,960 bytes; =target/nelisp= untouched
at 8,230,592):

#+begin_example
depth var: boundp=t value=16000 special=t
forward-comment newline: point=4 max=4 eobp=t   (host 4 4 t)
utf-8-unix="ab"  raw-text=coding-system-error
project-source -> (STRING 147)
build-application -> (void-function secure-hash)
#+end_example

The fourth change is =max-lisp-eval-depth=, which §1.8 had filed as "not a
gap".  The acceptance run found it immediately: =build-application=
stopped at =(void-variable max-lisp-eval-depth)=, not at =secure-hash=.
§1.8 now carries the correction and the reason it was wrong.

=raw-text= still signalling is not incidental — it is the check that the
accept-list grew by the one alias §1.5 justified and not by the three that
merely encoded one sample identically.

Two things about the =defvar= are worth keeping:

- *Bare, it turned =emacs-compat= red.*  An unguarded =defvar= of a stock
  Emacs variable counts as =shared-shadowing=: 269 against a baseline of
  268 that had been brought to exactly zero margin earlier the same day.
  Wrapping it in =(unless (boundp ...))= moved it to =shared-deferring=
  (272 → 273) and left the ratchet at 268.
- *The guard does not cost the special declaration.*  Measured on both
  runtimes: =special-variable-p= answers t and a =let= is still dynamic
  (the callee sees the bound value).  Four prelude variables already use
  this shape — =case-fold-search=, =tab-width=,
  =emacs-lisp-mode-syntax-table=, =major-mode= — so this follows the file
  rather than inventing for it.

*A defect this phase introduced, and the check that failed to catch it.*
Wrapping the =defvar= without adding the closing paren left the prelude
ending inside a form.  The verification used at the time — reading the
file form by form and treating =end-of-file= as success — cannot detect
that, because a form that runs out signals =end-of-file= too; it reported
"560 top-level forms, balanced" on a broken file.  =check-parens= (Doc 204
P5's own deliverable) distinguishes the two and was used instead.

What actually caught the break was =emacs-compat=, a gate for *counting
names*.  =make compile= returned rc=0 throughout: its target list is
=src/= and =packages/=, and the prelude is not in it.  Nothing byte-compiles
or parse-checks =scripts/nelisp-stdlib-prelude.el= — it is only ever
=load='ed (the shadow/parity smokes).  That gap is recorded in §6.5 rather
than fixed here, because a new gate needs a mutation row written and
proven red first.

** P3 — the hash route (size depends on §2.5)

Ships: whichever of B / C / D is chosen, plus a =secure-hash= bridge that
accepts *both* a string and a buffer (§1.7's three call sites need
=sha1= over a buffer, =sha1= over a string, and =sha256= over a string).

Exit criterion: =nelisp-standalone-build-application= produces a
Linux x86_64 ELF from a staging path, and =nelisp build= completes with no
Emacs on =PATH=.

*PARTIALLY LANDED 2026-09-19.  The bridge is done and measured; the exit
criterion is not met, for a reason outside this phase.*

Split apart (§6.2), the cost is *not* the hash.  One

supersede it.  The ratio, and the conclusion drawn from it, are unchanged.)  The barrier moved from digesting to *printing*, which is a
runtime performance question and not a gap in this document's list.

P3's own deliverable is complete.  The phase does not close until either

* §6 Open questions

** §6.1 Which hash route — DECIDED 2026-09-18: Option B

Settled: the external helper.  §2.5 records the trade and the two
constraints the implementation must honour.

What stays open under that decision is narrower.  A self-hosted build now
depends on =sha1sum= or =shasum= being present, so P3 must decide what
happens on a host where neither is -- error out, or fall back to the
pure-Elisp implementation and accept the runtime.  §1.7's numbers say the
fallback is only tolerable for the per-unit keys (209,413 bytes floor,
~22 minutes) and not for the digest (3,187,974 bytes, ~5.6 hours), which
argues for erroring rather than silently taking hours.  Measure before
choosing.

And Option C is not dead, only deferred: if the runtime ever grows a
native digest, P3's bridge is the single call site to repoint.

** §6.2 ANSWERED — and the answer is that hashing was never the cost

The question was what 112 per-unit cache keys really cost.  Measured
2026-09-19 on a reader built with P3's bridge, and the answer moves the
problem somewhere else entirely:

| operation (=shim-source=, 6,746 chars) | standalone | host 30.1 |
|---+---+---|
| =prin1-to-string= | 2.143 s | 0.0001 s |
| same under the key's =print-circle= etc. bindings | 2.726 s | — |
| =secure-hash= over the resulting text | *0.053 s* | — |
| whole =nelisp-standalone--unit-cache-key= | 2.761 s | 0.0001 s |

Read that table with §6.6's second hazard in mind: these timings did not
control for the garbage collection the printer provokes, so the standalone
column carries an unattributed collection of roughly half a second.  The
=secure-hash= row is the one that has since been confirmed by a different
route — 56.0 ms for a whole call, timed step by step in §6.6 — and the
whole-key row is the one superseded there.  The conclusion below does not
move: half a second either way leaves hashing a small percentage of a key
that costs seconds.

*Hashing is 2% of the key.*  The external helper does its job; Option B
was the right call and the 5.6-hour pure-Elisp figure is gone.  What is
left is the printer: =prin1-to-string= runs roughly *twenty thousand times
slower* than host Emacs on the same 6.7 KB form, and the builder calls it
once per unit.

For scale on the other end, host Emacs prints the largest unit source
(=applyfn-baked-source=, 115,133 chars) in 0.0009 s and computes its whole
key in 0.0135 s — it does the entire build in 7 s with 0 units
recompiled.

So §1.7's floor of 209,413 =prin1= bytes across 13 sources was the right
quantity to have measured and the wrong thing to attribute it to.  It was
never about which digest; it is about how long this runtime takes to
print.

That is not P3's problem to fix, and it is not a =secure-hash= problem at
all.  It is recorded here so the next reader does not re-derive the digest
question a second time.

** §6.3 Circular printing hangs

=prin1-to-string= on a circular list does not return (§1.8).  Out of scope
here — the builder never hands it one — but it is a live defect and the
measurement is recorded so it is not rediscovered from scratch.

** §6.4 Two static censuses failed; do not repeat them

Two attempts to enumerate the builder's undefined callees by walking its
source returned 3,103 and then 519 names, both dominated by noise — the
first collected every symbol it met, the second still collected =let=
binding names.  The structural reason is that most of this file is
*quoted* native-codegen templates, so a car-symbol walk cannot separate
code from data.

What worked instead was running the real builder and reading the error,
repeatedly.  Six of the seven gaps in §0 were found that way, one per
run.  If a census is wanted, the honest form is a driver that catches
=void-function= / =void-variable=, records it, and *injects a correct
implementation* before retrying — a nil-returning stub poisons the run
(one such stub put nil into a numeric global and produced a
=wrong-type-argument= that looked like a new barrier; another nil-stubbed
=secure-hash= and turned a cache-key path into a 30-minute recompile).

** §6.6 The printer, not the digest, is what blocks a self-hosted build

P3 removed the hashing barrier and uncovered the one underneath it.

=nelisp-standalone--unit-cache-key= prints the unit source with
=prin1-to-string= and hashes the text.  The hash is not the cost.  Timed
step by step on a reader built with P3's bridge, a whole =secure-hash=
call on 11,537 characters is *56.0 ms*, and it divides as:

| step | cost |
|---+---|
| =executable-find= | 10.6 ms |
| =make-temp-file= | 7.8 ms |
| =write-region= | 0.5 ms |
| =call-process= (=sha1sum=) | 34.1 ms |
| =buffer-string= + =substring= + =delete-file= | 0.7 ms |

The printer is everything else.  For =shim-source= (6,746 printed chars)
the whole key costs *3.065 s* measured as whole-process wall clock; the
hash inside it is under 2%.

It scales with the source, and the sources get much bigger.  Host Emacs
30.1 keys the largest of them in *0.0135 s* — roughly 3,600x — and
finishes the entire build in 7 s with 0 units recompiled.  A build links
112 units.

That is why =nelisp-standalone-build-application= sat at 99.9% CPU for 30
minutes and produced no ELF.  It is slow, not stuck, and the slowness is
not in anything Doc 205 set out to fix.

*** Where the time goes, measured

Measured 2026-09-19 as whole-process wall clock: a process prints
=shim-source= K=5 times and nothing else, against a K=0 process (9.002 s)
that subtracts startup, =require= and the digest warm.  Wall clock is used
deliberately rather than an in-process timer, for the reason in the second
hazard below — it charges each variant for every collection it provokes,
whatever runs when the collection lands.

| what was disabled | per print | share of baseline |
|---+---+---|
| nothing (baseline) | 2.733 / 2.936 s | — |
| =nelisp--prn-symbol-needs-leading-escape-p= | 2.420 s | 15% |
| =nelisp--prn-symbol-char-needs-escape-p= | 2.154 s | 24% |
| =nelisp--prn-symbol-escaped= entirely | *0.666 / 0.721 s* | *76%* |

Symbol escaping is three quarters of the printer.  That 76% was also the
figure an in-process measurement gave before the collection hazard was
understood; the two methods agreeing, by different routes, is why it is
quoted.  Replacing the escaper's function cell costs nothing by itself —
an identity wrapper measures 2,130.9 ms against a 2,128.2 / 2,105.7 ms
baseline.

*** Why the obvious fix does not work

Most symbols need no escaping at all, so a fast path that decides once and
returns =symbol-name= untouched looks free.  Measured, it is not:

- On a synthetic bench (9 names x 2000) it was 32% faster: 58.6 s to 39.6 s.
- On the real source it was *slower*: 1,512 ms to 1,752 ms, with
  byte-identical output.

The synthetic input had long names and was not representative.  Real
symbols here are short, so the extra look-ahead scan is pure addition
while the per-character predicate still runs.

Both of those figures predate the collection hazard below and have *not*
been retaken; they are kept because the conclusion (a look-ahead fast path
does not pay here) does not turn on a few per cent, but they should not be
quoted as precise.

*** So the two directions, now with numbers

1. *Make the printer faster.*  The ceiling on incremental work is about
   40% (the escaper's three parts, best case).  Closing a 3,600x gap needs
   something structural — not this function's inner loop.
2. *Stop printing whole unit sources to key them.*  Still the only
   direction with room in it — but the specific candidate this section
   first suggested is *dead*, and checking it is what killed it.

   The candidate was: a unit source is a constant in the builder's own
   file, whose digest is already computed in 1.541 s, so a key of
   (defvar name + that digest) would print nothing.  Two things make that
   unsound, both found by reading =nelisp-standalone--cached-unit= and its
   four call sites rather than by measuring:

   - *The source is not the defvar's value.*  Only the feature arm
     (=:19567=) passes =(symbol-value src)= untouched.  The =:glue= arm
     (=:19553=) picks =--target-arena-source= or =--target-gc-source=
     depending on name and target; =:28427= passes the value through
     =--patch-binding-kinds=; =:19577= passes generated driver source that
     depends on =NELISP_SRC=.  The same name yields different sources
     across targets and modes, so a name-keyed cache collides.
   - *The digest covers five files; the sources come from far more.*
     =--dep-files= lists =nelisp-standalone-build.el= plus four libraries.
     There are 190 =lisp/nelisp-cc-*.el= files, and call sites from
     =:29070= onward =locate-library= them individually.  A key built from
     name + those five digests would not move when the other 185 change.

   That second point is not hypothetical.  It is exactly the defect
   =--cached-unit='s own docstring records from 2026-08-19: the cache was
   keyed on NAME with freshness from a hand-written dependency list, the
   list was wrong at two of twenty call sites, and editing the
   =lisp/nelisp-cc-*.el= a source came from left the cache fresh and
   relinked the *old* object.  The build succeeded, the binary was
   unchanged, and the only symptom was that the edit had no effect.
   Content-addressing exists to make that impossible.

*** The replacement that survives: a type-tagged walk

Any replacement must still be a function of the full source content, so
what is left is to compute that content digest *without going through the
printer* — walk the sexp and append pieces directly.

**** It has to be tagged, and the untagged version is unsound

The first version simply appended each atom's text.  It was fast and
wrong:

| written | untagged text | collides with |
|---+---+---|
| =(nil n)= | ="(nn)"= | =(n n)= — nil against the symbol =n= |
| =(12 n)= | ="(12n)"= | the symbol =\12= |
| =("ab" n)= | ="(abn)"= | the symbol =ab= |

Tagging each atom by type and prefixing every variable-length payload with
its length (=#n=, =#T=, =#s<len>:<name>=, =#i<val>;=, =#t<len>:<text>=)
makes all nine hand-built cases distinct.

**** The fallback arm is the one hole, and it is closed by signalling

A =t= arm that emitted a constant would put every unhandled type into a
single collision class.  Censused over all thirteen =defconst ...-source=
constants — 86,349 objects — that arm is never reached:

| kind | count |
|---+---|
| cons | 43,168 |
| symbol | 22,561 |
| nil | 13,751 |
| integer | 6,846 |
| string | 19 |
| t | 4 |

No vector, float, record, hash-table, bool-vector or char-table occurs.
That is a fact about today's sources, not a guarantee about tomorrow's, so
the arm must *signal*.  Written that way and run against the tree, with a
positive control first — the arm has to fire on something it cannot
handle, or the run proves nothing:

: positive control (a vector) fired: t   hits=1
: walked ok=13  failed=0  fallback hits=0 (want 0)

The census counts what I thought to count; this is the stronger form,
because the check can fail and did not.

**** The key is deterministic

The same 26 cells (13 sources x 2 schemes) were computed in two
independent batches of fresh processes.  *All 26 digests matched.*
Elapsed times moved by +0.6% to +9.3%, all in the same direction, which is
the cost of the second batch sharing the machine — a reason to take ratios
within one batch, never across two.

**** What it costs, across every source in the tree

| source | current | tagged | x | method |
|---+---+---+---+---|
| =applyfn-baked= | 49,241.1 ms | 13,160.6 ms | 3.74x | in-process, both collected |
| =gc= | 21,061.5 ms | 5,594.5 ms | 3.76x | in-process, both collected |
| =arena= | 5,822.7 ms | 1,929.8 ms | 3.02x | in-process, both collected |
| =reader-eval-source= | 3,328.0 ms | 1,149.0 ms | 2.90x | wall clock |
| =shim= | 3,065.0 ms | 925.0 ms | 3.31x | wall clock |
| =reader-capture= | 2,065.0 ms | 617.0 ms | 3.35x | wall clock |
| =catch-throw= | 2,059.0 ms | 830.0 ms | 2.48x | wall clock |
| =arglist= | 702.3 ms | 242.5 ms | 2.90x | in-process, neither collected |
| =reader-boundary= | 583.4 ms | 217.0 ms | 2.69x | in-process, neither collected |
| =trap= | 321.6 ms | 151.5 ms | 2.12x | in-process, neither collected |
| =reader-errstub= | 198.9 ms | 108.9 ms | 1.83x | in-process, neither collected |

|---+---+---+---+---|

*88.6 s to 25.1 s.*  The method column is not decoration.  An in-process
row is quoted only where a collection fell inside both timed regions or
neither; the four sources where it fell inside the current scheme's region
and not the tagged one cannot be compared that way at all, and are
measured by whole-process wall clock instead, which charges each scheme
for every collection it causes.  Mixing the two methods in one total is a
compromise, and it is stated rather than hidden.

Two things in that table matter more than the total.

*The gain tracks size.*  The ratio runs from 3.76x down to 1.12x.  Every
key pays a floor — ~55 ms for the external hash process, plus the
collection the walk provokes — and for =reader-mut-str-len= that floor is
the whole cost.  Only the sources measured in seconds benefit.

*These are the thirteen =defconst ...-source= constants, not the 112 units
a build links.*  Do not multiply this total out to 112.  The =:glue= arm
picks between two of them by target, =--patch-binding-kinds= transforms
one, and one call site generates its source from =NELISP_SRC=, so the
whole-build figure has to be measured on a build.

**** So it is real, and it is not enough

The walk is about 3.5x cheaper across the sources the tree has, sound on
all of them, deterministic, and needs no new primitive.  It is also not
the thing that makes a self-hosted =nelisp build= practical: the largest
single unit still costs 13.2 s against host Emacs's 0.0135 s, and these
thirteen sources alone come to 25.1 s where host Emacs does the entire
build, 112 units, in 7 s.  Direction 1's ~40% ceiling and direction 2's
~3.5x do not multiply out to a 3,600x gap.

Read this section as removing a wrong turn and pricing the right one.  It
does not finish the job, and Doc 205 should not go SHIPPED on the strength
of P1-P3 plus this.

*** Two measurement hazards found along the way

**** Consecutive measurements in one process are not comparable

Running the same =prin1-to-string= twice gives 1,511 ms then 2,932 ms, and
=garbage-collect= only brings it to 2,112 ms — it does not come back.  The
arena has grown to 5 chunks, =used-bytes= 408 MB against
=live-after-last-gc= 43.8 MB, and stays slow in that state.

This was first misread as =fset= poisoning the function cell, because the
A/B happened to use =fset=.  An identity wrapper disproved that.  Every
in-process figure in this section is therefore one measurement per
process.

**** A collection is billed to whichever call runs next

The second hazard is worse, because the call it lands on looks guilty.  A
heavy allocation leaves the cost of the collection it provokes on the next
thing that runs:

| what was measured | cost |
|---+---|
| =(secure-hash 'sha1 "abc")=, nothing built first | 55.1 ms |
| the same, after a sexp walk that builds strings | *613.9 ms* |
| =(garbage-collect)= in that state, on its own | 547.9 ms |
| =(secure-hash 'sha1 "abc")= immediately after that collect | 55.2 ms |
| second and third calls | 54.1 / 56.3 ms |
| after walking the largest source instead | *3,416.4 ms* |

Three characters.  Neither length nor content can explain 613.9 ms, and
the cost tracks how much was allocated, not what was hashed.

This was diagnosed wrong four times before that — as slow hashing, as a
multibyte input, as the way the string was built, and as content
dependence — each with its own control, each control agreeing with the
wrong conclusion because it reproduced the same allocation.  Two things
settled it: hashing three characters, and replicating the hash bridge's
body with per-step timers, which produced *the same digest in 56.0 ms*
where the real call took 605.3 ms, proving no step inside it was slow.

It also hides.  Inserting a =princ= between the walk and the hash makes
the hash read 54.2 ms, because the collection lands on the =princ=.  An
earlier probe reported "write-region 0.4 ms, call-process 54.5 ms, sum
54.9" while leaving =make-temp-file= and =delete-file= untimed — the
collection had landed outside the timers, and the "sum" was not the
function's cost.

Where an in-process figure is quoted above, the collection was detected
rather than assumed, by sampling =:live-after-last-gc= around the timed
region.  That detector was itself controlled before anything was concluded
from it: it does not move across 100, 1,000 or 10,000 allocations and only
moves once the count is large enough to trigger a collection, and a second
collection that reclaims almost nothing still moves it.  So an unchanged
field means no collection ran, and a changed one means it did.

This hazard is *not* the arena growth above.  That one does not recover;
this one is fully restored by a single collection.  They present almost
identically, so both have to be tried.

**** What to do instead

Prefer whole-process wall clock for any comparison that will be quoted: K
operations per process against a K=0 floor.  It does not care where a
collection lands, and it is what a build actually experiences.  Descend to
in-process timers only for a breakdown, and then report whether a
collection fell inside.

One more trap, not about this runtime at all: the first wall-clock script
printed =9,00s= under a comma-decimal locale, and the arithmetic that
followed truncated at the comma — whole-second resolution wearing
hundredths.  Timing scripts here set =LC_ALL=C= and run the formatter
against a known value first.
