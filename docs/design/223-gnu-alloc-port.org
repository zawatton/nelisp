* Purpose

Doc 220 measured NeLisp's memory manager at 42.79% of the company load
(GC 23.69%, allocation 19.11%). GNU Emacs 31.1 pays far less because it
allocates each Lisp type from its own fixed-layout blocks, keeps mark bits
beside the objects, rebuilds per-type free lists in one sweep loop per type,
and validates conservative pointers through persistent block metadata.
NeLisp uses one general block allocator: an 8-byte header per block, a mark
in that header, an exact-start index rebuilt every collection, and a
heap-wide header walk that coalesces free runs.

This document maps every alloc.c mechanism to its NeLisp structure. Each
mechanism is *ported* (GNU's data structure and algorithm), *adapted* (GNU's
algorithm on a NeLisp-specific layout, with the reason), or *impossible* in
this stage (the blocking NeLisp layer is named). GNU source:
=/home/madblack-21/Downloads/emacs-31.1/src/alloc.c= and =pdumper.c=.

* NeLisp starting point (base ad41dc4bf, word heap through S4.2)

- A cons is a 32-byte Sexp view (tag byte 7, payload pointer at +8)
  allocated by =alloc-bytes 32 8=, plus a 24-byte =NlConsBox= payload
  (car WORD, cdr WORD, refcount) from =nl_alloc_consbox=. Identity and
  mutation live in the payload; views may be copied.
- Floats, strings and symbols are 32-byte Sexp slots. Producers write the
  tag into a caller-allocated slot (the result-slot protocol), so the
  allocator does not know the type when it hands out the slot. String
  character buffers are separate =alloc-bytes N 1= blocks and may be shared
  by several views (Doc 149 clone aliasing).
- Vectors, records and char-tables are header-less (tag 110, Doc 216 S4.1):
  one backing block that starts with a kind/length word.
- Every block has an 8-byte header =BLOCK_TOTAL | mark= (0 live, 1 marked,
  2 free, 4 conservatively pinned). Marking validates every pointer through
  =nl_gc_object_start_p=, which needs the exact-start index that
  =nl_gc_index_prepare= rebuilds by walking every header of every chunk.
  =nl_gc_sweep_merge_chunk= walks every header again and relinks coalesced
  free runs into size buckets.
- Every ordinary run cold-loads =BINARY.cold=, the post-prelude heap dumped
  at build time (=nelisp--arena-dump-image-stream=, an in-place swizzle plus
  a relocation table over the coalesced chunks). Image objects lie below
  the boot watermark and are never freed: this is NeLisp's pdumper.
- Compaction is off (flag 268435608 = 0). The conservative stack scan pins
  blocks (mark 4) and scans pinned blocks word by word.
- Parallel sections (=nelisp-thread-gc-inhibit=) disable free-list reuse
  (268435624 = 1) and allocate through the CAS bump path.

* Interaction with the word heap (Doc 216)

Typed blocks hold the payloads that the word-heap stages turn into objects.
A cons-block cell is the future tag-010 cons; a vector-block entry is
already the tag-110 backing. Nothing here adds a new tag or a new WORD
decoder: a view still points to its payload, and the payload's address
decides whether marking uses a side bit (block cell) or a header (legacy
image or parallel-section object). When S2 removes cons views, the WORD
itself is the cell address plus 2 and =CONS_BLOCK= applies directly.

* Implementation order

1. Cons blocks: ablocks, cons blocks, =nl_alloc_consbox= fast path,
   registry, side mark bits, =nl_sweep_conses=, conservative
   =live_cons_holding=, mark reset on conservative rollback. Increment (a)
   keeps the build-time dump on legacy conses (an environment flag read by
   the dump run) and makes a dump that meets a block cell fail loudly.
2. Increment (b): the dump converts block cells into legacy headered image
   payloads, so runtime and library images carry conses, and the flag goes.
3. Vector blocks with size-class free lists and large-vector fallback.
4. Floats, symbols and strings after word-heap S3/S5 (see the map).

* Expected effect and the remaining gap (S2)

Doc 220's churn profiles (base 9d5f4a515, four-layout means, millions of
Ir) put NeLisp cons churn at mark 991, index/prepare 287, rebuild 564,
allocation 106, zeroing 40 against GNU's whole-invocation GC plus
allocation of about 157. Most of NeLisp's cost is per collection over the
cold image: the index walk, the sweep walk and the marking of image objects
happen whatever the churned type. Typed blocks remove the allocator, index
and sweep work for churned objects only. The remaining gap is explained by
three GNU mechanisms this port does not yet reproduce:

- pdumper's dump is not swept and has a static object-start table
  (pdumper.c:5229); NeLisp still walks every image header in
  =nl_gc_index_prepare= and =nl_gc_sweep_merge_chunk=;
- =mark_object= trusts tagged pointers; NeLisp still probes the start index
  for every legacy object, image objects included;
- GNU marks with an explicit stack (alloc.c:6483); NeLisp recurses.

S2.1-S2.3 are therefore expected to stay red after S1; the criteria are not
revised. The measured numbers and their attribution are recorded in the
ledger.
