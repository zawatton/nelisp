* Purpose

Doc 220 measured NeLisp's memory manager at 42.79% of the company load
(GC 23.69%, allocation 19.11%). GNU Emacs 31.1 pays far less because it
allocates each Lisp type from its own fixed-layout blocks, keeps mark bits
beside the objects, rebuilds per-type free lists in one sweep loop per type,
and validates conservative pointers through persistent block metadata.
NeLisp uses one general block allocator: an 8-byte header per block, a mark
in that header, an exact-start index rebuilt every collection, and a
heap-wide header walk that coalesces free runs.

This document maps every alloc.c mechanism to its NeLisp structure. Each
mechanism is *ported* (GNU's data structure and algorithm), *adapted* (GNU's
algorithm on a NeLisp-specific layout, with the reason), or *impossible* in
this stage (the blocking NeLisp layer is named). GNU source:
=/home/madblack-21/Downloads/emacs-31.1/src/alloc.c= and =pdumper.c=.

* NeLisp starting point (base ad41dc4bf, word heap through S4.2)

- A cons is a 32-byte Sexp view (tag byte 7, payload pointer at +8)
  allocated by =alloc-bytes 32 8=, plus a 24-byte =NlConsBox= payload
  (car WORD, cdr WORD, refcount) from =nl_alloc_consbox=. Identity and
  mutation live in the payload; views may be copied.
- Floats, strings and symbols are 32-byte Sexp slots. Producers write the
  tag into a caller-allocated slot (the result-slot protocol), so the
  allocator does not know the type when it hands out the slot. String
  character buffers are separate =alloc-bytes N 1= blocks and may be shared
  by several views (Doc 149 clone aliasing).
- Vectors, records and char-tables are header-less (tag 110, Doc 216 S4.1):
  one backing block that starts with a kind/length word.
- Every block has an 8-byte header =BLOCK_TOTAL | mark= (0 live, 1 marked,
  2 free, 4 conservatively pinned). Marking validates every pointer through
  =nl_gc_object_start_p=, which needs the exact-start index that
  =nl_gc_index_prepare= rebuilds by walking every header of every chunk.
  =nl_gc_sweep_merge_chunk= walks every header again and relinks coalesced
  free runs into size buckets.
- Every ordinary run cold-loads =BINARY.cold=, the post-prelude heap dumped
  at build time (=nelisp--arena-dump-image-stream=, an in-place swizzle plus
  a relocation table over the coalesced chunks). Image objects lie below
  the boot watermark and are never freed: this is NeLisp's pdumper.
- Compaction is off (flag 268435608 = 0). The conservative stack scan pins
  blocks (mark 4) and scans pinned blocks word by word.
- Parallel sections (=nelisp-thread-gc-inhibit=) disable free-list reuse
  (268435624 = 1) and allocate through the CAS bump path.

* Interaction with the word heap (Doc 216)

Typed blocks hold the payloads that the word-heap stages turn into objects.
A cons-block cell is the future tag-010 cons; a vector-block entry is
already the tag-110 backing. Nothing here adds a new tag or a new WORD
decoder: a view still points to its payload, and the payload's address
decides whether marking uses a side bit (block cell) or a header (legacy
image or parallel-section object). When S2 removes cons views, the WORD
itself is the cell address plus 2 and =CONS_BLOCK= applies directly.

* Implementation order

1. Cons blocks: ablocks, cons blocks, =nl_alloc_consbox= fast path,
   registry, side mark bits, =nl_sweep_conses=, conservative
   =live_cons_holding=, mark reset on conservative rollback. Increment (a)
   keeps the build-time dump on legacy conses (an environment flag read by
   the dump run) and makes a dump that meets a block cell fail loudly.
2. Increment (b): the dump converts block cells into legacy headered image
   payloads, so runtime and library images carry conses, and the flag goes.
3. Vector blocks with size-class free lists and large-vector fallback.
4. Floats, symbols and strings after word-heap S3/S5 (see the map).

* Implementation status (2026-10-21)

** Cons blocks (S1.1)

=nelisp-standalone--typed-alloc-forms= (arena.o) and
=nelisp-standalone--typed-gc-forms= (reader-gc.o) hold the port.

- Allocation: =nl_alloc_consbox= takes its payload from =nl_cons_alloc=
  (Fcons): =cons_free_list=, then =cons_block_index=, then a new block from
  =nl_ablock_alloc= (lisp_align_malloc). Each cell charges 24 bytes to the
  collector debt, as =consing_until_gc= does.
- Metadata: the registry maps a 512 KiB group base to its entry; a block's
  type word sits at offset 32752. =nl_typed_find= rejects addresses outside
  the lowest and highest group first, as =mem_find= does with
  =min_heap_address= and =max_heap_address=.
- Marking: a cons view whose payload is a block cell sets the cell's side bit
  (=nl_cons_mark_cell=) and never probes the exact-start index. Cold-image and
  parallel-section payloads keep their legacy header marks.
- Sweeping: =nl_sweep_conses= runs inside =nl_gc_sweep= (and after a
  compaction) and rebuilds =cons_free_list=.
- Conservative scanning: =nl_gc_conserv_word= first asks =nl_gc_conserv_typed=
  (mark_maybe_pointer); =nl_live_cons_holding= rejects cells past
  =cons_block_index= in the current block and cells whose car is the dead
  marker.
- Statistics: =nelisp--arena-stats= appends the cons block count and the live
  and free conses of the last sweep. An explicit =garbage-collect= counts
  block conses from the sweep and skips image objects, as GNU's gcstat skips
  pdumper objects; the legacy heap objects are counted at their first mark
  (see "garbage-collect's counters").
- Images: =nelisp--arena-dump-image-stream= appends one converted region after
  the coalesced chunks, one 32-byte legacy block per cell (=nl_dump_cons_*=).
  Cells the image walk reached are live payloads, the rest are free blocks.
  =nl_mc_logoff= and =nl_mc_phys= map cells to the region and back, so the
  in-place swizzle, the relocation table, the restore and the loader are
  unchanged. The single-chunk copy dump refuses to run while cons blocks are
  in use.

** Next increment: vector blocks

Tag-110 backings up to GNU's =VBLOCK_BYTES_MAX= (2040 bytes) move to 32 KiB
vector blocks with GNU's size-class free lists (=allocate_vector_from_block=)
and =sweep_vectors=' coalescing; larger backings stay headered general blocks
(the large-vector list). Two structural decisions are needed first:

- Mark storage: GNU sets =ARRAY_MARK_FLAG= in the header word. NeLisp's
  kind/length word is read during a collection, by marking, the census and
  the image walk, without masking, so a side bitmap with one bit per 8-byte
  granule is the lower-risk adaptation.
- Image conversion: variable sizes need a per-block granule-to-image-offset
  table so that =nl_mc_logoff= stays O(1) for interior field addresses.

Integration points found while porting conses, all of which assume that
every heap object is a headered block inside the arena chunks:

- =nl_gc_block_elem_cap= reads =BLOCK_TOTAL= at owner-8 to bound
  =nl_gc_mark_inline_words=; a vector-block backing has no such header and
  needs its size from the kind/length word.
- =nl_gc_in_arena= validates pointers in marking, the conservative resolver
  and runtime helpers; a block outside the chunks fails it.
- The census, =nl_fa_slot= and =nl_fa_vectorlike_fields= dedup tag-110
  backings through =nl_gc_mark_block=.

** Image objects as pdumper objects (step 2)

GNU never sweeps its dump: dump objects keep their mark bits in a separate
bitmap (pdumper.c:5247 =pdumper_marked_p_impl=, pdumper.c:5259
=pdumper_set_marked_impl=), cleared by =pdumper_clear_marks= from =gc_sweep=
(alloc.c:7114 =pdumper_clear_marks=), and a dump pointer is validated against
the dump's object-start table (pdumper.c:5229 =pdumper_find_object_type_impl=).
NeLisp's cold image is that dump (adapted):

- =nl_boot_build= runs once per boot watermark, after a cold-image restore.
  One header walk of [data start, watermark) records a start bit for every
  image object, the live bytes, and the hole runs (maximal runs of blocks
  inside the restored image's free blocks, which later allocations reuse).
- Marking an image object sets its bit in the boot mark bitmap; its header
  is never written. =nl_gc_object_start_p= answers image objects from the
  start bitmap; the per-collection index covers only the hole runs and the
  range above the watermark.
- =nl_gc_sweep_merge_chunk= sweeps chunk 0 as the hole runs plus the range
  above the watermark and adds the image's live bytes; image objects are
  never swept. The boot mark bitmap is cleared after every sweep and on
  every mark reset.
- The conservative scan accepts an image object start or a pointer at most
  4 KiB inside it (GNU accepts only exact starts for dump objects) and pins
  it in the boot bitmap.
- Without a restored image (the build-time dump run) nothing changes.

The restored image was 289 MB of arena with 34.7 MB live in 582K blocks and
254 MB free in 81K hole runs, because the dump copied whole chunks with the
dumping run's garbage. GNU's dump holds live objects only, so it has no hole
runs to sweep.

Marking an image object is one pass, as in pdumper (F3 of the speed unit).
=nl_gc_mark_block= used to ask =nl_boot_start_p= (range, alignment, start bit) and
then =nl_boot_mark= (the same range and index again, then the test-and-set), two
inlined copies of the address arithmetic: 78 instructions for a block that is
already marked or newly marked.  It now tests the range and the alignment once,
reads the start bit and the mark bit with one shared word index and bit mask,
and answers; a block outside the image falls through to the heap path unchanged
(57 instructions per call, the rest being this compiler's stack-machine code).
=nl_gc_mark_cons_payload=, =nl_gc_mark_vbox= and =nl_gc_mark_vectorlike= tested the
typed envelope through a call of =nl_typed_find= before asking about the image;
they compare the envelope inline, so an image pointer never calls it.  No
function is added (the F1 closure stays at 314).  A steady-state collection falls
from 185.2M to 174.0M instructions.  =tools/ai/gc-port-image-edges.py= checks the
safety property: items reached only through a global (image conses, strings,
vectors, floats, bignums) survive five collections with the conservative scan off
and three with it on, fresh heap objects stored into image conses and held only by
them survive five more, and a first and a second-generation dump and restore keep
all of it (ledger S1.17).

** Live-only image dump (step 3)

pdumper copies only the objects =dump_object= reaches from the roots. The
stream dump (=nelisp--arena-dump-image-stream=) now does the same in three
passes over the existing image walk:

1. Mode 1: the walk marks what it traverses; =nl_mc_logoff= includes the
   block that every visited field and its target point into (a legacy block
   gets mark 4, which later traversal still upgrades and recurses; an image
   object gets a bit in a separate included bitmap; a cons-block cell is
   included by traversal only). Nothing is written.
2. =nl_dump_compact_assign= sorts the chunks by address and gives every
   included block an image offset in address order, checks that both
   columns increase, and ranks the reached cells of every cons block.
3. Mode 2: the walk swizzles in place and records the relocation table
   through that packed layout. =nl_dump_compact_write= writes only the
   included blocks (mark bits cleared) and the reached cells. A heap target
   without an image offset fails the dump. The restore runs on every path
   that swizzled.

The loader is unchanged. The build-time image is now 44 MB on disk instead
of 310 MB: a 22.1 MB span of 503K blocks with no free block, 16.9 MB of
interned names and 628K relocations. A restored image therefore has no hole
runs. Collections, the index and the sweep touch only what was allocated
after the restore.

The relocation table of the dump (one 8-byte entry per pointer field the walk
reaches) was sized by the heap: =nl_mc_total= plus the cons and symbol cells,
one entry for every word of the whole region, and its demand-paged mapping
counts against =ulimit -v=.  A second-generation dump of a library image asked
for 2.99 GB on the base's run and 4.05 GB on a build whose arena high-water mark
was 7 % higher, which exceeds the 8 GiB cap.  pdumper.c sizes its tables from
what it dumps.  Pass 1 now counts the pointer fields it visits
(=nl_float_state+88=); after pass 2 the table is allocated again, once, with
that count plus 1/16 and a page of entries; pass 3 refuses to write past it (the
dump fails like any excluded target) and the counts of the passes agree.
=tools/ai/gc-port-dump-budget.py= dumps a heap with a 300 MB pointer-free
string, then dumps again under =--cold-load-from= that image, and requires the
address space to grow by no more than 8 bytes per relocation entry plus 96 MiB
through each dump (ledger S1.14).  The binary before this change grew 449 MiB
through the first dump and 678 MiB through the second, a table the size of the
string; this one grows 10 and 15 MiB.

Loading such an image needs no hole map.  The stream dump writes only included
blocks, with their mark bits cleared, so the image has no free block and no
hole run (pdumper has no hole map either).  The writer stamps trailer version 2
for that; the loader then skips =nl_cold_clear_marks=, the coalesce and relink
walks of the free-list rebuild and =nl_boot_hole_map_build= (together 45.7M
instructions of a 116.5M startup, each a walk over the image's 329,000 block
headers), and publishes only the image's origin and end (=nl_boot_hole_map_none=;
=nl_boot_build= keys on the published end, not on a map, and without a map
=nl_boot_hole_p= answers 0 and every block below the watermark is boot, the
sweep's old no-map arm).  A version 1 image (an older writer) takes the old path
and builds its map.  =(nelisp--debug-switch 46)= answers the state (bit 0 a map,
bit 1 the boot structures, bit 2 an image), 47 the number of hole granules, 48
checks the hole scan on a synthetic header run; =tools/ai/gc-port-image-holes.py=
loads the companion image, a copy stamped version 1 and a copy stamped version 3
(refused) on both linkages (ledger S1.16).  Startup falls from 116.5M to 70.8M
instructions (21.4 to 18.0 ms wall, paired); the first collection of a process
loses the 13M of hole queries its boot structure build made.

** Sixteen-byte cells and header-less cons WORDs (word-heap S2.1/S2.2)

GNU's =struct Lisp_Cons= is 16 bytes (car, cdr), and a cons
=Lisp_Object= is its address plus the =Lisp_Cons= tag; no other object
stands between a reference and the cell.  NeLisp now matches both
halves:

- The refcount word is gone (16adbe722).  =nelisp_nlconsbox_clone= no
  longer does an atomic add, the unlinked drop kernel is retired, and
  =CONS_BLOCK_SIZE= is 2030 cells.
- A cons WORD is the payload address | 2 (Doc 216's tag 010,
  e39acbe88).  Legacy 32-byte views (tag 000) remain valid, and identity
  is the payload address in both.  The producers (Fcons, the VM's
  cons/list and argument lists, =nl_val_clone_into=) emit the direct
  WORD.  Raw stores into a cell canonicalize through =nl_word_canon=
  (458117db8).  =nl_cons_car_ptr= and =nl_cons_cdr_ptr= pass a direct
  cons through: a transient view could not survive an eval that collects
  (the sf-progn rule).  Consumers read through the semantic accessors.
  The x86_64 and aarch64 emitters dispatch on the low bits.  Marking,
  the live-only dump (pointer class 2 in the relocation table) and the
  loader handle the class.
- Moving compaction runs only while no cons block exists.  GNU never
  moves conses, and cells in cons blocks hold edges the debug moving
  path cannot rewrite.

Retained arena bytes per cons dropped from 72 (base) to 16 on both
populations (individual conses and one make-list).  The build-time image
is 34.4 MB and holds no cons header view (4dd3167b8).  The last legacy
producers were the &rest spine copier, the special-form marker test
(which kept every tag-7 view with a nonzero data word) and the dump's
walk of the recorded driver scratch.  The live-only dump now starts from
the Lisp roots only (=nl_fa_live_roots=), as pdumper does.

** Special forms: interim encoding

GNU represents a special form as a subr object with =max_args=
=UNEVALLED= (lisp.h:2175 =struct Lisp_Subr=, =PVEC_SUBR= at lisp.h:1000;
=eval_sub= dispatches at eval.c:2651).  NeLisp's function cell for a
special form holds the list =(builtin NAME ...)= inside a tag-7 view
whose data word carries the marker 13108 (=nl_apply_do_fset= sets it;
=nl_n3_special_object= and the post-lookup test read it).  This is an
interim encoding.  word-heap-census.py counts such a view as a
special-form subr object, not a cons header alias, but only when it
carries the marker, is a function cell (slot 1 of a mirror-entry
record) and holds =(builtin NAME ...)= for one of GNU 31.1's 22 special
forms.  There are 21 today, at boot and after a cons population.
Word-heap S5.3 (gc-port S1.7) stays red until special forms are subr
objects.  That change crosses the evaluator's dispatch, the function
cells and subrp/functionp/func-arity, and the printer.

** Symbol blocks (Doc 226 D9)

GNU allocates a symbol from a =symbol_block= (alloc.c:3616-3626).  Such a
block is about 1 KiB from =lisp_malloc=, registered as =MEM_TYPE_SYMBOL=
in the mem_node tree.  The allocation path is Fmake_symbol (alloc.c:3675):
it pops =symbol_free_list=, else bumps =symbol_block_index=, else takes a
new block, and init_symbol (alloc.c:3660) fills the cell.  The gcmarkbit
lives in the 48-byte =struct Lisp_Symbol= itself (lisp.h:786, 794).
=symbol_marked_p= and =set_symbol_marked= (alloc.c:4057, 4065) use the
pdumper bitmap instead for a dumped symbol.  process_mark_stack's
Lisp_Symbol case (alloc.c:6626) marks function, plist and the =val=
member.  sweep_symbols (alloc.c:6997) rebuilds the free list:
=function= = dead_object, =next= = the link (alloc.c:7032-7033).  It
frees a wholly free block once more than a block of free symbols is held
(alloc.c:7050).  live_symbol_holding (alloc.c:4675) accepts only a
symbol's address or the address of one of its fields.

Here (gc-port, for the symbols lane's direct symbol WORDs, class 110,
kinds 4 and 16):
- Blocks (adapted size).  A symbol block is a 32 KiB typed block of
  type 2 from the 512 KiB groups, the size cons blocks use.  The typed
  registry plays mem_find, so the block size follows the registry rather
  than malloc.  It holds 682 cells of 48 bytes.  The =next= block link
  at 32736 is the same as a cons block's, and the type word is at 32752.
- Allocation (ported).  =nl_symbol_alloc= pops the free list (link at
  +40), else the next cell of the current block, else a new block.  It
  charges 48 bytes to the GC debt and returns the backing address of a
  zeroed cell, or 0 when memory is exhausted.  The symbols lane fills the
  cell, header first.  In a parallel section the cell comes zeroed from
  the general heap: the free list has a single writer, as for conses.
- Mark (ported, adapted bit).  The collector owns header bits 24 and up.
  Bit 24 is the gcmarkbit; bits 0-23 are the symbols lane's (kind,
  redirect, trapped_write, interned, declared_special, pinned, FORWARDED
  type).  At the three class-110 WORD edges (=nl_gc_mark_word=, the cdr
  path of =nl_gc_mark_cons=, the WORD slot path), an inline header test
  recognizes kinds 4 and 16 before anything reads a length, because their
  header bits are flags.  A separate inlinable helper for that test, and
  a non-inlined =nl_symbol_mark_cell=, each cost the F1 prelink closure a
  record.  callpath-perf's merge left the closure at its 304-record
  bound, so both are written inline.  =nl_gc_mark_symbol= marks a block cell through its
  gcmarkbit, and an image or general-heap symbol through its block mark,
  as symbol_marked_p does.  Then it traces name, val, function and plist
  (+8..+32).  Every =val= member is a WORD or an immediate (D9), so all
  four are traced; =next= is raw.  =nl_gc_mark_vectorlike= is unchanged:
  it still validates boxes taken from legacy views.  =nl_gc_mark_symbol=
  takes a =let=, so the inlined mark helpers carry one call, not four
  mark expansions.  That keeps the F1 prelink closure's root evidence
  small, and the closure includes this mark path.  The image walk's
  class-110 dedup goes through the same =nl_gc_mark_vbox=.
- Sweep (ported).  =nl_sweep_symbols=, beside =nl_sweep_conses= in both
  sweep paths.  Live cells feed the debt threshold and the gcstat symbol
  count.  Every mark-without-sweep reset clears the bits as it does for
  cons blocks: =nl_gc_mark_reset_all= and =bf_arena_mr_chunks=.
- Conservative scan (ported).  =nl_gc_conserv_typed= resolves a typed
  type-2 word through =nl_live_symbol_holding=.  The accepted offsets are
  the cell, the WORD (+6) and the five fields.  The scan envelope
  (=nl_gc_index_prepare=) now covers the typed groups as well as the
  chunks.  Before this change, a stack word naming a cons or symbol cell
  in a group outside the chunks' range was skipped before it reached the
  typed check.
- Image dump (ported, as for cons cells).  Pass 2 ranks the reached
  cells after the cons cells, in the symbol region.  During the dump the
  rank sits in header bits 32-63, with bit 25 meaning "ranked", and
  =+456= lists the cells by rank.  The writer emits each cell as a
  56-byte headered legacy block with its collector bits cleared.
  Relocation and the restore mapping go through
  =nl_dump_compact_logoff= and =nl_dump_compact_phys=.  A restored
  symbol is an image object, so it is never swept and is marked in the
  boot bitmap, as GNU's dumped symbols are.
- No moving.  Moving compaction is a debug path, gated off once any
  symbol cell has ever been allocated: symbols never move, so eq and
  eq-hash identity is the cell's address.
- Self-test.  =nelisp--debug-switch= 40 (make N cells), 41 (verify) and
  42 (counts) exercise the paths on this line, where no Lisp operation
  makes a symbol cell yet.  =tools/ai/gc-port-symbol-blocks.py= runs
  them, including a dump and restore, on both linkages (gc-port S1.8).

** Float blocks (word-heap S5, step (c))

GNU allocates a float from a =float_block= (alloc.c:2431), registered as
=MEM_TYPE_FLOAT= in the mem_node tree; make_float (alloc.c:2481) pops
=float_free_list=, else bumps =float_block_index=, else takes a new block.
The gcmarkbit of a float lives in the block's side bitmap (=gcmarkbits=).
sweep_floats (alloc.c:6894) rebuilds the free list from the bitmap and frees a
wholly free block once more than a block of free floats is held.
live_float_p (alloc.c:4764) accepts only a float's address.

Here, for the float objects of word-heap S5 (class 110, kind 3):

- Blocks (adapted size).  A float block is a 32 KiB typed block of type 3 from
  the 512 KiB groups that cons and symbol blocks use.  A cell is 16 bytes, the
  kind word (3) then the double, so a block holds 2046 cells, up to the =next=
  link at 32736.  GNU's cell is 8 bytes; Doc 216 has the route to that.
- Allocation (ported).  =nl_float_alloc= pops the free list (the link is at +8 of
  a free cell, whose kind word is 0), else takes the next cell of the current
  block, else a new block, and charges 16 bytes to the GC debt.  It answers 0
  when typed cells are disabled, in a parallel section (the free list has one
  writer) or when memory is exhausted, and =nl_float_object= then takes a
  general-heap object.  The state is =nl_float_state=, 128 bytes of BSS after
  =nl_exit_values= (free list, block list, registry index, live, free, block
  and allocation counts, the dump's rank count and array).
- Mark (adapted bit).  The gcmarkbit is bit 24 of the kind word, as for symbol
  cells (bits 0-23 are the kind).  =nl_gc_mark_vectorlike= and the image walk's
  dedup =nl_gc_mark_vbox= test the block type and take the bit; a float has no
  children, and an image or general-heap float keeps its block mark.
- Sweep (ported).  =nl_sweep_floats= sits beside =nl_sweep_conses= and
  =nl_sweep_symbols= in both sweep paths; every mark-without-sweep reset clears
  the bits (=nl_float_unmark_all=, =nl_float_clear_collector_bits=).
- Conservative scan (ported).  =nl_gc_conserv_typed= resolves a type-3 word
  through =nl_live_float_holding= (the cell, its WORD or a field of it; a cell
  beyond the block index was never allocated, a kind word other than 3 marks a
  free cell), as mark_maybe_pointer does for MEM_TYPE_FLOAT.
- Image dump (ported, as for symbol cells).  Pass 2 ranks the reached cells
  after the symbol region (rank in header bits 32-63, bit 25 = ranked); the
  writer emits each as a 24-byte headered block with its collector bits
  cleared; a restored float is an image object, never swept.
- No moving.  A typed float cell never moves, and moving compaction is gated
  off once any float block exists.
- Self-test.  =(nelisp--debug-switch 44)= answers (LIVE FREE BLOCKS ALLOCATED)
  float cells and 45 checks that a float held only by native frames survives and
  is a float_block cell.  =tools/ai/gc-port-float-blocks.py= runs the allocation,
  sweep and reuse cases, a dump and restore, and a second-generation dump and
  restore on both linkages (ledger S1.13).

** garbage-collect's counters (F1 of the speed unit)

GNU's =Fgarbage_collect= reports the totals its sweeps accumulate: =sweep_conses=,
=sweep_strings= and =sweep_vectors= each touch every object once and add to =gcstat=.
NeLisp's strings and vectors live in the general heap, which has no per-type sweep
(S1.2 is still open for them), and the explicit =garbage-collect= took its numbers
from an identity-set census of the marked edges.  Every legacy slot the marker
reached was classified (=nl_gc_typed_slot=, about 128 instructions a call) and
inserted into a hash table in an mmap'd scratch region, and then the whole intern
table was walked (=nl_intern_next=, 1,048,576 slots of 16 bytes) to count the interned
symbols: 37M of the 174M instructions of a steady-state collection of the churn
workload, and the cache and page-fault cost of the table besides.

The counts now come from the marker's first visit of each object, the nearest NeLisp
event to GNU's sweep visit.  =nl_gc_mark_block= answers 2 for a newly marked heap
block, 1 for a newly marked image block and 0 for a block already marked or not
one, and the marker's own branches count on the 2: a string at its character buffer
(=nl_gc_mark_legacy_slot=, tags 5 and 14), a mutable string at its box (6, 15), a
vector, record, char-table or closure at its box (=nl_gc_typed_vectorlike=, the word
vectors and tags 8, 9, 12, 17, 18, 19), a bool-vector at its box and a legacy cons at
its payload (=nl_gc_mark_cons=).  Cons-block, symbol-block and float cells are counted by
their sweeps, as before.  An image block is never counted (GNU never counts a pdumper
object).  A symbol is counted at its name block when that is a heap or image block, and
the interned symbols are the intern table's occupancy, walked once and cached under the
arena's bump pointer, which only an interning moves.  A tag-16 symbol (=make-symbol=) has
an identity that is not a block, so it alone still goes through the identity set.  The
empty string is one string, as in GNU.  Counting is on only in mode 4 of
=nl_gc_typed_state=, which =nl_gc_stats_run= sets for an explicit =garbage-collect=; the
other collections do not pay for it, and =nl_gc_typed_slot= is no longer called on the
marking path outside the census (mode 1) and the alias rewrite of =clear-string= (mode 2).

The census stays as the reference: =(nelisp--debug-switch 49)= collects once with
the identity set and once with the counters and answers =(MASK C0..C5 K0..K5)=, the
counters and then the census, MASK bit I set when row I differs.
=tools/ai/gc-port-gc-stats.py= (ledger S1.18) checks MASK = 0 after each of a dozen
scenarios on both linkages, and across a dump and a restore, where the image population
is not counted and the heap objects stored into it are.  With the conservative scan on, the
two collections pin different stack words and a few cells may differ (the check allows 64).
Two differences from the census are accepted: a string whose buffer another string with a
different length also names counts once (the census counted it twice), and an
uninterned symbol in the image is still counted, as the census always did.

** Bytecode VM safepoints (maybe_gc)

The bytecode interpreter never reaches a collection point.  GNU polls
=maybe_gc= in =exec_byte_code= at every =Bcall= (bytecode.c:797, after
=record_in_backtrace=) and on every 256th backward branch
(bytecode.c:861-866, =quitcounter=); eval.c polls it in =eval_sub= (2602)
and =Ffuncall= (3206).  NeLisp's =nl_gc_midform_collect= is called from
the interpreted =while= back edge (=lisp/nelisp-cc-sf-while.el=) and from
the native-bytecode poll (=lisp/nelisp-native-poll.el=), nowhere else, and
every VM activation allocates its frame vector (=nl_alloc_vector= of depth +
1, about 48 bytes for a small function), which only a sweep frees.

Measured on 2026-10-22 on the codegen lane's S5.13 workload (a GNU-compiled
function calling another, 18,300,000 times, under the 8 GiB cap): on this
line before the poll (c49) the run completes in 9.5 s with a peak RSS of 908
MiB (virtual 2.1 GB), growing linearly at about 48 bytes per call from 56 MB
and falling back only at the explicit =garbage-collect= after the loop;
=nelisp--gc-pressure= reads 5236 % at the end of the loop and the mid-form
collection counter is 0 before and after.  The same loop written as an
interpreted =while= saw-tooths between about 120 and 350 MB.  The eval/core
line allocates about 380 bytes per call in the same loop and exits 88 at
about 6.9 GB RSS.

A second gap showed once the VM polled.  The typed blocks (cons, symbol,
vector) are mapped by =nl_ablock_new_group= outside the arena chunks, so they
never move =chunk-bytes-reserved=, the counter the growth trigger watches; and
the debt trigger, which does count them, arms only after two collections
(=nl_gc_debt_due=).  A loop that allocates only typed cells therefore reaches
neither trigger.  A call-free bytecode loop that conses once per iteration ran
60,000,000 iterations to a peak RSS of 974 MiB with the poll in place and no
collection.  =nl_gc_vm_poll= carries a backstop for this window: before the debt
trigger arms, one chunk (64 MiB) of debt opens the gate, as a mapped chunk
would.  The cadence policy itself (two collections before arming) is the
gc-cadence lane's and is left as it is.

The contract this line provides:

- =nl_gc_vm_poll= (scripts/nelisp-standalone-build.el, after
  =nl_gc_midform_collect=): runs a mid-form collection when the growth or
  debt trigger is due, as the =while= back edge does, derives the budget
  again (next bullet) and returns 0.  Calling it unconditionally costs two
  loads and the gate (the armed flag, the reservation against the trigger,
  the debt test), about 51 instructions; a poll site should test the budget
  first.
- The budget, GNU's =consing_until_gc= (alloc.c, tested by =maybe_gc= in
  lisp.h).  =nl_gc_until= is a signed 64-bit word in the driver BSS (a
  linker symbol, =(data-addr nl_gc_until)=; =nl_gc_until_base=, 8 bytes
  after it, is the value it was last set to).  Every allocation fast path
  subtracts its bytes from it: the free-list and run paths of
  =nl_alloc_bytes= (strings, vectors, bignum limbs, boxes, large blocks) and
  the cons, symbol and float cells.  **A poll site is
  =(if (< (heap-read-u64 (data-addr nl_gc_until) 0) 0) (nl_gc_vm_poll) 0)=,
  one load and a compare, at every =Bcall= and every 256th backward
  branch.**  A nonnegative word proves that none of the triggers can be due:
  it is a slice of the headroom before the debt reaches its limit (64 MiB
  before the trigger arms, which is the backstop), at most 4 MiB, less one;
  it is set to -1 when the force hook is on or the reservation has reached
  the mid-form trigger, and a chunk mapping (the only thing that raises the
  reservation) and the hook make it -1 at once.  A negative word means
  "decide now": =nl_gc_vm_poll= decides exactly as before, collecting when a
  trigger is due, and refills.  The threshold policy is unchanged and stays
  the gc-cadence lane's (=nl_gc_debt_limit_for=); the budget only reads it, in
  =nl_gc_budget_refill=.  The debt is =nl_gc_stats+0= (folded at each refill)
  plus the slice spent, =nl_gc_debt_now=; =nelisp--arena-stats=, the pressure
  reading and the collection total use the exact figure, a raw reader of
  =nl_gc_stats+0= sees it only as of the last refill (at most 4 MiB behind).
  Debug switches: 76 answers the word, 77 its base, 78 the exact debt.
  =tools/ai/gc-port-budget.py= (ledger S1.19) checks all of it on a VM that
  polls this way.  A VM may sample, as callpath's did before this, but an
  inline test at every call is now cheaper than sampling.
- Call sites, GNU's: at =Bcall= entry before the callee is entered
  (bytecode.c:797), and when a counter of backward branches (a PC lower than
  the previous instruction's, plus the branches a fused fast loop reports)
  reaches 256 (bytecode.c:861-866).  A third site, the entry of a VM
  function called from a builtin (=sort=, =mapcar= with a bytecode function;
  GNU's =Ffuncall=, eval.c:3206), has the same preconditions once the
  arguments have been copied into the activation's frame; it is not part of
  this contract and is not tested here.
- Preconditions at a call site.  It is a VM instruction boundary where
  (1) every heap value the VM uses afterwards is reachable from the GC root
  stack (the activation's roots), a recorded evaluator frame, a heap object
  reachable from those, or a native stack slot (the conservative scan pins
  pointers, interior ones included, in [sp, stack top)); (2) no such value
  lives only in a callee-saved register (the scan does not read registers,
  see the next section; DSL locals live across a call are in stack slots
  because register promotion is limited to call-free loops); (3) caches of
  heap addresses (mirror entries, frame cursors) are dropped afterwards, as
  after any call that can run Lisp: objects never move in a mid-form
  collection, but a swept block is reused.  The gate refuses while a
  collection runs and parks parallel workers around one, so a worker needs
  no extra check.
- The force hook.  =(nelisp--debug-switch 70)= makes every poll collect (the
  trigger is zeroed before the gate), =71= restores the allocator's
  triggers, =72= answers the number of mid-form collections so far.
  =test/gc-port-vm-poll/force-check.el= replays the 152-case GNU bytecode
  corpus and an allocating loop with a collection at every poll (6,710
  collections on the reference build).
- The bounded-memory checks, =tools/ai/gc-port-vm-poll.py=, runnable
  against any binary: =leak= (the 18.3M-funcall workload: exit 0, the right
  answer, peak RSS at most 400 MiB), =loop= (60M iterations of a call-free
  bytecode loop that allocates a cons each: bounded only by the
  backward-branch poll and the backstop), =force= (the corpus under the hook,
  at least 100 forced collections: a VM without polls, or a binary without
  the hook, answers 0) and =check= (all three on both linkages).

With the inline test the same reference polls cost less than the call they
replace: on the 18.3M-call funcall workload, paired on CPU 8, the inline test
takes 0.947 of the time of the unconditional =(nl_gc_vm_poll)= at each =Bcall=
(8.46 s against 8.97 s), with the same 9 and 13 collections, 151 and 121 MiB
peaks and 6,710 forced collections (the cadence is unchanged).

Verified on a reference build, this line plus the two polls in this line's VM
(=tools/ai/gc-port-vm-poll-reference.patch=, kept for the VM's owners; the VM
itself belongs to the callpath lane and to the eval/core integrator): peak RSS
151 MiB (funcall) and 121 MiB (loop) on dyn, 147 and 116 on static, 9 and 13
collections; the corpus passes 152/152 under the hook on both linkages.
Controls: without the polls (c49) the funcall run peaks at 908 MiB, the loop at
973 and the hook answers 0 collections; with the polls but without the
backstop the funcall run peaks at 349 MiB and the loop at 975.

** Scanning callee-saved registers

GNU's =mark_memory= scans the C stack after =flush_stack_call_func= has spilled
the callee-saved registers (=__builtin_unwind_init= in lisp.h:4466, or =setjmp=
into a stack buffer; =mark_c_stack= at alloc.c:5212, =flush_stack_call_func1=
at alloc.c:5252), so a Lisp_Object that lives only in a register at a
collection is still found.  =nl_gc_scan_regs (TOP)= does the same for
=nl_gc_conserv_maybe=.  It is hand-assembled (the raw unit =gc-regs.o=): it
pushes rbx, rbp, r12-r15 (and rcx and r11, which the extern-call model keeps
intact; rdi and rsi too on Win64) and calls =nl_gc_conserv_scan= from the pushed
block up to the stack top, so the scan starts at the spilled values.  The arm64
targets keep the former behaviour (the scan from the caller's sp) until a spill
is written and run on that hardware.  Compiled code keeps live values in stack
slots, so none was lost before; register promotion would have lost them, which
this prepares for.

A collection cannot test it.  The collector's own frames leave stale copies of
a register in the slots of the frames the scan covers (a first version kept a
cons in r12 and collected: it survived with the spill switched off as well).  So
the test reads the window the stub hands the scan.  =(nelisp--debug-switch 73)=
runs =nl_gc_regs_selftest=, which loads five sentinels into rbx and r12-r15,
calls the real =nl_gc_scan_regs= with a TOP that ends the scan at the spilled
block (nine words: the pad, r11, rcx, r15 down to r12, rbp, rbx), and
=nl_gc_conserv_scan=, with a buffer named by =nl_gc_regs_trace=, copies that
window instead of scanning it: the answer is how many sentinels it shows (5).
74 is the negative control, a window of the same size at the caller's own frame
with no spill (0), and 75 answers how many times a collection has reached
=nl_gc_scan_regs=; the test requires =garbage-collect= to raise it.  Where
=gc-regs.o= has no self-test (Win64 and the arm64 targets) the switches answer -1
and the check fails.  =tools/ai/gc-port-regs.py= runs it on both linkages
(ledger S1.15).

* Expected effect and the remaining gap (S2)

Doc 220's churn profiles (base 9d5f4a515, four-layout means, millions of
Ir) put NeLisp cons churn at mark 991, index/prepare 287, rebuild 564,
allocation 106, zeroing 40 against GNU's whole-invocation GC plus
allocation of about 157. Most of NeLisp's cost is per collection over the
cold image: the index walk, the sweep walk and the marking of image objects
happen whatever the churned type. Typed blocks remove the allocator, index
and sweep work for churned objects only. The remaining gap is explained by
three GNU mechanisms this port does not yet reproduce:

- pdumper's dump is not swept and has a static object-start table
  (pdumper.c:5229); NeLisp still walks every image header in
  =nl_gc_index_prepare= and =nl_gc_sweep_merge_chunk=;
- =mark_object= trusts tagged pointers; NeLisp still probes the start index
  for every legacy object, image objects included;
- GNU marks with an explicit stack (alloc.c:6483); NeLisp recurses.

S2.1-S2.3 are therefore expected to stay red after S1; the criteria are not
revised. The measured numbers and their attribution are recorded in the
ledger.
