#+TITLE: Doc 214 — Importing application libraries from other languages
#+DATE: 2026-10-24
#+STATUS: DRAFT — candidate selection and acceptance design; no foreign library imported or runtime compatibility established

* 1. Objective and selection rule

Expand the libraries available to applications and services written in
Emacs Lisp on NeLisp by converting selected upstream implementations into
NeLisp packages. Preserve upstream behavior within an explicit supported
subset, and expose an idiomatic Emacs Lisp interface.

Only additional capabilities belong in the import backlog. Exclude
functionality already implemented in NeLisp, nelisp-emacs-lib, or reusable
GNU Emacs Lisp sources available in those projects. Do not select a
duplicate library simply to exercise another language frontend. Existing
provider integration and runtime compatibility repairs are separate tasks.

The selected six candidates are Mustache rendering, general structured
schema validation, reusable property-based testing, YAML documents,
WebSocket framing, and application workflow state machines. They are
proposals, not claims that their source already converts successfully.

* 2. Existing implementation audit

The bounded source audit covered =packages/= in NeLisp and =src/=,
=packages/=, relevant tests, and selected =vendor/emacs-lisp/= providers
in =../nelisp-emacs-lib/=. A separate =../nelisp-emacs/= directory was not
present in this checkout; the reusable implementation inspected here is
=../nelisp-emacs-lib/=.

The findings below establish source locations and scope. Tests were read
where relevant; application runtime tests and upstream suites were not
executed for this design. Vendored code, facade installation, host execution,
standalone execution, and browser execution are distinct availability states.
An existing source provider with an integration gap gets reuse priority;
that gap alone does not justify translating a second implementation.

** 2.2 Other existing providers and boundaries

- =packages/nelisp-json/= already owns JSON processing. Additions below
  consume its values and do not introduce another JSON parser.
- =packages/nelisp-sqlite/= supplies open/close, execution, selection, and
  transaction functions, with tests in its =test/= directory.
  =packages/nelisp-state/= is a persistent SQLite KV store, not an
  application workflow state machine.
- =packages/nelisp-http/= supplies HTTP client/cache helpers. Its API
  and the HTTP server above remain the transport reuse points.
- =packages/nl-contract/= supplies predicate, function, and result
  contracts. =packages/nelisp-apps-sdk/src/nelisp-apps-sdk-schema.el=
  validates app manifests and ABI declarations. Neither inspected surface
  establishes a general nested application-data schema library.
- =packages/nl-check/= performs expansion-time form checks.
  =../nelisp-emacs-lib/src/generator.el= provides iterators. These are
  different from reusable random input generators with shrinking;
  neither is used as evidence that fast-check's proposed scope exists.
- =packages/nelisp-toml/= owns TOML, not YAML document parsing.
- =packages/nl-ffi/= supplies external-library access. SQLite, libcurl,
  OpenSSL, and libsodium are not additional source-conversion work items
  in this document. Reuse applicable existing bindings; any genuinely
  missing cryptographic operation needs a separate, specific requirement.
  This does not assert that all four libraries have complete bindings.

* 4. Import architecture and ownership

#+begin_example
Pinned upstream source + license + selected upstream tests
    -> language frontend and explicit dependency closure
    -> semantic lowering / required compatibility helpers
    -> generated Emacs Lisp or nelisp-cc input, identified explicitly
    -> existing NeLisp compilation and package loading
    -> public Emacs Lisp adapter + standalone application tests
#+end_example

=../nelisp-cfront/= is a reference for frontend/backend separation and
generated compiler input. Its =.el= output is =nelisp-cc= grammar; the
extension alone does not establish that it can be loaded as ordinary
interpreted Emacs Lisp. Each import records its actual execution path.
Existing C frontend support does not imply JavaScript, TypeScript,
Python, or C# frontend support.

Language-specific work must preserve the semantics exercised by the
selected upstream source and tests:

- JavaScript/TypeScript: distinct null/undefined/false representations,
  truthiness, object lookup, closures, string operations, and exceptions.
  TypeScript types can be processed by an existing build-time compiler;
  runtime behavior and dependencies still require explicit conversion.
- Python: bytes versus text, iteration, exceptions, classes, and module
  dependencies. The wsproto framing subset avoids assuming that all of
  Python's HTTP/compression standard library has been ported.
- C#: required generic specializations, delegate calls, class/interface
  dispatch, and exceptions. Converting Stateless does not imply a general
  CLR, arbitrary NuGet support, or complete .NET library compatibility.

Keep generated implementation, semantic compatibility helpers, and the
public adapter separate. Do not add native primitives solely to make one
foreign library faster. Target opt-in packages; preserve existing runtime
and Emacs-compatible APIs. Package names and physical locations remain
unassigned until ownership and dependency checks are completed.

* 5. Reproducible import contract

Each accepted import must record:

1. Upstream project, immutable revision, license/SPDX data, original file
   hashes, and required notices. Preserve upstream source bytes.
2. The exact imported modules/functions and supported upstream API subset.
   Record dependency closure, generated sources, build-time tools, and any
   runtime host requirements separately.
3. Translator revision, options, patches, generation command, and output
   hashes. Use repository-relative paths or explicit environment settings.
4. Upstream test selection and expected behavior, including invalid inputs.
   Record unsupported cases as explicit scope limits; do not drop failing
   tests or silently skip unconvertible functions to obtain a pass.
5. Value/exception adapters and source-location mappings sufficient to
   trace failures to the pinned upstream implementation.
6. A reusable existing provider for each overlapping capability. Import
   only the proven delta; rerun the duplicate audit before widening scope.

A native binding or an invocation of Node, Python, or .NET can provide a
reference oracle. It does not satisfy the source-conversion acceptance
criterion. Host-assisted tests must not be reported as standalone execution.

* 6. Acceptance criteria

These are required future checks, not results obtained for this document.
Create a machine-checkable progress ledger before implementation, using
=../../../../.claude/reference/progress-ledger.md= and
=../../../../bin/progress-meter.sh=. Every implementation stage must end
with an actual end-to-end check; pending and unknown checks remain undone.

** 6.1 Common package gates

- The pinned upstream tests pass in their original runtime.
- The selected source converts without unreported skipped functions.
- Run the same deterministic inputs on upstream and imported implementations;
  compare values, errors, ordering, and relevant state transitions.
- Load the package and exercise its public adapter in standalone NeLisp,
  with foreign runtimes absent from the execution path.
- Include a negative control that fails with a deliberately broken result
  or implementation; a checker must distinguish failure from success.
- Record runtime identity, supported target, test counts, duration, and
  memory behavior. Apply the workspace memory/load limits to actual runs.
- If publishing for the browser, separately prove the package on Doc 213's
  browser target. A host or native pass does not establish browser support.

** 6.2 Package-specific minimums

| ID | Required behavior and integration example |
|----+-------------------------------------------|
| L01 | Compare upstream/spec fixtures for escaping, missing keys, nested context, sections, and partials. Render an application record into an HTML page and a notification body. |
| L02 | Accept valid nested records; reject wrong types and missing fields with exact paths. Exercise unknown-field policy, unions, transformations in the selected subset, and invalid schema use. Validate the same request through the existing application transport. |
| L03 | Prove seed reproducibility, a passing property, and a deliberately failing property that shrinks to a smaller witness. Test imported generators against the upstream pinned version; then use them on a separate NeLisp package. |
| L04 | Compare semantic values and serialization round trips for the declared YAML schema. Cover duplicate-key policy, malformed input, Unicode, multiline strings, and the chosen alias behavior. Load application configuration through its public adapter. |
| L05 | Compare frame sequences and connection events for masking, fragmented UTF-8, control frames, close handshakes, and invalid lengths. Exercise a real client/server echo and close through the existing network/HTTP adapters. Compression stays unsupported until its own tests pass. |
| L06 | Compare transition/guard/action order, hierarchy, invalid triggers, and reentry rules. Persist and restore an inspection/job workflow using the existing state/SQLite layer, with application-owned transaction boundaries. |

* 7. Delivery order

1. Confirm the six feature deltas and existing provider boundaries; pin
   sources/tests and identify the required language frontend coverage.
2. Deliver L01 and L02 with standalone examples and their original-runtime
   differential checks. Use existing CSV, numeric, and storage providers.
3. Deliver L03 and apply it to an independent package's public API; do not
   credit tests generated only on the host as an imported library pass.
4. Deliver L04, L05, and L06 as separate packages when their language and
   runtime prerequisites are proven. Each delivery includes a real consumer.

The first integrated application reads data through existing providers,
validates it with L02, stores it through existing SQLite/state APIs, renders
it with L01, and serves it through the existing HTTP layer. L03 exercises
its input handling. No excluded library becomes a prerequisite for this
milestone merely because it appeared in the earlier candidate survey.

** 9.2 Package and API proposal

Propose the opt-in package =packages/nelisp-mustache/=, subject to the
ownership checks in section 4. Keep a pinned upstream-source area,
generated implementation, compatibility helpers, public adapter, tests,
and generation recipe separately identifiable. Do not modify existing
HTTP, JSON, numeric, or CSV packages to install this package implicitly.

The first public API is a render operation taking a template, explicit
data values, and a partial-name map, returning text. Decide and document
the exact function name and value representation before implementation.
Function-valued views and lambda sections are outside this first subset.
Reject unsupported callable inputs explicitly rather than changing their
meaning or accidentally invoking a foreign runtime.

** 9.4 Frontend prerequisites and parity boundaries

The inspected source exercises JavaScript objects/prototypes, closures,
arrays, regular expressions, string operations, and exceptions. Confirm
coverage for the selected call graph before asking a worker to convert it.
A frontend that handles only arithmetic and control flow is insufficient.

Keep null, false, missing properties, and empty arrays distinguishable at
the adapter boundary. Include non-ASCII and supplementary-plane text in
comparison fixtures. Preserve upstream template/lookup behavior within the
declared subset; use existing escaping only if its exact output matches.
Record source-index/error differences if internal token positions cross
JavaScript and Emacs Lisp string representations.

Choose an explicitly pinned original-runtime test environment when M0
starts. Its dependency closure and test counts remain unverified here.
Do not mark L01 delivered at M1 or from generated text alone: the package
must pass its declared upstream comparisons, standalone checks, negative
control, and M4 consumer scenario.
