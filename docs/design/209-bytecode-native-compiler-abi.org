* §1 Purpose and scope

This document defines the ABI questions that must be settled before verified
bytecode CFGs can be lowered to callable native code. It separates the raw
runtime-unit interface that exists today from the boxed object/call interface
that a general bytecode compiler needs. It is a design constraint and evidence
record, not an implementation claim, shipped format, or authorization to call
an arbitrary native artifact.

The current bytecode frame IR can represent stack slots and verified control
flow for an admitted subset. That does not make its blocks callable native
code. In particular, Bswitch edges currently describe a snapshot of a mutable
constant hash table, and frame IR marks runtime switch lowering unsupported
until a mutation guard or equivalent dynamic dispatch is specified.

* §2 Verified current ABI: raw runtime units

The current raw-v1 interface is a deliberately narrow machine-word interface:

- The loader names it =nelisp-runtime-raw-v1= and accepts Linux =gnu/linux=
  =x86_64= only. Calls use the ordinary x86-64 SysV integer argument
  registers, up to six arguments, and one unsigned 64-bit result word.
- Its manifest names =nelisp-private-nelr-v1= as the artifact format and
  =nelisp-aot-raw-unit-v1= as the native payload format. The payload is
  serialized link-unit text plus explicit relocation/import metadata; it is
  not an ELF relocatable object.
- Its versioned layout id is
  =nelisp-runtime-reload-layout-v1:x86_64:sexp32:block16:bss-state64=.
  The =sexp32= label is a layout identity, not evidence that raw-v1 call
  arguments are validated or rooted Lisp objects.
- =nelisp-native-unit-call= admits only integer arguments of the declared
  export arity and returns a raw word. Unit staging refuses imports, and
  fixes the public export names, order, arities, and runtime binary identity
  for the lifetime of a unit id. This API is not a boxed Lisp function-call
  ABI.

=nelisp-native-load-raw-check= validates the raw kind, format, runtime ABI,
opt-in marker, layout id, platform, architecture, section sizes, exports,
imports, and declared artifact hash before mapping. The v1 loader carries the
binary SHA-256, layout id, build id, source SHA-256, artifact SHA-256, and
object SHA-256 on its handle where supplied by the manifest. The unit stage
path additionally compares the manifest binary hash to the running binary,
re-hashes the source and artifact around staging, validates the artifact's
own hash, and requires an empty imports list. These checks establish identity
and admission for this raw interface; they do not establish a boxed-object,
closure, or bytecode execution contract.

* §3 Existing boxed-object mechanisms (not a general compiler ABI)

There are useful mechanisms in adjacent runtime paths, but they do not close
the bytecode-native ABI:

- =nelisp-native-load-call= distinguishes =:abi raw= from =:abi boxed= and
  honors parameter and return representations. Its boxed path reserves an
  exclusive pinned boundary frame containing result, mirror/environment,
  frame, scratch, name, callback, and scratch-cell slots; it refuses a busy
  frame. This is a bounded trampoline convention, not yet the frame layout
  or stack-map contract for arbitrary compiler-generated control flow.
- =nelisp-eln-objects-encode= creates stable GNU views of supported object
  graphs, tracks roots in its unit, and records leases for pointer-valued
  objects. Activation decode only accepts pointer words leased by that
  activation; activation release drops those leases. The current main tree
  adds restricted S6-only cases: authenticated artifact-symbol words,
  entirely empty interned-symbol views, opaque identity-only interned-symbol
  views, and opaque identity-only vector views. Opaque symbol cells and
  vector contents are poison words checked at native boundaries; only exact
  admitted multi-import shapes can enable them, and vectors are not traversed
  or synchronized as ordinary object graphs. These are constrained bridges
  to authenticated ports, not general readable/writable object layouts.
  Selected conses, strings, bignums, and floats still use the existing
  leased-view paths. Neither these views nor the S6 registered-lambda
  constant resolution in =nelisp-eln-native-subr--resolve-constant-cells=
  define a general bytecode closure object ABI or captured-environment GC
  policy.
- Doc 207 demonstrates a narrowly admitted GNU Emacs 31.1 nonlocal-exit
  chain. Its safety depends on its exact authenticated imports, forward-only
  control flow, suppression after the first exit, and a dispatcher that
  captures and resumes the exit after native frames return. It is not a
  general unwind ABI for loops, arbitrary native calls, or VM frames.

These are precedent and implementation material. A future bytecode compiler
must name the selected mechanism explicitly in its manifest and prove that
its requirements are met; it must not infer that any raw-v1 export is a boxed
callable.

* §4 Required contract for a general boxed bytecode entry

The following items are mandatory before a compiler-generated bytecode
function can be admitted as a boxed native entry.

** §4.1 Values and object identity

Specify the tagged-word layout, immediate encodings, pointer/handle encoding,
word width, endianness, alignment, and supported object classes under a
versioned ABI id. Preserve Lisp identity and mutation semantics across every
boundary. A value word must never be mistaken for a raw integer or an address
without a declared representation. Define how constants and mutable constant
objects are retained and observed.

** §4.2 Allocation, safepoints, and GC roots

Every allocating or blocking operation must define when collection can occur.
At each such point the native frame must expose every live Lisp value through
an explicit stack map, pinned slot, or stable handle understood by the
collector. State whether objects move, how interior pointers are handled, and
how returned or callback-created objects acquire roots before the next
safepoint. Define root lifetime for normal return, error, quit, throw, unwind,
and cancellation. Raw machine temporaries are not roots.

** §4.3 Calls, callbacks, and results

Specify argument and result slot layout, arity rules, direct and indirect call
gateways, import authentication, callback re-entry, and the representation
of return values. A call must distinguish a Lisp result from error/quit/throw
status without smuggling condition state through an untyped integer. Define
tail-call behavior and whether generated code may call host/runtime primitives
directly. Preserve effects and evaluation order established by bytecode
verification.

** §4.4 Unwind and nonlocal exits

Define the frame record and handler/cleanup search order. A nonlocal exit must
cross generated frames while running each cleanup exactly once and releasing
roots only after values needed by cleanup are protected. Specify how native
and VM frames compose, how exits are captured/resumed, and how a cleanup that
signals a replacement condition behaves. Doc 207's admitted-chain protocol
can be reused only for code satisfying its admission proof; it cannot be
silently generalized.

** §4.5 Closures and function values

Specify a closure representation containing callable identity and captured
environment, how captures are rooted and updated, and how function-cell
lookup, dynamic rebinding, =funcall=, equality, and lifetime work. Define
re-entrant calls and recursive closures. Until function objects and captures
have a validated representation and GC policy, closure-valued constants,
indirect calls, and callback values remain unsupported.

* §5 Manifest lifecycle and cache identity

The raw-unit lifecycle is a useful precedent: stage validates without
publication, candidates have a 900-second TTL and bounded capacity, publish
checks the expected table/generation identity and atomically switches the
stable gates, and a rejected candidate is reclaimed. Publication records
generation, source/artifact hashes, binary identity, and a bounded history.
Superseded code and tables remain mapped because the runtime cannot prove no
caller is still executing through an old generation; current reclaim refuses
to release retired generations. These facts must remain visible in any
bytecode-native lifecycle contract.

The standalone artifact-lifecycle acceptance case now builds raw artifacts
from materialized byte-code objects without source forms. Equivalent inputs
produce identical stable manifest fields; changing bytecode or constants
changes native object identity. Rehashed manifests with a wrong runtime ABI
or binary SHA are refused by the real stage path without advancing the active
generation. Three valid stage/publish/call replacements reach generation 3.
A separately loaded boxed entry preserves a mutable constant's object
identity across forced GC and three open/close cycles. These bounded checks
exercise the existing lifecycle; they do not establish general cache reuse,
safe reclamation of retired code, or arbitrary bytecode support.

the reader's callback-port count. These indexed, authenticated ports expand
the bounded S6 import gateway; they do not make raw-v1 exports general Lisp

  moving or nonmoving for each object class.
- The canonical =sexp32= tagging, fixnum range, pointer compression, and
  portability story beyond x86_64/Linux.
- Stack-map encoding, safepoint placement, root-slot allocation, and the
  allocator/collector handshake for generated frames.
- How generated calls return conditions and nonlocal exits, how native frames
  compose with VM frames, and how cleanup replacement exits are handled.
- General closure and function-cell representation, captured-environment
  rooting, dynamic rebinding, and authenticated indirect-call policy. A
  registered-lambda artifact constant in an admitted S6 shape is a narrow
  existing mechanism, not proof of a general closure value ABI.
- Which mutable constants are snapshotted, rooted, guarded, or dispatched at
  runtime. In particular, Bswitch's current CFG edge snapshot is not sound as
  a runtime dispatch plan if its hash table may subsequently change.
- Exact manifest schema/versioning, cryptographic artifact identity fields,
  cache invalidation rules, concurrent publication policy, and safe retired
  generation reclamation.

boxed bytecode-native entries must be rejected as unsupported. Raw-v1 remains
limited to its current integer-word contract.
