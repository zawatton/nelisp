* 0. Purpose

This document is the live verification companion to Doc 38.

It exists to answer four questions at any point in time:

1. what lane is currently active;
2. what has actually been proven;
3. what still blocks the practical replacement claim;
4. which checks must be re-run after each shared substrate change.

This file is intentionally operational.  Update it as work lands.

* 1. Status vocabulary

Use only these status values:

| Status | Meaning |
|--------+---------|
| TODO | not started or not yet proven |
| IN-PROGRESS | active lane, current failure under investigation |
| BLOCKED | known blocker exists, but not enough evidence for closure |
| PROVEN | the stated level is currently supported by evidence |
| REGRESSION | previously proven, currently failing or untrusted |

Proof level uses the Doc 34 ladder:

- L0 readable
- L1 loadable
- L2 surface
- L3 representative execution
- L4 dependency chain
- L5 workflow
- L6 product path

* 4. Recheck rules

After any shared substrate change, re-run the smallest affected checks first.

Suggested order:

1. direct narrow test or vendor proof for the edited owner;
2. nearest lane sentinel;
3. the strongest currently passing workflow smoke that depends on that owner.

In practice:

- language/macro changes: recheck the focused proof, then a representative
  package load using those facilities;
- buffer/text-property changes: recheck focused tests, then Magit/Org-adjacent
  sentinels if relevant;
- file/process changes: recheck process smoke, VC/Tramp/Magit sentinels;
- replay/bootstrap changes: recheck probe harness and the current heavy-file
  repro.

* 5. Current operator policy

When choosing the next implementation task:

1. prefer a TODO or BLOCKED item in the highest-leverage lane;
2. prefer a change that unlocks multiple later rows;
3. keep Magit smoke green, but do not treat one green smoke as completion of
   the replacement goal;
4. do not mark an item PROVEN above the level actually evidenced.

* 6. Update procedure

When a task lands:

1. update the affected row status;
2. record the newly proven level;
3. replace placeholder verification text with the actual gate when useful;
4. note whether a larger dependent lane should be rechecked next.
