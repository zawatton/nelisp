* Executive Summary

NeLisp should not be positioned merely as a faster implementation of Emacs Lisp.
Its long-term objective should be to become an independent programming platform
that combines the strongest properties of Lisp with the deployment simplicity of
Go, the native execution model of systems languages, and an execution environment
designed for AI-assisted programming.

The core positioning is:

#+BEGIN_QUOTE
NeLisp is a self-hosted native Lisp for building tools, agents, servers, and
programmable systems.
#+END_QUOTE

The strategic differentiation should be built around four properties:

- Native execution
- Interactive development
- Self-hosting
- AI-native programmability

The project should preserve Emacs Lisp compatibility as a major ecosystem and
migration advantage, but it should not allow compatibility constraints to prevent
the design of a modern language and toolchain.

The target is not to outperform Rust at low-level systems programming, nor to
replace Python across every domain. The target is to create a category in which
NeLisp is the most natural choice:

#+BEGIN_QUOTE
A language for systems that must remain inspectable, modifiable, scriptable, and
AI-programmable while running as native software.
#+END_QUOTE


* 1. Project Vision

** 1.1 Mission

Build a modern Lisp platform that is:

- Simple to install
- Simple to build and distribute
- Fast enough for native applications
- Interactive during development
- Suitable for long-running services
- Suitable for AI agents and automation
- Compatible with a large part of the Emacs Lisp ecosystem
- Capable of self-hosting its compiler and runtime
- Usable without Emacs

** 1.2 Long-Term Vision

NeLisp should evolve from a language implementation into a complete software
platform consisting of:

- Language specification
- Native compiler
- Runtime
- Garbage collector
- Standard library
- Package manager
- Package registry
- Formatter
- Test runner
- Documentation system
- Debugger
- LSP server
- Build system
- FFI layer
- AI/agent runtime
- Application ecosystem

The desired developer experience should be comparable in coherence to Go or Rust.

** 1.3 Strategic Identity

NeLisp should be described as:

#+BEGIN_QUOTE
A native Lisp with live programming, self-hosting, Emacs Lisp compatibility, and
first-class support for AI-driven software.
#+END_QUOTE

The project should avoid being described primarily as:

- An Emacs extension language
- An Emacs Lisp clone
- A Lisp experiment
- A compiler research project

Those descriptions may be technically accurate in part, but they limit perceived
scope and adoption potential.


* 2. Strategic Positioning

** 2.1 Core Value Proposition

NeLisp should combine strengths usually found in separate language families.

| Property | Reference Ecosystem | NeLisp Goal |
|----------+---------------------+-------------|
| Simple deployment | Go | Single native binary |
| Native execution | Rust/C/C++ | Fast native code |
| Interactive development | Common Lisp/Smalltalk | Live REPL-driven workflow |
| Metaprogramming | Lisp | Macros and code-as-data |
| Existing ecosystem | Emacs Lisp | High compatibility |
| AI scripting | Python | Simple APIs and dynamic composition |
| Self-modification | Lisp/Smalltalk | Runtime redefinition |
| Self-hosting | Systems languages | Compiler/runtime written in NeLisp |

** 2.2 Target Market

Initial adoption should focus on developers building:

- Developer tools
- AI agents
- Automation systems
- CLI applications
- Build tools
- Infrastructure tools
- Local-first applications
- Long-running programmable services
- Embedded scripting environments
- Lisp-based DSLs

Only after establishing strength in these areas should the project aggressively
target broader application development.

** 2.3 Killer Use Case

The primary recommended killer use case is:

#+BEGIN_QUOTE
AI-native programmable agents whose behavior can be inspected and modified at
runtime.
#+END_QUOTE

Example:

#+BEGIN_SRC emacs-lisp
(defagent research-agent
  :tools '(web filesystem shell)
  :memory 'persistent

  (when (new-task-p)
    (research task)
    (write-report result)))
#+END_SRC

This should not merely be syntactic sugar around an API. NeLisp should make
agents, tools, structured state, dynamic code loading, inspection, and runtime
redefinition natural language-level concepts.


* 3. Language Design Principles

** 3.1 Compatibility Without Stagnation

Emacs Lisp compatibility should be treated as an adoption asset, not as the final
language boundary.

Recommended architecture:

#+BEGIN_EXAMPLE
                 NeLisp
                    |
        +-----------+-----------+
        |                       |
 Modern NeLisp APIs     Emacs Lisp Compatibility
#+END_EXAMPLE

Compatibility should be divided into tiers:

- Tier 1: Source-compatible standard forms
- Tier 2: Common Emacs Lisp libraries
- Tier 3: Compatibility shims
- Tier 4: Unsupported Emacs-specific runtime functionality

The compatibility level should be measurable and published.

** 3.2 Modern Core Language

NeLisp should introduce modern facilities where Emacs Lisp is weak or historically
constrained.

Candidates include:

- Modules
- Namespaces
- Pattern matching
- Structured data types
- Better error objects
- Async/await
- Tasks
- Channels
- Futures/promises
- Structured concurrency
- Optional type annotations
- Better foreign types
- Standardized immutable data structures
- Explicit package metadata

Example:

#+BEGIN_SRC emacs-lisp
(module http-server
  (export start-server))

(struct response
  status
  headers
  body)

(match request
  ((request :method "GET" :path "/health")
   (response 200 nil "ok")))
#+END_SRC

** 3.3 Lisp Semantics Must Remain Central

NeLisp should not become "Rust with parentheses."

The language must preserve the reasons Lisp remains powerful:

- Homoiconicity
- Macros
- Interactive evaluation
- Symbolic manipulation
- Runtime introspection
- Dynamic redefinition
- DSL construction
- Minimal syntactic complexity

Any feature that destroys these properties should require extremely strong
justification.


* 4. Runtime Architecture

** 4.1 Native Execution

The production path should generate native executables that do not require Emacs.

Target workflow:

#+BEGIN_SRC shell
nelisp build --release
./my-app
#+END_SRC

Expected properties:

- No Emacs dependency
- Predictable startup time
- Reproducible builds
- Debug and release build modes
- Static or mostly self-contained distribution where practical
- Cross-platform output

** 4.2 Interactive Runtime

A major differentiator should be live interaction with a running program.

Desired workflow:

#+BEGIN_EXAMPLE
edit
  |
compile function
  |
load into running process
  |
inspect state
  |
continue execution
#+END_EXAMPLE

The runtime should support:

- Function redefinition
- Variable inspection
- Stack inspection
- Heap inspection
- Dynamic module loading
- Live patching
- REPL attachment to running processes

** 4.3 Self-Hosting

NeLisp should progressively move compiler and runtime components into NeLisp.

Long-term self-hosting targets:

- Reader
- Parser
- Macro expander
- Compiler
- Optimizer
- Object writer
- Package manager
- Build tool
- Documentation generator
- Test runner

A minimal bootstrap layer in C/Rust/assembly is acceptable where required for
platform integration.

** 4.4 Garbage Collection

GC design should prioritize:

1. Correctness
2. Predictable latency
3. Developer ergonomics
4. Throughput
5. Memory efficiency

The runtime should expose GC metrics and diagnostics.

Example:

#+BEGIN_SRC emacs-lisp
(runtime:gc-stats)
(runtime:heap-summary)
#+END_SRC

Future options may include:

- Generational GC
- Incremental GC
- Concurrent marking
- Region-based allocation for temporary workloads
- Arena APIs for systems-oriented code


* 5. Concurrency Model

** 5.1 Objective

Concurrency should become one of the language's visible strengths.

The goal is not merely internal runtime parallelism. It should be easy for users
to express concurrent programs.

** 5.2 Proposed Model

Recommended primitives:

- task
- spawn
- await
- channel
- select
- parallel-map
- cancellation
- structured concurrency scopes

Example:

#+BEGIN_SRC emacs-lisp
(let ((a (async (download url-a)))
      (b (async (download url-b))))
  (await-all a b))
#+END_SRC

Server example:

#+BEGIN_SRC emacs-lisp
(spawn
  (http:serve :port 8080))
#+END_SRC

Parallel collection processing:

#+BEGIN_SRC emacs-lisp
(parallel-map #'compile-source source-files)
#+END_SRC

** 5.3 Design Constraint

Concurrency must remain simpler than Rust async programming.

The desired mental model is closer to Go in usability while preserving Lisp's
runtime dynamism.

* 8. Foreign Function Interface

** 8.1 Goal

NeLisp must be able to consume existing ecosystems rather than rebuilding every
library from scratch.

The FFI should be extremely simple.

Example:

#+BEGIN_SRC emacs-lisp
(ffi:library "sqlite3")

(ffi:defun sqlite3-open
  ((filename string)
   (db pointer))
  :returns int)
#+END_SRC

** 8.2 Bindgen

Provide automatic header binding generation.

#+BEGIN_SRC shell
nelisp bindgen sqlite3.h
#+END_SRC

** 8.3 Interoperability Priorities

Priority order:

1. C ABI
2. Rust libraries through C-compatible interfaces
3. OS native APIs
4. Python interoperability
5. JavaScript/WASM interoperability

Python interop may eventually support:

#+BEGIN_SRC emacs-lisp
(import-python "numpy")
#+END_SRC

This should be considered an ecosystem bridge, not a dependency of the core
runtime.

* 12. AI-Native Programming Model

** 12.1 Objective

NeLisp should be designed for programs that are partially written, modified, or
orchestrated by AI systems.

This should become a first-class strategic differentiator.

** 12.2 Agent Abstraction

Example:

#+BEGIN_SRC emacs-lisp
(defagent research-agent
  :model "gpt-5"
  :tools '(web filesystem shell)
  :memory 'persistent
  :policy 'research-policy

  (on-task task
    (let ((sources (research task)))
      (write-report sources))))
#+END_SRC

** 12.3 Tool Calling

Example:

#+BEGIN_SRC emacs-lisp
(deftool read-file (path)
  :input ((path string))
  :returns string
  (fs:read-text path))
#+END_SRC

** 12.4 Structured Output

Example:

#+BEGIN_SRC emacs-lisp
(defschema market-report
  (summary string)
  (risks (list string))
  (opportunities (list string)))
#+END_SRC

** 12.5 Runtime Mutation

AI agents should be able to modify selected code safely.

Required concepts:

- Capability boundaries
- Module permissions
- Sandboxed evaluation
- Transactional code loading
- Rollback
- Audit log
- Signed modules
- Policy enforcement

This is critical. "AI-native" must not mean arbitrary unrestricted self-modifying
code.

** 12.6 MCP Support

NeLisp should provide first-class MCP support.

Example:

#+BEGIN_SRC emacs-lisp
(require 'mcp)

(mcp:server
  :name "filesystem-tools"
  :tools '(read-file write-file list-directory))
#+END_SRC

* 16. Performance Strategy

** 16.1 Goal

NeLisp does not need to beat Rust in every benchmark.

The strategic performance target is:

#+BEGIN_QUOTE
Much faster than typical dynamic scripting languages, while retaining an
interactive Lisp development model.
#+END_QUOTE

** 16.2 Performance Priorities

Priority order:

1. Startup time
2. Function call overhead
3. Allocation performance
4. GC latency
5. String processing
6. Hash tables
7. File I/O
8. HTTP workloads
9. Concurrency
10. Numerical workloads

** 16.3 Benchmarks

Create a public benchmark suite containing:

- Startup
- Fibonacci
- JSON parse/serialize
- Regex
- HTTP server
- File traversal
- Hash map operations
- Parallel map
- Compiler throughput
- Agent orchestration workloads

Compare against:

- Emacs Lisp
- Common Lisp
- Python
- Go
- Rust
- Lua
- JavaScript

Benchmark methodology must be transparent and reproducible.


* 17. Security Model

** 17.1 Importance

AI-native and dynamically programmable systems create additional risk.

Security must therefore be a language/runtime design concern.

** 17.2 Capabilities

Introduce explicit capability objects for:

- Filesystem
- Network
- Process execution
- Environment variables
- Native FFI
- Package installation
- Runtime code mutation

Example:

#+BEGIN_SRC emacs-lisp

  (run-agent task))
#+END_SRC

** 17.3 Sandboxing

Future sandbox mechanisms may include:

- Process isolation
- seccomp on Linux
- sandbox-exec alternatives on macOS
- Windows job objects/restricted tokens
- WASM execution mode
- Restricted evaluator
- Resource quotas

* 24. Final Design Principle

The central strategic principle should be:

#+BEGIN_QUOTE
Do not build NeLisp as a better historical Lisp implementation.

Build NeLisp as the Lisp that developers would design if Lisp were being created
today for native applications, live systems, and AI-assisted software development.
#+END_QUOTE

NeLisp should preserve the fundamental Lisp advantage:

#+BEGIN_QUOTE
Programs are not static artifacts. They are inspectable, transformable, and
programmable systems.
#+END_QUOTE

Go demonstrates the value of simple deployment.
