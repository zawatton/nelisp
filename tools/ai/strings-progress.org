#+TITLE: Strings: GNU 31.1 struct Lisp_String with sdata blocks and compaction

# User decision 2026-10-21: fix the representation first, imitating GNU.
#
# NeLisp strings still sit behind 32-byte views, aliased string views and
# per-producer copies. Word-heap S3 (strings header-less) is open, and gc-port
# marks string compaction blocked on it. The unibyte residual lane found the
# string-producer workload 46.85x slower than GNU in wall-clock.
#
# GNU 31.1 alloc.c:
# - struct Lisp_String headers in string_block;
# - character data in sblock/sdata, allocated by allocate_string_data;
# - large strings in their own sblocks;
# - sweep_strings frees headers, and compact_small_strings slides live sdata
#   and fixes back pointers;
# - multibyte and unibyte follow GNU's size_byte rules.
#
# This lane owns the string half of word-heap S3. gc-port owns the GC driver
# and calls this lane's string sweep and compaction; agree the hook points
# with it through the coordinator.
#
# Base: eval/integ-20261021w (eval/core 7d2d49fa3 plus the word-heap line,
# in final checks).
#
# Bar: wall-clock own cost against GNU 31.1, as paired per-round ratios on

** S1.1 Strings are header-less word-heap objects in GNU 31.1's layout: a 32-byte struct Lisp_String header in a string block plus sdata (sdata_size(8) = 24 B), so at most 56 B per 8-character unibyte string excluding block bookkeeping; the census of string views and copies is 0
#+NOTE: 2026-10-21 coordinator: the strings lane stopped on a GNU-against-ledger contradiction (target/strings/blocker.json). GNU's Lisp_String is 32 B (lisp.h:1555-1579) and sdata_size(8) is 24 B (alloc.c:1352-1394), so GNU's own structure needs at least 56 B, above the word-heap S0-revised 48 B. That threshold predates the user's 2026-10-21 rule to imitate GNU's implementation, so GNU's layout is the target. The criteria count is unchanged.
#+NOTE: 2026-10-22 GNU-layout reconciliation: S1.1's historical word-heap 'header-less' wording and Doc 216 S0 packed kind/length proposal conflict with GNU lisp.h:1555-1640. As authorized, the canonical WORD is a tagged pointer to the genuine 32 B header; its fields hold character count and size_byte, not a packed word-heap header. Existing symbol encoding stays unchanged. The retained-root check observes 56 -> 56 B per eight-byte string, and 40 -> 0 B per extra alias; the unchanged 56 B predicate rejects the legacy base.
#+NOTE: 2026-10-22 GNU byte-unit clarification: the 56 B census uses eight payload bytes (eight unibyte characters). GNU alloc.c:1352-1394 sizes sdata from SBYTES: 32 + align8(nbytes + 9). Eight multibyte Han characters occupy 24 bytes and therefore 72 B of header+sdata. As authorized, GNU structure governs this other word-heap S0 wording conflict; the eight-byte 56 B check and zero-owned-alias requirement are unchanged.
