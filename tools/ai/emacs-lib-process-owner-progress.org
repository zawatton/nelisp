#+TITLE: emacs-lib: one owner for processes on the standalone

Objective (user, 2026-11-13): unify the process implementations.  At
da5adaa85 the standard process functions are defined in up to four places
(scripts/nelisp-stdlib-prelude.el, emacs-process-builtins.el,
emacs-process-events.el, emacs-cc-pipe-process-1.el, emacs-cc-process-1.el,
emacs-eventloop.el, lisp/nelisp-process-buffer.el) and whichever loads last
wins.  Measured defect: a process made with :buffer and no :filter gets
`process-filter' = nil and its output is never inserted (GNU: the filter is
`internal-default-process-filter', which inserts at the process mark).  This
breaks vc-print-log (smokes ledger S1.3) and any package that reads process
output from a buffer.

Rule (unification plan 2026-11-03, criterion 1 and 5): one representation and
one owner per concept.  Process primitives are GNU C-level, so the NeLisp core
owns them where it defines them; emacs-lib keeps only thin delegates or
`fboundp'-guarded fallbacks with no state of their own.

Read with (from the NeLisp repo root, target/nelisp present):
  NELISP_BIN=target/nelisp bin/progress-meter.sh --ledger tools/ai/emacs-lib-process-owner-progress.org

* S4 One pipe representation (added 2026-11-14)

The core buffer pipe (lisp/nelisp-process-buffer.el) is the one pipe
representation.  At 18369f42c emacs-lib keeps a second one (OS-pipe vectors in
emacs-cc-pipe-process-1.el), and a pipe from `make-pipe-process' passed as
`:stderr' to `make-process' (GNU epg.el pattern) signals
wrong-type-argument processp on the standalone.
