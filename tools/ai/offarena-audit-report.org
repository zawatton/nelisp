#+TITLE: Off-arena memory audit: GC-managed addresses stored where the GC never scans
#+DATE: 2026-11-03

* Method

Read-only source audit of origin/main 5a61f834a (no build, no target/nelisp run).
For each in-scope file I located every off-arena allocation (anonymous or file
mmap via =syscall-direct 9=, =nelisp-native-load--mmap=, =nelisp-os-mmap=, and
runtime =nelisp-os--alloc= buffers that the stdlib comments describe as
malloc'd), then every =ptr-write-*= / =nelisp-os-write-*= into that memory,
and classified each written value: integer, raw bytes, code, off-arena
address (safe) or arena address (alloc-bytes block, =nl_alloc_str= payload,
=nl_alloc_vector= box, cons/Sexp box).  An arena address is safe only if Lisp
keeps it live (variable, list, hash table) for as long as the off-arena word
holds it.  Reference fix pattern: =nelisp-native-load--slot-pins= in
lisp/nelisp-native-load.el (keep the address as an integer in a hash table).

Scope command (run from the repository root):

#+begin_example
grep -rlE 'syscall-direct 9 |native-load--mmap|\bmmap\b|"malloc"|"calloc"|"realloc"' scripts/nelisp-stdlib-prelude.el packages lisp --include='*.el' | grep -v '/test/'
#+end_example

This lists 19 files.  Verdict counts (rows, not files): 0 at-risk, 25 safe,
14 out-of-scope.  Rows total 39.

Caveats: static reading only; no probe was run (ledger S2.1 stays pending).
Native-code-written values (results in the =out= slot, callback slots) are
generated by AOT code whose GC discipline was not audited here.

* At-risk details

No row is rated at-risk.  The two known cases (box string arm, scratch vector)
are fixed via slot-pins and re-checked above.  One rated-safe item remains a
watch item because it depends on code I did not audit:

** nelisp-native-load-call (lisp/nelisp-native-load.el:2762), native-written results

Code path: native code writes a result Sexp (string payload or vector box)
into the mmap =out= slot; =nelisp-native-load-unbox= then reads tag, payload
pointer and length.  =nelisp-native-load--payload-string= copies the pointer
into a Lisp variable before its first loop, so the post-return path is safe.
The unaudited part is the interval inside the native call: if generated code
re-enters the evaluator (aot_builtin_call dispatch) and a =while= back-edge
collects, an arena object held only by the =out= or callback slot would be
freed.  Rated safe on the assumption that the rootstack and EvalCtx frames
cover such values.

Probe sketch (run only if someone wants to retire the uncertainty):
1. Allocate a victim with =alloc-bytes= (say 64 bytes, align 8); write a
   distinct marker M into word 0.  Store its address ONLY in an mmap'd word
   (=nelisp-native-load--mmap 4096 nil= then =ptr-write-u64=), then drop every
   Lisp reference (setq the variable to nil; keep the mmap base).
2. Run =(garbage-collect)=.
3. Churn: allocate several hundred same-size =alloc-bytes= blocks, writing a
   distinct word 0 into each.
4. Read word 0 through the saved address.  A changed word (or equality with a
   churn block's marker) means the block was reclaimed and reused: reproduced.
5. Positive control: store the victim address XOR-masked (for example
   =(logxor addr #x5a5a5a5a5a5a)=) in a Lisp variable instead of the plain
   address, drop the plain one, run the same garbage-collect and churn.  The
   block must be reclaimed (word 0 changes).  If the masked control is NOT
   reclaimed the probe is invalid because the GC found the block another way.
6. Negative control: repeat step 1 but also keep the address as a Lisp integer
   (the slot-pins pattern); word 0 must stay M.
For the native path specifically, repeat step 1 with the address placed in
the =out= slot of a loaded handle by a native function that calls back into
Lisp with a =while= loop long enough to trigger a mid-form collection.

* Decision (coordinator, 2026-11-03)
- No at-risk site. Coordinator spot check: lisp/nelisp-native-unit.el, lisp/nelisp-native-callsite.el and lisp/nelisp-stdlib-os.el call neither alloc-bytes nor any nl_alloc_* constructor, so they create no arena object to leak into their mmap'd or malloc'd memory.
- The two sites in lisp/nelisp-native-load.el that do leak into mmap'd slots were fixed in a3f79db87 and 5a61f834a, and the slot-pin smoke polices them.
- Watch item, not probed: a result Sexp that native code writes into the mmap'd out slot is unpinned between the ptr-call return and nelisp-native-load-unbox. The unbox reads the payload pointer into a Lisp integer, which pins it, before its first while loop, so no GC point is known in that gap. GC inside the native call depends on the generated code's rootstack discipline, which this audit did not cover.
- This is a static audit. The earlier rawptr audit missed the scratch-vector defect statically, so "safe" here means "no arena write found", not "proven by probe".
