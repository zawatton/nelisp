#+TITLE: GNU runtime speed diagnosis and measured comparisons
#+DATE: 2026-10-24

* Status and measurement scope

GNU speed parity is not achieved. Current experimental candidate D5 improves
ordinary-vector access and equal recursion, but fails the unchanged
old-baseline regression limit and strengthened warmed FX GC acceptance.
D4 is the preserved previous candidate. Both still exceed GNU elapsed time
in the repeated top-level builtin corpus.
Wall time is the acceptance metric; instruction and frame counts explain
possible causes but cannot establish speed parity.

The user subsequently challenged strict measurement comparability. The D5
tables remain exploratory comparisons of the explicitly different execution
configurations below; they cannot establish matched-mode GNU parity.
Independent Astra audit verified identical generated fixtures, final N,
warm/reset sequence and timer expressions across roles in each campaign.
Every timed NeLisp body has an FX record, while GNU interprets source;
actual executor entry and GC telemetry were not proved by these reports.
The longer vector campaign uses CPU0, whereas the bounded20 campaign uses
CPU12; CPU is matched within each campaign. Generic calibration chooses N
separately per role even though the final Ns in these two reports coincide.

Strict replacement qualification separates source interpretation on both
runtimes and the identical genuinely GNU-generated bytecode on both.
It requires actual executor/retained-operation proof, runtime input aliasing
checks, common fixed work/chunks/reset schedules, active GC policy/counters,
isolated timing jobs and uncertainty reporting. Quoted equal inputs may be
merged by compilation, so new fixtures must construct distinct structures.
Bounded slow-case resource failures and short intervals remain visible.
Audit =target/astra-measurement-protocol-audit.md=; strict qualification and
new timings are incomplete. No old data is relabelled as strict parity.

The comparison contexts below are deliberately distinct:

- Top-level dispatcher loops use fresh-process N/2N elapsed-time slopes.
- The twenty-function corpus measures complete closed-function loops under
  each runtime's normal execution configuration. NeLisp may use its automatic
  FX path; GNU uses interpreted source. This is a default-configuration
  comparison, not proof of an exclusive matching engine.
- Historical call-floor diagnostics subtract an empty loop in the same
  process. They cannot replace complete-loop acceptance.
- Practical workflows include their stated validation work and collections.

Three-round studies are exploratory. CPU affinity, raw output, executable and
cold-image identities, calibrated iteration counts and short intervals remain
in the reports. Concurrent machine activity prevents a universal speed claim.

* Diagnosis and implementation priorities

The separate gpt-6-astra ultra audit is complete:
=target/astra-speed-d5-audit.md=, SHA
=fc9a00d5b83db2257b1707c0f65c43e24e13a8e25bfc9bf95a0c855443d9c615=.
It found no material weakening in the D5 route-proof adapter. Actual binary
group initialization grew from20624/22624 to20896/24656 bytes. Source proves
that shared list/frame bodies add mode tests at indexed reads; this does not
yet prove the fraction of runtime cost or isolate timing causality. A separate
list/frame group generation slice is being tested before a new build.

Current equal still runs Lisp atomic predicates before identity, whereas
GNU internal_equal_1 checks BASE_EQ before type dispatch and uses native
field access for descent. A captured private intrinsic identity guard is the
next small overlay; public eq advice/redefinition must remain invisible.

Current char-syntax validates and decodes through Lisp calls, gethash and
char-table aref; the new ordinary-vector primitive deliberately declines
that char-table representation. GNU uses direct native character/table
operations. Current regexp already has mutation-checked cached patterns
and specialized plans, so the old Claude cache diagnosis cannot simply be
reapplied. Its matcher and entry setup still execute in Lisp, while GNU uses
native regexp execution. Hash calls still consume list arguments and perform
callback, moving-GC and weak-table work. Removing opaque transport safely
requires a separate word-argument helper and callback/weak-GC acceptance.
These are source-level differences, not measured time shares.

1. The enlarged initialized dispatcher accompanied a measured regression. D4
   splits literal name resolution from two initialized handler groups.
   Actual ELF routes now zero 20880/22880 bytes versus D3's 59360 bytes;
   the resolver has no calls, indirect jumps, syscalls or non-stack writes.
   Actual proof: =target/dispatch-name-split/d4-native/evidence.json=.
2. Generic calls construct argument conses after values are already rooted.
   The isolated argument-frame slice removes those conses only for handlers
   with proven indexed access. It preserves canonicalization, lazy debug
   frames, errors, the public ABI and the original unsupported fallback.
   Frozen-source audit and actual-runtime qualification are still required.
3. Practical ring hot paths use aref/aset/length, whose list-consuming general
   handlers remain outside that structural proof. Astra approved a separate
   ordinary-vector FX primitive slice using existing access kernels, exact
   arities/type/bounds, live function authentication and unchanged fallback.
   Char-table bridge shapes and all unsupported representations decline.
4. Interpreter/global-variable loops, bytecode calls, multibyte substring,
   and checked file processing remain separate measured gaps. Do not infer
   their time shares from instruction counts or generalize one successful
   vector case to the complete runtime.

Acceptance remains the nine machine-checkable criteria in
=tools/ai/gnu-runtime-speed-progress.org=. Measurement preparation and native
safety progress are not percentages of the speed gap closed.
